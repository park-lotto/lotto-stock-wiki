# 두 모델로 최고의 결정 찾기 — 논의 규약

_2026-09-09 · 코덱스(기본) × 클로드(오푸스/페이블)_

---

## 왜 필요한가 — 오늘 실제로 있었던 일

사장님이 "초가 짧다"고 하셨을 때, 클로드는 **글자수 게이트**를 파고 있었다.
그건 원인이 아니었다. 진짜 원인은 **재료가 아예 안 들어간다**는 것이었고,
사장님이 "밀도가 없다" → "볼 이유가 없다" → "GPT는 잘 뽑는데"라고 **세 번 다시**
말씀해 주셔서야 닿았다.

즉 **틀린 층을 파고 있는데 혼자서는 모른다.** 그걸 잡아주는 게 두 번째 모델이다.
사장님이 세 번 말해주는 자리를, 모델이 대신하는 것이다.

---

## 규약 — 4단계

### ① 문제를 한 파일에 적는다

```
docs/decide/<날짜>-<주제>.md
```

사장님(또는 먼저 붙은 모델)이 **질문 하나**만 적는다. 답을 적지 않는다.

### ② 두 모델이 **서로 안 보고** 각자 답한다  ★핵심

**먼저 쓴 답을 보고 쓰면 그쪽으로 끌려간다.** 그러면 두 모델을 쓴 의미가 없다.
각자 자기 칸에만 쓴다. 상대 칸은 자기 답을 쓰기 전에 **열지 않는다**.

각자 반드시 담을 것:
```
□ 결론 한 줄
□ 근거 — 실측 수치·파일·줄번호. "그럴 것 같다" 금지
□ 이 답이 틀렸다면 무엇 때문일까 (자기 답의 약점)
□ 확인 못 한 것
```

### ③ 서로 **비판한다** — 동의는 답이 아니다

상대 답을 읽고 각자 적는다. **"동의합니다"만 쓰면 그 라운드는 실패다.**

```
□ 상대 근거 중 실측으로 확인 안 된 것은 무엇인가
□ 상대가 안 본 층(입력·데이터·설정·다른 경로)은 없나
□ 상대가 맞다면 내 답의 어디가 틀렸나
□ 갈린다면 — 무엇을 재면 갈리나  ← ★이게 제일 중요하다
```

### ④ 갈리면 **말로 이기지 말고 재서 이긴다**

의견이 갈리면 논쟁을 늘리지 않는다. **실측 명령 하나**를 정해서 돌린다.
결과가 나온 쪽이 이긴다. 잴 수 없으면 그 사실을 적고 사장님께 올린다.

```
판정 방법 : (예) 라이브 DB 5,202편에서 X를 세면 갈린다
결과      : (붙여넣기)
결론      : 
```

---

## 사장님이 보는 것

**마지막 줄만 보시면 된다.**

```
결론      : 
왜        : (한 줄)
못 정한 것 : (있으면. 사장님이 정하실 것만)
```

논쟁 과정은 파일에 남지만 읽으실 필요 없다.
**사장님께는 사장님만 답할 수 있는 것만 묻는다** — 돈·우선순위·방향·포기할 것.
기술 선택은 두 모델이 재서 정한다.

---

## 일은 어떻게 나누나

**같은 파일을 동시에 고치면 반드시 깨진다.** 이 저장소엔 이미 격리 장치가 있다.

```
py tools/track.py start <트랙명>     # .tracks/<트랙명> 폴더 + 브랜치
py tools/track.py finish <트랙명>    # 게이트 통과해야만 라이브
```

- **모델마다 다른 트랙**을 준다. 서로의 폴더를 건드리지 않는다.
- 메인 폴더의 코드는 **누구도** 고치지 않는다.
- 병합은 `finish`가 게이트(문법→import→pytest)를 돌린 뒤에만 한다.

### 서로의 코드를 리뷰할 때

```
git -C .tracks/<상대트랙> diff main...HEAD
```
읽기만 한다. **남의 트랙 파일을 고치지 않는다** — 고칠 게 있으면 논의 파일에 적는다.

## 하지 말 것

```
✗ 상대 답을 보고 자기 답을 쓰기          → 끌려간다. 두 모델 쓴 의미가 없다
✗ "동의합니다"로 끝내기                  → 비판이 없으면 라운드 실패
✗ 근거 없이 우기기                       → 실측 명령을 내고 재라
✗ 3라운드 넘게 논쟁하기                  → 못 정하면 사장님께 올린다
✗ 사장님께 기술 선택을 묻기              → 재서 정한다
✗ 같은 파일을 두 모델이 동시에 고치기    → 트랙을 나눠라
✗ 정답지 없이 "정확도 올랐다" 주장       → before/after를 사람이 보게 내라
```

## 언제 이걸 쓰나

**매번 쓰지 마라.** 오버헤드가 결과보다 커진다.

| 쓴다 | 안 쓴다 |
|---|---|
| 같은 증상이 **두 번 이상** 재발할 때 | 오타·문구 수정 |
| 뿌리가 안 잡힐 때(“고쳤는데 그대로”) | 이미 원인이 명확한 버그 |
| 되돌리기 어려운 설계 결정 | 일상 작업 |
| 비용·속도 트레이드오프 | 사장님이 이미 방향을 정한 것 |

## ★실제로 어떻게 쓰나 — 이 창이 단체방이다 (2026-09-09 추가)

클로드는 Bash로 `codex exec`를 **직접 부를 수 있다**(도구: `tools/discuss.py`).
그래서 사장님은 **창 하나에서만** 말씀하시면 된다. 파일을 옮길 필요가 없다.

| 사장님이 쓰는 말 | 클로드가 하는 일 |
|---|---|
| `@코덱스 …` | 코덱스에 던지고 답을 화면에 그대로 붙인다 |
| `@둘다 …` | ①내 답을 파일에 **먼저 봉인** → ②코덱스 호출 → ③서로 비판 → ④결론 3줄 |
| `@코덱스 이 작업 해` | 코덱스 트랙을 만들어 작업시킨다(내 트랙과 분리) |
| (지정 없음) | 클로드가 한다 |

```
py tools/discuss.py log  "<주제>" 클로드 "<내 답>"     # ★코덱스를 부르기 전에 먼저
py tools/discuss.py ask  "<주제>" "<질문>"             # 코덱스 호출(read-only)
py tools/discuss.py show "<주제>"                      # 지금까지 오간 것 전부
```

기록: `docs/decide/<날짜>-<주제>.md` — 사장님은 파일의 **마지막 결론**만 보시면 된다.

**한계(정직하게)**: 코덱스는 클로드가 부를 때만 답한다. 먼저 말을 걸거나 사장님과
직접 주고받지는 못한다. 흐름은 사장님 → 클로드 → 코덱스 → 클로드 → 사장님이다.
