## 데이터

### 신설 테이블 2개

```sql
CREATE TABLE IF NOT EXISTS challenge_member (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    customer_id INTEGER NOT NULL UNIQUE,
    cohort TEXT NOT NULL DEFAULT '1기',
    active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS challenge_submission (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    customer_id INTEGER NOT NULL,
    url TEXT NOT NULL,
    platform TEXT NOT NULL,          -- instagram / youtube / tiktok
    shortcode TEXT,                  -- 있으면 dedup_key의 재료
    dedup_key TEXT NOT NULL,         -- 중복 판정 키(저장 시 확정)
    submit_day TEXT NOT NULL,        -- 'YYYY-MM-DD' (KST) ★하루 판정 기준
    submitted_at TEXT NOT NULL,
    title TEXT, thumb TEXT, channel TEXT,
    views INTEGER, likes INTEGER, comments INTEGER,
    fetch_status TEXT NOT NULL DEFAULT 'pending'   -- pending/ok/failed/skipped
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_chal_sub_dedup
    ON challenge_submission(customer_id, dedup_key);
CREATE INDEX IF NOT EXISTS idx_chal_sub_day ON challenge_submission(submit_day);
CREATE INDEX IF NOT EXISTS idx_chal_sub_cust ON challenge_submission(customer_id, submit_day);
```

`submit_day`를 **저장 시점에 KST 문자열로 확정**한다. 조회할 때마다 UTC→KST를
다시 계산하면 계산이 두 군데 적히고 언젠가 어긋난다(0순위-B).

### 기간 설정 (기존 settings 재사용)

`challenge_start` · `challenge_end` · `challenge_daily_goal`(기본 2) 세 키를
`_ADMIN_SETTING_KEYS`에 추가. 2기·3기를 열 때 코드 수정이 필요 없다.

## 화면

### ① 멤버 제출 `/challenge` — 1기 멤버만

- URL 입력칸 + [제출] 버튼
- 상단에 **오늘 N/2** 큼직하게 + 기간 내 누적 달성일수
- 아래 내 제출 목록(날짜별 그룹, 썸네일 카드)
- 참가자가 아니면 "1기 챌린지 참가자만 이용할 수 있어요" 안내

### ② 관리 `/challenge/admin` — 관리자 전용, 탭 2개

**달성현황 탭**: 세로 멤버 / 가로 날짜 그리드.
칸 색 = 0개 빨강 · 1개 노랑 · 2개+ 초록. 우측에 달성률·연속일수.
100명 × 30일이면 가로 스크롤 — 날짜는 sticky 헤더로 고정.

**영상 탭**: `index.html`의 `.cards` 그리드 재사용.
정렬(조회수순·최신순) · 멤버 필터 · 플랫폼 필터.

## 제출 처리 흐름

```
POST /api/challenge/submit  {url}
  ① 참가자인가 확인            → 아니면 403
  ② 기간 안인가 확인            → 아니면 422
  ③ URL 파싱 → platform·shortcode
  ④ 중복 확인(같은 shortcode)   → 이미 있으면 422 "이미 제출한 영상이에요"
  ⑤ challenge_submission INSERT (fetch_status='pending')  ★여기서 제출 확정
  ⑥ 응답 즉시 반환 — 멤버는 기다리지 않는다
  ⑦ 백그라운드: adopt 경로로 수집 → 성공 UPDATE(ok) / 실패 UPDATE(failed)
     틱톡은 수집을 건너뛰고 skipped
```

**저장을 먼저, 수집을 나중에.** 인스타 Playwright 수집은 수십 초가 걸리고
간헐적으로 실패한다. 수집 결과에 카운트를 묶으면 **멤버가 올렸는데 미달성으로
찍히는 사고**가 난다. 카운트의 진실은 `submit_day` 한 곳이고, 수집은 장식이다.

## 실패·경계 처리

| 상황 | 동작 |
|---|---|
| 수집 실패 | `fetch_status='failed'` — 링크·제목만 카드로. **카운트는 인정** |
| 틱톡 | `skipped` — 링크 카드. 카운트 인정 |
| 같은 영상 재제출 | 422, 저장 안 함 |
| shortcode를 못 뽑는 URL | **정규화한 URL 자체**를 중복 키로 쓴다 (아래) |
| 기간 밖 제출 | 422 "챌린지 기간이 아니에요" |
| 참가자 아님 | 403 |
| 지원 안 하는 URL | 422 + 어느 플랫폼을 받는지 안내 |

### 중복 판정 키

`shortcode`는 플랫폼마다 뽑히는 모양이 다르고 틱톡 단축링크(`vt.tiktok.com/...`)는
아예 못 뽑는다. 그래서 중복 키를 **두 단계**로 둔다:

1. `shortcode`가 있으면 그것으로 (같은 영상의 다른 URL 형태도 잡힌다)
2. 없으면 **정규화한 URL**(소문자·쿼리스트링 제거·끝 슬래시 제거)로

`dedup_key` 컬럼 하나에 위 결과를 담아 `UNIQUE(customer_id, dedup_key)`로 건다.
판정을 조회할 때마다 다시 계산하지 않는다 — 저장 시점에 확정한다(0순위-B).

⚠️ 2번 폴백은 완벽하지 않다(같은 영상을 단축링크와 원본링크로 각각 내면 둘 다 통과).
틱톡 단건 수집을 나중에 붙이면 1번으로 수렴한다. 지금은 이 구멍을 알고 간다.

## 테스트

- `submit_day`가 KST 경계에서 옳게 갈리는지 (UTC 15:00 = KST 익일 00:00)
- 수집 실패해도 달성 카운트가 유지되는지 ← **가장 중요**
- 중복 shortcode 거부
- 비참가자 403 / 관리자 아닌 회원의 `/challenge/admin` 403
- 기간 밖 422
- 달성현황 그리드 집계가 제출 데이터와 일치하는지

★ 테스트에 **고정 날짜를 박지 않는다** — 며칠 뒤 반드시 깨진다
(`reference_테스트_시한폭탄_침묵except`). 상대 날짜로 쓴다.

## 안 하는 것 (YAGNI)

- 채널 자동 크롤(멤버가 안 내도 자동 인정) — 100채널 매일 크롤은 비용·차단 리스크
- 순위·포인트·상품 지급 — 지금은 "누가 하고 있나"만 보면 된다
- 알림(미달성자 리마인드) — 운영해보고 필요하면 추가
- 영상 품질 평가 — 챌린지는 꾸준함이 목적
