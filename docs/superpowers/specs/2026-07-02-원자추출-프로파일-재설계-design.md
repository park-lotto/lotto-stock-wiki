# 원자(atom) 추출 프로파일 재설계 — 설계 (2026-07-02)

## 배경

텔레그램/유튜브/증권사리포트/블로그/뉴스 5개 소스에서 Gemini 질문지로 원자(atom)를
추출해 `pipeline/atoms/atoms.db`에 저장하고 `/insights` 대시보드에 보여주는 시스템이
있다. 조사 결과 다음 문제가 확인됐다:

- **유튜브·블로그·뉴스가 완전히 동일한 질문지(`post_questionnaire.py`의 `POST_PROMPT`)를
  쓴다.** 채널 타입 태그 자체가 없어서(`youtube_registry.json`엔 trust/url만), 데이트레이딩형
  채널(진입가·손절가·보유기간·차트패턴)도 일반 insight 칸에 눌려 담긴다.
- **뉴스는 가장 부적합하다.** `[묶음]방산.md`처럼 무관한 헤드라인 여러 개를 한 파일에
  넣어도 `target_kind` 하나로 통째로 뭉개진다.
- **텔레그램은 이미 채널 타입 분기(5종: sector/market/stock_tips/insight/report_relay)가
  있어 상대적으로 잘 설계됐지만, 그럼에도 정보가 샌다.** `leading_sectors`(배열),
  `noise_ratio`(0~1), 대표 `quote` 필드를 Gemini가 채우도록 프롬프트엔 있는데, 원자로
  변환하는 코드가 없어 조용히 버려진다(`telegram_questionnaire.py:217-237`).
- **리포트는 슬롯은 풍부한데(rating/tp_new/tp_prev/thesis/risk 등) DB 컬럼이 없어서**
  `content = " / ".join(parts)`(`questionnaire.py:201-208`) 한 줄 텍스트로 뭉쳐 저장된다.
  "6월에 목표가 올린 리포트만" 같은 구조 질의가 불가능하다.

근본 원인: 질문지가 **소스타입 단위**로만 분기하고 있는데, 실제로는 같은 소스타입
안에서도 **채널/콘텐츠의 성격**에 따라 뽑아야 할 정보와 질문지가 완전히 달라야 한다.

## 목표

1. 새 채널을 추가하거나 기존 채널을 재검토할 때, **Claude가 먼저 샘플 콘텐츠를 직접
   보고 그 채널의 성격을 분석 → 맞는 질문지를 설계 → 검수 → Gemini로 시험 → 재검수**하는
   반복 가능한 온보딩 루프를 만든다. 이 루프를 거치지 않고 채널이 프로덕션에 들어가는
   일이 없게 한다.
2. 질문지 슬롯은 반드시 DB에 저장되거나, 저장하지 않기로 한 이유가 문서화돼야 한다
   (지금처럼 프롬프트엔 있는데 저장 코드가 없어 조용히 사라지는 걸 금지).
3. 구조화된 슬롯(리포트의 rating/tp_new 등)이 텍스트 뭉치로 손실 압축되지 않도록 저장
   구조를 바꾼다.

## 범위

**이번 스펙에서 한다:**
- 채널 온보딩 스킬(신규 슬래시커맨드) 설계·구현
- 프로파일 레지스트리 + `structured_fields` 저장 구조 신설
- 유튜브 마이그레이션 (채널 타입 태그 신설 + 데이트레이딩 프로파일 신설)
- 리포트 마이그레이션 (기존 3분류 로직 유지, structured_fields 저장만 추가)
- 텔레그램 우선순위 2개 채널을 온보딩 스킬로 소급 재검토: **태린이아빠 주식투자**(insight/B),
  **요약하는 고잉**(insight/C)

**이번 스펙에서 안 한다 (다음 스펙):**
- 텔레그램 나머지 10개+ 채널 재검토
- 블로그·뉴스 마이그레이션 (POST_PROMPT 계속 사용, 이번엔 안 건드림)
- `youtube_ingest.py` 삭제(죽은 코드로 확인됨, 별도 정리 작업으로 미룸)

## 아키텍처

### 1. 채널 온보딩 스킬 — `/channel-onboard <소스타입> <채널명>`

새 커스텀 스킬(`.agents/skills/channel-onboard/`)로 만든다. Claude가 대화 세션 안에서
직접 실행하는 반자동 프로세스이며, 배치 스크립트가 아니다(판단이 들어가는 단계가
많아서 사람 개입 없는 완전 자동화는 이번 스펙 범위 밖).

```
STEP 1 — 샘플 수집
  유튜브: /watch 스킬로 그 채널의 최근 영상 3~5개 확인(프레임+자막)
  텔레그램: raw/telegram/{채널}/ 최근 메시지 N개(예: 20개) 직접 Read

STEP 2 — 채널 성격 분석 (Claude)
  전형적으로 어떤 정보가 매번 나오는지, 어떤 형식인지(시황요약형/종목추천형/
  데이트레이딩형/리서치형 등) 파악. 기존 프로파일 레지스트리에 맞는 게 있는지 판단.

STEP 3 — 질문지 설계 (Claude)
  기존 프로파일 재사용 또는 신규 프로파일 작성. 신규 프로파일은:
    - Gemini 프롬프트(질문 슬롯 목록)
    - 슬롯 → 저장 위치 매핑표(atoms 컬럼 or structured_fields 키)
  두 가지를 산출물로 만든다.

STEP 4 — 1차 검수
  설계한 질문지(슬롯 목록 + 저장 매핑표)를 사용자에게 보여주고 확인받는다.

STEP 5 — Gemini 시험 실행
  STEP1 샘플 중 3~5개에 대해 실제로 그 질문지로 Gemini를 돌려본다.

STEP 6 — 2차 검수
  Gemini 결과를 원문과 대조 — 슬롯이 실제로 채워지는지, 근거 없이 지어내지
  않는지(기존 verify_questionnaire.py의 인용대조 패턴 재사용). 사용자에게 결과를
  보여주고 확인받는다. 실패하면 STEP3로 돌아가 질문지 수정.

STEP 7 — 등록
  통과하면 registry.json(텔레: telegram_channels.json / 유튭: youtube_registry.json)에
  `profile: "<프로파일명>"` 태그를 달아 프로덕션 가동.
```

### 2. 프로파일 레지스트리

소스타입별로 여러 "프로파일"을 정의한다. 프로파일 = {프롬프트, 저장 매핑표, 검증룰}.

- 텔레그램: 기존 5종(sector/market/stock_tips/insight/report_relay) 유지, 온보딩 스킬로
  검토한 채널은 이 중 하나를 쓰거나 신규 프로파일을 만들 수 있음
- 유튜브: 신규 정의 — 시황브리핑/종목추천/데이트레이딩(신규)/리서치요약
- 채널 판정은 **하이브리드**: registry.json에 기본 프로파일 태그를 달아두되, 콘텐츠가
  그 태그와 다르면(예: 시황브리핑 채널인데 이번 영상만 종목추천) Gemini가 콘텐츠 단위로
  재판단해서 오버라이드할 수 있다 — 지금 리포트가 이미 하는 자체판단 방식과 동일한
  메커니즘을 유튜브에도 적용.

### 3. 저장 구조 — `structured_fields` 신설

`atoms` 테이블은 지금처럼 대시보드용 공통 요약(asset/sector/date/signal/strength_score/
content)만 담당한다. 프로파일별 구조화 슬롯(리포트의 rating/tp_new/tp_prev/
earnings_outlook/thesis/risk/valuation_basis/supply_comment, 유튜브 데이트레이딩의
entry_price/stop_loss/hold_period/chart_pattern 등)은 신규 `structured_fields` 컬럼
(TEXT, JSON 직렬화)에 원본 그대로 보존한다. `content`는 지금처럼 사람이 읽는 요약
텍스트로 계속 만들되, structured_fields가 진짜 원본이 되고 content는 그로부터 파생된
표시용 텍스트로 위치가 바뀐다.

**슬롯 유실 방지 원칙**: 프로파일의 질문지에 있는 슬롯은 반드시 `structured_fields`
키 하나에 매핑되거나, 저장 매핑표에 "버림: <이유>"로 명시돼야 한다. 온보딩 스킬
STEP3의 산출물(저장 매핑표)이 이 원칙을 강제하는 체크리스트 역할을 한다.

### 4. 유튜브 마이그레이션

- `youtube_registry.json`에 채널마다 `profile` 필드 추가(텔레그램 registry의 `type`
  필드와 동일한 역할)
- 데이트레이딩 프로파일 신설: entry_price(진입가), stop_loss(손절가), hold_period(보유
  기간), chart_pattern(차트패턴 근거), target_price(목표가) 슬롯
- `post_ingest.py --source youtube`가 채널 프로파일을 조회해 해당 프롬프트를 쓰도록
  분기 추가(지금은 모든 소스가 `POST_PROMPT` 하나만 씀 — youtube만 분기, blog/news는
  기존 `POST_PROMPT` 그대로 유지)

### 5. 리포트 마이그레이션

기존 `questionnaire.py`의 stock/sector/market 3분류·자체판단 로직(`STEP0`)은 이미
콘텐츠 기반 자체판단이라 온보딩 스킬 대상이 아니다(리포트는 브로커별 "채널"이 아니라
문서 단위로 섞여 있어서 채널 온보딩 개념이 안 맞음 — 그대로 유지). 변경하는 건 저장
방식뿐: `_stock_atom()`/`_base()`가 만드는 구조화 필드(rating/tp_new/tp_prev/
earnings_outlook/thesis/risk 등)를 `content` 텍스트로 뭉치기 전에 `structured_fields`
JSON으로도 별도 저장.

### 6. 텔레그램 소급 재검토 — 태린이아빠 주식투자 / 요약하는 고잉

두 채널 모두 현재 `type: "insight"`로 태깅돼 있다. 온보딩 스킬 STEP1~6을 실제로
두 채널에 대해 실행해서:
- 지금의 `insight` 프로파일이 이 두 채널에 실제로 맞는지, 아니면 신규 프로파일이
  필요한지 판단
- `leading_sectors`/`noise_ratio`/`quote` 필드가 실제로 이 두 채널 메시지에서 자주
  나오는 유의미한 정보인지 확인하고, 유의미하다면 이번에 `structured_fields`로
  저장 경로를 만들어 유실 문제를 실제로 해결(다른 소급 채널로 확장하기 전에 이
  2개로 먼저 검증)

## 에러 처리

- Gemini 시험 실행(STEP5)이 실패하거나 빈 응답이면 → 기존 `_gemini_text()`의 모델
  폴백·키 로테이션 로직을 그대로 재사용(신규 로직 안 만듦)
- structured_fields JSON 직렬화 실패(순환참조 등 비정상 상황) → 해당 원자는
  structured_fields를 NULL로 두고 content만 저장, 원자 생성 자체는 막지 않음(부분
  실패가 전체를 막지 않게)
- 온보딩 스킬 STEP6 검수에서 반복적으로(3회 이상) 실패하면 → 해당 채널은 프로덕션
  등록을 보류하고 사용자에게 보고(무한 재귀 방지)

## 테스트

- `structured_fields` 저장/조회 왕복 테스트(리포트 픽스처 기준, 기존
  `test_questionnaire_to_atoms.py` 확장)
- 유튜브 데이트레이딩 프로파일: 픽스처 영상 자막으로 entry_price/stop_loss 등 슬롯이
  올바르게 채워지는지 단위 테스트
- 슬롯 유실 방지 체크: 프로파일 정의(프롬프트)에 있는 모든 슬롯 키가 저장 매핑표에
  존재하는지 검증하는 정적 체크(신규 프로파일 추가할 때마다 자동 실행)

## 롤아웃

기존 5개 소스의 나머지 채널(텔레 10개+, 블로그, 뉴스)은 이번 스펙에 포함되지 않는다.
태린이아빠/요약하는 고잉 2개 채널로 온보딩 스킬이 실전에서 검증되면, 다음 스펙에서
나머지 채널로 확장한다.
