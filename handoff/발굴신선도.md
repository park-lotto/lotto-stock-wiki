## 2. 결론 — 사장님이 이상하게 느낀 게 맞다

**그 화면은 2026-07-14 10:55 KST에 돌린 발굴 결과가 그대로 복원된 것 = 47시간 전 데이터다.**

`N시간 전`은 **지금 기준이 아니라 그 발굴이 돌던 순간 기준**으로 얼어붙은 값이다.
`#6`의 릴스는 7/14 09:55에 올라온 것이고, 지금은 실제로 **48시간**이 됐다.

## 4. 왜 위험한가

- 47시간 된 데이터를 **"1시간 전 터진 릴스"**로 읽고 채널을 고르게 된다.
- `속도(시간당 댓글)` · `가속` 같은 **이 페이지의 핵심 지표가 전부 그때 기준**이다.
  이 페이지의 목적 자체가 "지금 막 터지는 채널 잡기"인데 판단 근거가 이틀 전 것.

## 5. 권고안

**① 발굴 시각을 화면에 박는다 (프론트만 수정)**
```
저장된 발굴 38곳 · 2026-07-14 10:55 발굴 (47시간 전 데이터) — 🔄 업데이트로 갱신
```
+ 24시간 초과 시 ⚠️ 배지. `updated_at`은 이미 서버가 주므로 `discover.html` 한 곳만 손대면 된다.

**② `age_hours` 자동보정은 비권장** (판단 근거를 남김)
표시값을 `age_hours + (now - updated_at)`로 고치면 시간은 정직해지지만
`speed`(시간당 댓글)·`accel`은 여전히 그때 값이라 **서로 어긋나 더 헷갈린다**.
시각을 밝히고 "다시 발굴하라"고 유도하는 쪽이 맞다.

## 6. 작업 힌트 (삽질 줄이기)

- **DB 파일명은 `shopping_shorts/data/reference.db`** — `app.db` 아니다. (`config.py:23`)
  내가 `app.db`로 조회해서 "feed 없음" 오탐을 한 번 겪었다.
- **서버엔 `sqlite3` CLI가 없다.** `python3 -c "import sqlite3..."`로 조회할 것.
- 서버 조회 예:
  ```
  ssh -i C:\Users\TheRose\crawling_bot_client\LightsailDefaultKey-ap-northeast-2.pem ubuntu@3.39.179.148 \
    "cd /home/ubuntu/lotto-stock-wiki && python3 -c \"import sqlite3,json; c=sqlite3.connect('shopping_shorts/data/reference.db'); r=c.execute('SELECT updated_at FROM discovery_feed WHERE id=1').fetchone(); print(r)\""
  ```
- **로컬 DB엔 feed가 없다** (`reference.db`에 discovery_feed 행 0). 로컬에서 화면 재현하려면
  발굴을 한 번 돌리거나 서버 값을 봐야 한다.
- 같은 렌더 코드가 `index.html:347` · `outreach.html:159` 에도 있다 — **같은 문제가 있는지 확인할 것**
  (거기도 저장된 피드를 복원하는 구조라면 동일 결함).
