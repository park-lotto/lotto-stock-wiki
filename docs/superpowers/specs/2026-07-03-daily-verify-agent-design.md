# 일일 검증 에이전트 (v1) — 설계

## 배경

텔레그램 뉴스릴레이 필터를 만들면서 실채널 데이터로 검증했더니 버그 3개가 나왔다.
사용자는 이런 "만들고 나서야 버그 발견"이 아니라, 매일 자동으로 상태를 점검하고
보고하는 시스템을 원한다 — 이 프로젝트뿐 아니라 크롤링 등 다른 작업에도 적용
가능한 형태로.

같은 날 실제로 원격서버(stockbrain1.duckdns.org)가 두 번 네트워크 장애로
다운됐다 — 이게 설계의 핵심 제약을 결정했다: **서버 안에서 도는 체커는 서버
자체가 죽으면 아무것도 못 한다(보고조차 못 보냄).**

## 기존 자산

`pipeline/atoms/daily_health.py` — 원자카운트 급감(-50%) 감지 + pytest 실행 +
텔레그램 카드 보고(정상=1줄/이상=상세) + 14일 히스토리. 이미 잘 동작하는
패턴이라 새로 안 만들고 확장한다.

크론(원격서버): `remote_daily_ingest.py`가 하루 5번(8/12/15/18/21시) 돌고 있음.

## 범위 (v1)

**포함:**
1. 크롤링 신선도 — raw/telegram, raw/news, raw/report 오늘자 파일수를
   **같은 요일 최근 4주 평균**과 비교(단순 어제 대비 아님 — 주말/공휴일은
   원래 적으므로 요일별 기준 필요, 오늘 설계리뷰에서 발견).
2. 코드 회귀 — pytest 전체 스위트, 실패 항목만 보고(AI가 자동 수정 안 함).
3. 로컬 서비스 상태 — `systemctl is-active stockbrain`. inactive면 재시작
   1회 자동 시도 후 재확인, 그래도 실패면 "수동확인 필요"로 보고.
4. 통합 텔레그램 보고 — 기존 `send_telegram` 패턴(BOT_TOKEN/CHAT_ID) 재사용,
   1일 1회(크론, 21시 인제스트 직후).

**제외(v1 범위 밖, 명시적으로):**
- 서버 외부 도달성 체크(오늘 겪은 네트워크 장애 감지) — 서버 안에서 도는
  체커로는 원리적으로 불가능함이 오늘 두 번 실증됨. 대신 사용자에게
  UptimeRobot 같은 무료 외부 서비스 가입을 안내(가입은 계정 필요, AI가
  대신 못 함).
- AI가 발견한 코드버그를 자동으로 고치는 것 — 검증 없이 위험. 발견→보고까지만.

## 아키텍처

```
scripts/daily_verify.py (신규, daily_health.py 패턴 확장)
  ├─ check_crawl_freshness() — raw/{telegram,news,report} 요일별 평균대비
  ├─ check_test_regression() — pytest 전체, 실패목록
  ├─ check_service_health()  — systemctl is-active, 죽었으면 재시작 1회
  └─ build_report() + send_telegram() — 통합 카드 발송
```

순수함수(수집)와 부수효과(재시작 시도, 텔레그램 발송)를 분리 — 순수함수는
유닛테스트, 부수효과는 수동/통합 검증.

## 저장/이력

`pipeline/atoms/daily_health.py`의 `health_history.json`과 별도로
`pipeline/atoms/daily_verify_history.json`(14일 보관, 같은 패턴) — 크롤링
신선도의 "요일별 4주 평균" 계산에 이 히스토리를 쓴다.

## 에러 처리

- 개별 체크 함수 실패(예외) → 그 체크는 "측정불가"로 표시, 전체 실행은
  안 죽음(기존 `daily_health.py`의 pytest 타임아웃 처리와 동일 원칙).
- 서비스 재시작 시도 자체가 실패해도(예: sudo 권한 문제) 예외 없이 상태만
  기록.

## 테스트

- 요일별 평균 계산 함수: 고정 fixture 히스토리로 결과값 검증.
- 신선도 판정(부족/정상) 임계치 로직: 경계값 포함 유닛테스트.
- pytest 결과 파싱: 성공/실패 케이스 각각.
- 텔레그램 리포트 조립: 정상 케이스(1줄) / 이상 케이스(상세) 포맷 확인.
- 서비스 재시작 로직은 subprocess mock으로 — 실제 systemctl 호출은 원격
  배포 후 수동 1회 확인.
