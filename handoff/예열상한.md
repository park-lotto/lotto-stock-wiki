# 예열상한 — 핸드오프

**소유 트랙**: 예열상한 — 이 파일은 이 트랙 세션만 수정한다. 다른 트랙은 읽기만.

## 2026-08-27 — 즐겨찾기 미리분석이 안 되던 것 (완료·라이브)

사장님: "담아둔것도 분석이 안되고 그런건 모지"

### 원인 (서버 워커 로그 실측)
`journalctl -u 'shopping-shorts-worker@*' | grep 'task=prewarm'` — **워커 로그**다(웹 아님).

결과 분포가 시각으로 정확히 갈렸다:
```
KST 00시 16 / 01시 7 / 02시 3 / 07시 5 / 08시 13  → 전부 skipped_cap
KST 09시 3 / 10시 4                                → 전부 done
```
경계가 KST 09:00 = **UTC 00:00**. 일일 상한(`_PREWARM_DAILY_CAP`)이 세는 '하루'가
UTC라 리셋이 한국 오전 9시였다. 낮에 40건을 쓰면 그날 저녁~다음날 아침 9시에 담는 건
통째로 스킵. 당시 카운터는 `2026-08-27|8`인데 44건이 스킵돼 있어 처음엔 버그로 보였다
— UTC 08-26 몫이 이미 찼던 것이지 버그가 아니었다.

★기능이 죽는 건 아니다 — 스킵돼도 제작소에서 쓸 때 그때 추출한다. **조용해서** 몰랐다.

### 고친 것 (prewarm.py / app.py / static/index.html)
- `_today_kst()` — 상한의 '하루'를 한국 날짜로. 자정 리셋.
- `_PREWARM_DAILY_CAP` 40 → **100** (사장님 "100건으로 올려봐 상황보게").
- `daily_remaining()` — 남은 몫을 **세기만** 한다(조회가 몫을 까먹으면 안 된다).
- `basket/toggle` 응답에 `prewarm_left`·`prewarm_note`, 프론트 `notePrewarm()`이 토스트.
  하루 한 번만 띄운다.

### 알아둘 것
- **예열 1건 = Gemini 호출 최대 2회** (extract_auto + _fill_structure 구조분석).
  100건이면 하루 최대 200회. 크레딧은 1건으로 세지만 실제 호출은 2번이다.
- 예열은 **`access_level(cid) == "full"`일 때만** 돈다(app.py, 2026-08-20 체험판 개방).
  무료 등급은 안 돈다 — 인스타 429로 본 수집이 죽던 07-30 사고 때문.
- 상한은 **전 고객 합산**이다(settings `prewarm_daily`).
- `archive.html`은 showToast가 없어 안내가 안 뜬다(담기·예열 자체는 정상).

### ⏭ 다음
- 며칠 관찰 → 100이 적정한지. 확인: settings `prewarm_daily` 값, 로그의 skipped_cap 건수.
- 부족하면 상한을 더 올리거나, Gemini 비용이 부담이면 낮춘다.
- archive.html 안내 필요하면 showToast 이식.

## 2026-08-28 — 상한 100도 하루에 찼다 + 조용한 스킵 (완료·병합)

조율가(cid 207) 제보: "즐겨찾기 영상들 분석중 몇초 하다가 다시 분석전으로 돌아갑니다"
(/collection 오류신고)

### 원인 (서버 실측)
- settings `prewarm_daily` = `2026-08-28|100` → **오늘 몫 소진**
- 오늘 워커 로그 `skipped_cap` **180건**. cid 207이 누른 qid 3801~3806은 전부
  `작업 시작 → skipped_cap → 작업 완료`가 0.04초. 즉 큐에 아무것도 안 남는다.
- 그러면 `_analysis_state`가 `idle`을 돌려주고(app.py:11430), collection.html이
  누른 직후 칠한 pending을 `loadAnalysis()`로 덮어써 **'분석 전'으로 되돌아간다.**
- ★기능 고장이 아니라 **상한 소진을 화면이 '안 눌린 것'처럼 보여준 것**이 결함이다.
  담기 경로(`/api/mix/basket/toggle`)엔 이미 안내가 있었는데(app.py:1384)
  즐겨찾기 분석 버튼 경로(`/api/basket/analyze`)에만 빠져 있었다.

### 고친 것
- `_PREWARM_DAILY_CAP` 100 → **300** (사장님 확정. 오늘 실수요 280건대)
- `run_prewarm(manual=True)` — **사람이 직접 '분석'을 누른 건은 상한을 건너뛴다**
  (사장님 확정). 자동 몫을 까먹지 않게 `prewarm_daily_manual` **별도 카운터**에 센다
  — 같은 카운터에 더하면 담기예열이 굶는다.
- `/api/basket/analyze` → `manual=True` 전달. 주소 없는 항목은 `no_url`로 갈라
  `note`로 이유를 돌려준다(종전엔 "걸었다"고 답하고 큐엔 아무것도 없었다).
- `collection.html` — 되돌아간 항목이 있으면 말한다(종전엔 침묵).

### ⏭ 다음
- **관측**: `settings.prewarm_daily` / `prewarm_daily_manual` 두 값과 워커 로그
  `skipped_cap` 건수. 300도 차면 또 올릴지 판단(1건 = Gemini 최대 2회).
- 수동 예외를 열었으니 **수동분 폭주** 여부를 `prewarm_daily_manual`로 지켜본다.
