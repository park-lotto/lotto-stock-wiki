# 슬롯 기반 화면 조합 — 화면-대사 짝을 파이프라인 전체에서 불변으로

## 배경 — 왜 다시 설계하나

`대본퀄v3` 트랙(2026-07-31)에서 화면-대사 어긋남 버그를 하루 종일 고쳤다(핑퐁이 순서 섞음 →
차단, 백본 ON에서 리라이트 안 탐 → 강제, 화면 재배정 멱등성 확보 등). 그런데도 새 버그(세트
< 비트일 때 화면 중복, job `8226822c5b09` 실측)가 또 나왔다 — 3번 이상 다른 자리에서 같은
계열 문제가 반복되면 증상 수정이 아니라 아키텍처를 의심하라는 신호(systematic-debugging
Phase 4.5).

### 근본 원인 (실측 확정)

`_assign_timeline`(edit_plan.py:410)이 화면 세트(`groups`)를 비트 수(`n`)로 정수 나눗셈
비례 배분한다. 이 함수가 파이프라인에서 **두 번** 불리는데(grounding 직후 1회, 여러 후처리
뒤 1회), 그 사이 `_fix_beat_structure → _split_long_beats`가 긴 비트를 문장 단위로 쪼개
**비트 수를 늘린다.** 두 번째 호출 시점엔 `n(비트) > len(groups)(세트, 불변)`가 되어 서로
다른 비트가 같은 세트를 가리키는 중복이 생긴다. 최소 재현 스크립트로 실측 패턴(비트[0,1]이
`s0-1` 공유, 비트[3,4]가 `s0-15` 공유)과 정확히 일치함을 확인함.

**더 근본적으로**: `_assign_timeline`은 비트의 실제 나레이션 내용을 전혀 안 보고 순번(인덱스)
비례로만 화면을 배정한다. "화면 리스트"와 "대사 리스트"가 처음부터 별개로 만들어지고, 파이프
라인 중 여러 지점(grounding 직후, split 후, 핑퐁 후처리 후)에서 인덱스 산술로 반복 재짝짓기
된다 — 짝짓기가 여러 번 일어나는 구조라 그때마다 깨질 위험이 있다. 이게 화면 중복뿐 아니라
"맥락 없는 장면이 붙는다"는 사장님 지적의 근본 원인이기도 하다.

## 원칙 (오늘 논의로 확정)

1. **화면(세트)과 대사(비트)는 처음부터 하나의 리스트, 하나의 원소(슬롯)로 취급한다.**
   슬롯 개수 = 비트 개수, 항상 1:1, 파이프라인 전체에서 절대 안 바뀐다. 화면 리스트와 대사
   리스트를 따로 두고 나중에 인덱스로 짝짓는 구조를 제거한다.
2. **완벽한 낱말 단위 매칭을 강제하지 않는다.** 모든 비트가 그 순간 화면과 100% 맞을 필요
   없음 — 2~3개 정도만 확실히 맞아도 되고, 제일 중요한 건 **큰 흐름**(전체 스토리 단계
   순서)이 화면 순서와 같은 방향으로 가는 것. `_flag_offtopic` 같은 낱말 겹침 검사는 참고
   지표로만 남기고, 하류가 그걸 근거로 화면을 강제로 바꾸게 하지 않는다.
3. **길이 어긋남은 재생성으로만 흡수한다.** 화면(슬롯)은 절대 불변, 대사만 다시 쓰게 한다.
   `_split_long_beats`처럼 비트를 쪼개 화면까지 새로 나누는 로직은 제거한다.
4. **실사 렌더까지는 안 간다.** "영상을 실제로 만들고 그걸 보고 대본 쓰기"(레퍼런스 프로그램
   방식)와 방향은 같지만, 지금 문제(중복·맥락없음)는 전부 "개수/순서" 문제였지 "태깅 텍스트가
   부실해서 톤이 안 맞았다"는 사례는 없었다. 저비용(텍스트 태깅 유지)으로 먼저 검증하고,
   부족하면 그때 실사 렌더 단계를 검토한다.
5. **UI·파이프라인 단계 구성은 그대로.** 다운로드→분석→매칭→TTS→최종렌더 5단계 유지, TTS·
   자막도 지금처럼 매칭(1단계) 안에서 함께 처리한다(레퍼런스처럼 2단계로 쪼개지 않음).
   `produce.html`이 받는 `d.beats` 응답 스키마(narration+primary+fit 등이 한 객체)는
   이미 슬롯 모양과 같으므로 프론트엔드는 변경 없음.

## 새 아키텍처

```
[1] 영상 2개 태깅 (기존 유지, script_extract.py)
      ↓ seg_map (seg_id, scene_desc, text, shot_role 등)

[2] ★NEW: 슬롯 시퀀스 결정 — Gemini 1회 호출
      입력: 두 영상의 전체 태깅 조각(seg_id, scene_desc, shot_role, text, 길이)
      출력: 스토리 순서로 정렬된 seg_id 리스트
      역할 태깅은 고정 어휘집 없이 Gemini가 영상마다 자유 명명(예: "조리1_계란풀기",
      "완성비주얼") — 프롬프트로 "이 조각들을 보고 자연스러운 순서를 짜라"고 유도.
      → 이 순서·개수는 이후 절대 불변 (핵심 불변식)

[3] ★NEW: 슬롯별 길이 예산 계산
      각 seg 실제 길이(초) → 글자수 예산 (기존 _rewrite_block의 budget 계산 재사용)

[4] 대본 생성 (Gemini, 기존 리라이트 프롬프트 방식 유지)
      "화면은 이미 정해졌다" + 슬롯별 예산으로 비트를 씀
      슬롯 개수 == 비트 개수 강제. 안 맞으면 재생성(화면은 절대 안 건드림)

[5] 길이 어긋남 처리 — 우선 최소 구현
      대사가 예산 초과/미달이면 재생성만 반복(화면 불변). 최대 재시도 후에도 안 맞으면
      있는 그대로 진행. (세밀한 보정 규칙은 실측 후 필요하면 추가 — 지금은 과설계 안 함)

[6] TTS/자막 (기존 위치 그대로, 1단계 안에서 — mix_pipeline.py 순서 불변)

[7] 최종 렌더 (기존 유지)
```

## 제거/축소 대상 (기존 코드)

- `_assign_timeline`의 반복 호출(grounding 직후 + 후처리 뒤 재호출) — 슬롯이 처음부터
  고정이므로 한 번으로 끝. 인덱스 비례 배분 로직 자체가 불필요해짐.
- `_split_long_beats`의 "비트를 쪼개 화면도 나누기" 동작 — 화면 불변 원칙과 충돌하므로
  제거하거나, 문장만 쪼개고 화면(같은 슬롯)은 공유하게 완화.
- `_flag_offtopic`의 하류 강제력 — 검사는 남기되(참고 지표), fit 점수를 깎아 하류가 화면을
  강제로 바꾸게 하는 연쇄는 끊는다.

## 검증 계획

새 구조로 실제 job 1~2개(레시피류, 이전 실측에 쓴 것과 유사한 소재)를 생성해 리뷰:
1. 화면 중복이 사라졌는가
2. 스토리 흐름(문제→조리→완성 등 큰 단계)이 화면 순서와 같은 방향인가
3. 길이 재생성이 과도하게 반복되지 않는가(예: N회 넘게 실패하는 비율)

세 가지 중 하나라도 기대에 못 미치면 [2]를 "역할 라벨링(1차 호출) → 순서 조립(2차 호출,
또는 규칙 기반)"으로 분리하는 2단계 방식으로 전환한다 — 지금은 과설계를 피하기 위해 1회
호출로 시작하고, 실측 후 필요하면 나눈다.

## 스코프 밖 (이번 설계에서 안 다룸)

- 실사 렌더 후 Gemini가 보고 쓰는 방식(레퍼런스 프로그램 완전 재현) — 원칙 4번 참조, 필요
  시 별도 설계.
- UI 단계를 레퍼런스처럼 2단계로 줄이는 재설계 — 원칙 5번 참조, 이번엔 안 건드림.
- `_pick_timeline`의 소스 전환 규칙(완성 컷 끝에만, 문제 컷 앞에만 등) — 슬롯 결정을
  Gemini 판단으로 옮기되, 이런 상식적 순서 규칙은 사후 검증 필터로 유지할 여지가 있음
  (구현 단계에서 필요 시 추가).
