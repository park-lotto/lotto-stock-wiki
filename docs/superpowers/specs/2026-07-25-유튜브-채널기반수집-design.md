# 설계 — 레퍼런스 랭킹 유튜브 채널기반 수집 (틱톡 계정시드 미러)

**날짜**: 2026-07-25
**대상**: `shopping_shorts/`
**상태**: 설계 승인됨(구두) → 스펙 검토 대기
**트랙**: 유튜브채널수집

## 1. 목적 / 배경

레퍼런스 랭킹의 **유튜브**는 현재 **키워드(언어코드) 시드 검색**만 수집한다(`_collect_youtube`).
`/refs` 관리페이지가 유튜브 채널을 `kind=account` 시드로 등록하지만 `_collect_youtube`가
account 시드를 **읽지 않아 저장만 되고 수집되지 않는다** — 죽은 등록.

틱톡은 Phase 1(2026-07-24)에서 **무료 계정시드(@handle, yt-dlp)** 를 자동 수집의 기본으로 삼았다.
유튜브도 **같은 채널기반 모델**을 얹어, 인스타 레퍼런스와 동일한 경험을 완성한다:

> 인스타: 엑셀 채널목록 → 각 채널 릴스 수집 → 속도/가속/참여율 랭킹 → 카드
> 유튜브: 등록 채널(/refs) → 각 채널 Shorts 수집 → 속도/가속/참여율 랭킹 → **같은 카드**

**핵심 차이(틱톡과 다른 점)**: 유튜브는 키워드검색도 Data API라 **무료**다. 그래서 틱톡처럼
유료경로를 opt-in으로 숨길 필요가 없다 → **채널 + 키워드 두 경로를 자동 수집에서 함께** 돌린다.

## 2. 비용 — 0원 (Data API 쿼터만)

유튜브 Data API v3는 **건당 과금 없음**. 하루 무료 쿼터 10,000 units만 있다(키당). 채널기반은:

| 호출 | units |
|---|---|
| channelId 해석 (`channels.list`, 캐싱 후 재사용 / `/channel/UC..` URL은 0) | 1 |
| 업로드 플레이리스트 최근분 (`playlistItems.list`) | 1 |
| 영상 지표·길이 (`videos.list`) | 1 |
| **채널 1개당** | **~2–3** |

채널 100개 = 하루 ~300 units = 무료한도의 3%. 사실상 공짜. 키 여러 개면(`YOUTUBE_API_KEYS`)
각 10,000씩이라 로테이션으로 더 늘어난다. 인스타(Apify 💵)·틱톡 키워드(Apify 💵)와 달리 **0원**.

## 3. 아키텍처 — 기존 파이프라인 재사용, fetcher만 추가

```
_collect_youtube()
 ├─ 키워드 시드(언어코드)   → youtube_client.search_shorts()      [기존, 무변경]
 ├─ 계정 시드(kind=account) → youtube_client.fetch_channel_shorts() [★신규]
 ├─ raw 병합 + video_id 중복제거 (같은 영상이 양쪽서 나오면 1개)
 └─ build_youtube_items → apply_grades → save_run/last_run_platform  [기존, 무변경]
```

채널 fetcher가 키워드 경로와 **동일한 raw dict**를 반환하므로 `build_youtube_items` 이하가
그대로 흘러간다. 랭킹 카드·3열 지표(속도/가속/참여율)·등급 로직 전부 인스타와 공용.

### raw dict 계약 (build_youtube_items 입력, ranking.py 기준)
`fetch_channel_shorts`는 아래 키를 채운다(키워드 경로 `search_shorts`와 동일):
```
video_id, channel_id, channel_title, title, description,
thumbnail, published_at, views, likes, comments
```

## 4. 신규 컴포넌트 `youtube_client.fetch_channel_shorts(seed, published_after_iso, max_videos=50)`

플랫폼별 fetcher는 서로 **은닉**된다 — 입력은 시드 문자열, 출력은 공통 raw dict.

1. **seed → channelId + 업로드플레이리스트 해석** (캐싱):
   - `/channel/UC...` URL → 정규식 직접 파싱 (**0 units**), uploads는 `UC`→`UU` 규칙으로 즉시 도출
   - `@handle` / `youtube.com/@handle` → `channels.list?forHandle=@handle` (1 unit)
   - `/user/name` (레거시) → `channels.list?forUsername=name`
   - `/c/name` 커스텀 → 위 실패 시 `search.list?q=name&type=channel` (100 units, 최후수단)
   - 성공 시 `channels.list(part=contentDetails)`의 `relatedPlaylists.uploads`로 업로드플레이리스트 확보
   - 결과(channel_id, uploads_playlist)를 **캐시 테이블**에 저장 → 다음 수집부터 재해석 없음
2. `playlistItems.list(playlistId=uploads, part=contentDetails, maxResults=min(max_videos,50))`
   → 최근 videoId + publishedAt (1 unit)
3. `videos.list(part=snippet,contentDetails,statistics, id=videoIds청크50)` (1 unit)
   → duration·조회수·좋아요·댓글·제목·썸네일·channelTitle
4. **필터**: `contentDetails.duration ≤ 60초`(숏폼만) **AND** `published_after_iso` 이후(14일 창)
5. raw dict 리스트 반환

**키 로테이션**: 기존 `_first_ok(url, params)` 패턴 재사용(403이면 다음 키, 전부 소진 시 빈 처리).

### duration 파서 (ISO8601 → 초)
`PT#H#M#S` 파싱. 판정: `PT59S`✅ / `PT1M`(=60)✅ / `PT1M1S`❌ / `PT2M`❌ / `PT1H..`❌.
(≤60초 포함. 라이브·롱폼은 자연 배제)

## 5. 저장 / 설정

- **신규 소형 테이블** `youtube_channel_cache(seed_value TEXT PRIMARY KEY, channel_id TEXT,
  uploads_playlist TEXT, resolved_at TEXT)` — 해석 1회 후 재사용. store에 get/put 2함수.
- 수집창 = 기존 `YOUTUBE_WINDOW_HOURS`(14일 = 336h, 틱톡·키워드와 동일).
- 채널당 상한 = 최근 50개(playlistItems 한 페이지). **새 설정값 없음**(YAGNI) — 실제 노출은 14일 창이 정함.
- 시드 저장은 기존 `platform_seeds`(kind='account') 그대로. `/refs` 유튜브 탭이 이미 등록 중.

## 6. `service._collect_youtube` 변경

```
seeds = store.list_seeds("youtube")
keyword_seeds = [s for s in seeds if s.kind in {ko,en,ja,zh,ru} or legacy "keyword"]
account_seeds = [s for s in seeds if s.kind == "account"]

raw = []
raw += (기존 언어별 search_shorts 루프)          # 키워드 경로 무변경
for acc in account_seeds:
    raw += youtube_client.fetch_channel_shorts(acc.value, after)   # ★신규
raw = dedupe_by_video_id(raw)                    # ★신규: 양쪽 겹치면 1개
items = build_youtube_items(raw, ...)            # 이하 무변경
```

- 시드가 아예 없으면(키워드·계정 둘 다 0) 기존처럼 `[]` 반환.
- `build_youtube_items`는 현재 video_id 중복제거를 하지 않으므로 **병합 단계에서 dedupe**한다.

## 7. 에러 처리 (틱톡 계정 스킵 미러)

- **비공개·삭제·업로드없음·해석실패** → 그 채널만 스킵(빈 리스트), 전체 수집 계속.
- **403(쿼터 소진)** → `_first_ok`가 다음 키로 로테이션. 전 키 소진 시 그 채널 스킵.
- 채널 하나의 실패가 다른 채널·키워드 경로를 막지 않는다(best-effort).

## 8. UI — 신규 없음

- `/refs` 유튜브 탭이 이미 `kind=account` 시드를 등록/삭제한다(핸들·URL). 변경 불필요.
- 랭킹 화면 `▶️유튜브` 탭도 이미 존재하고 카드 렌더는 플랫폼 공용(`STATE.items`).
- **지금까지 등록만 되고 안 뜨던 유튜브 채널이 실제로 수집되어 랭킹에 뜬다** — 이게 산출물.

## 9. 테스트 (TDD, 먼저 작성)

- **duration 파서**: `PT59S`/`PT1M`/`PT1M1S`/`PT2M`/`PT1H2M` 경계.
- **`fetch_channel_shorts`** (requests mock 3-API):
  - raw 스키마 키 완비 + build_youtube_items 통과
  - ≤60초 필터(61초 영상 배제)
  - 14일 창 필터(오래된 영상 배제)
  - `/channel/UC..` URL 직접 파싱(0 units, API 미호출 확인)
  - `@handle` → forHandle 해석
  - 캐시 재사용(2번째 호출 시 channels.list 미호출)
  - 비공개/빈 채널 → 빈 리스트(예외 안 던짐)
- **`_collect_youtube`**: 계정+키워드 raw 병합 후 video_id 중복제거(겹치는 id 1개).
- **store 캐시**: put→get 라운드트립.

## 10. 범위 밖 (YAGNI)

- 구독자수 표시·채널 활동맵(/refs 유튜브) — 인스타에만 있는 것, 후속.
- 채널당 개수 설정값 — 14일 창으로 충분.
- 스케줄 자동수집 — 현행 수동 "지금 수집" 유지.
- 크로스플랫폼 같은 창작자 중복제거 — 후속.
