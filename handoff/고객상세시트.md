# 핸드오프 — 고객 상세 시트 (pro 고객관리)

- 갱신: 2026-08-29
- 트랙: `고객상세시트` / 브랜치 `track/고객상세시트`

## 무엇을·왜

사장님 지시: **"고객관리에서 고객 누르면 상세창으로 이동해서 관리되게. 날짜별로 어떤
작업을 어떻게 했는지 접속부터 디테일한 부분까지. pro 이상 등록된 사람만 고객관리시트가
필요해. 결제 후 평균적으로 얼마나 사용하는지 api는 얼마나 소모하는지."**

확정한 방향(사장님 선택):
1. **API 배선을 먼저 고치고** 화면을 만든다
2. **전원 상세창을 열되, 시트 지표(평균 사용량·원가율)는 pro에게만** 계산
3. **전용 페이지** `/admin/customer/{id}` (모달은 빠른 조작용으로 유지)

## ★가장 중요한 발견 — API 원가의 96%가 주인 미상이었다

착수 전 서버 DB 실측(2026-08-29):

```
gemini_usage 28,314건 중 customer_id가 채워진 것은 1,235건(4%)
미상 27,079건 = 86,580원.  하루 12,000원 중 고객이 식별되는 건 462원뿐.
op도 마찬가지로 27,079건이 NULL이었다.
```

**원인**: `usage_meter.record()`가 `track(customer_id=)` 컨텍스트만 봤는데,
`track()`을 부르는 곳이 `mix_pipeline.run_mix_job` **하나뿐**이었다. 대본·렌즈·태깅·
썸네일 등 나머지 경로는 전부 주인 없이 쌓였다.

**해결**: `keyctx`가 이미 "이 작업이 누구 것인가"를 알고 있다(HTTP는 미들웨어
`_auth_guard`, 워커는 `_owned_job`). `record()`가 그걸 **폴백으로 읽게** 한 줄 이었다.
판정은 여전히 keyctx 한 곳이다(0순위-B) — 여기선 읽기만 한다.

`op`도 같은 문제라, 호출 스택의 **모듈 이름**으로 유도한다(`_OP_BY_MODULE`).
Gemini 호출부가 25개 모듈에 흩어져 있어 거기마다 적으면 반드시 빠뜨린다.
표에 없는 새 모듈은 '(미지정)'이 아니라 **모듈명 그대로** 남는다.

⚠️ **과거 27,079건은 소급 불가**다. 화면이 이 사실을 대놓고 말한다
(`_AI_ATTRIBUTION_SINCE = "2026-08-29"`). 0원을 "안 썼다"로 읽으면 정반대다.

## ★덤으로 잡은 것 — 관리자 목록이 18.2초였다

작업 중 발견. 라이브 실측으로 `/api/admin/customers`가 **18.2초**(290명·229KB).
사장님이 관리 페이지를 열 때마다 18초를 기다리고 계셨다.

DB 쿼리는 전부 0.00초였다. 범인은 **고객마다 반복되는 파이썬 작업**:

| 원인 | 1인당 | 290명 |
|---|---|---|
| `_lens_key_info`가 `Store(DB_PATH)`를 새로 만듦 → `_init_schema` | 18ms | 5초+ |
| `_lens_has_own_key` + `_lens_key_count`가 **각각** 키 복호화 | 2회 | — |
| `access_level`·`_is_admin`·`_code_admin`이 각각 `get_customer` | 3회 | 5.4초 |
| `_effective_limits`가 설정값을 고객마다 다시 읽음 | 6회 | — |

처방(전부 실측 확인):
- `_effective_limits_all(store, customers)` 신설 — 설정은 한 번만, plan은 목록에서
  꺼낸다. **29.2초 → 0.42초**
- `access_level(cid, cust=...)` — 이미 읽은 dict를 넘기면 DB를 안 친다. **5.4초 → 0.00초**
- `_lens_key_info(cid, store, cache)` — `keys_for` 한 번으로 has_own·개수를 **함께** 정한다

### ⚠️⚠️ 여기서 회귀를 냈고 테스트가 잡았다 (반드시 기억할 것)

캐시를 처음엔 **무조건** 켰더니 렌즈 한도 테스트 **10건이 깨졌다**. 같은 cid로 키
개수를 바꿔가며 재는 테스트가 캐시에 걸린 것인데, 이게 라이브로 나갔다면
**키를 등록·삭제한 고객이 20초간 옛 한도로 막히거나 통과**했을 것이다.

→ **캐시는 기본 꺼짐**(`cache=False`)이고 **목록을 그리는 읽기 경로에서만** 켠다.
   막는 쪽(`check_and_count`)은 항상 지금 값을 본다.
   `test_한도게이트는_캐시를_쓰지_않는다`가 이 규칙을 지킨다.

## ★시간 형식이 4가지다 — 반드시 `_kst_day`를 거쳐라

| 형식 | 쓰는 곳 |
|---|---|
| epoch초(UTC) | `customer_activity.at`, `payments.paid_at`, `customers.last_seen/approved_at` |
| ISO8601(`T`+`+00:00`) | `mix_jobs.created_at/updated_at`, `gemini_usage.ts` |
| `datetime('now')` 공백형 | `points_ledger.created_at`, `job_queue.*` |
| `YYYY-MM-DD`(UTC 날짜) | `usage.day`, `customer_access.day`, `gemini_usage.day` |

⚠️ 공백형은 타임존이 없다 — **UTC로 읽어야** 한다. 로컬로 읽으면 9시간 밀린다.
⚠️ `YYYY-MM-DD`는 시각 정보가 없어 KST 보정이 불가능하다. 화면이 "UTC 날짜 기준이라
   오전 9시 이전 건은 전날 칸"이라고 밝힌다.

## 그 밖의 함정 (전부 이번에 실측으로 밟은 것)

| 함정 | 진실 |
|---|---|
| `gemini_usage.customer_id` | **TEXT 컬럼**인데 int가 섞여 저장돼 있다. 조회는 양쪽 다 비교, 저장은 문자열로 통일 |
| 포인트 소수점 | 0.1P씩 float으로 더하면 `-48.20000000000002`가 화면에 뜬다 → **내부 정수로 더하고 마지막에 한 번만** P로 변환 |
| 원가율 `0.0%` | 38.66원/770,000원이 반올림돼 0.0%가 되면 "원가가 안 든다"로 읽힌다 → `_ratio_pct`가 작은 값에 자릿수를 더 준다 |
| `usage.day` | 체험 render는 날짜가 아니라 리터럴 **`"trial"`**(영구 1회 버킷) |
| `usage.customer_id = -1` | **전역 집계 버킷**이다. 개인 시트에 섞이면 안 된다 |
| 결제 금액 | pro 33명 중 **금액이 들어간 건 5명뿐**(각 77만원). 나머지는 승인 시 금액 칸을 비워 0원이다 → 시트가 `amount_missing`으로 밝히고 수익성 칸을 비운다 |
| 소요시간 | `mix_jobs`엔 칸이 없다. **`job_queue.owner`가 cid의 문자열 형태**라 거기서 뽑는다 |
| `script_usage` | customer_id가 **없다**(전역 참신성 회피용). 고객별로 못 쪼갠다 |
| 로컬 DB | `BYOK_MASTER_KEY`가 없어 키 복호화가 **전부 실패**한다(28행 중 0건). 키 관련 판정을 로컬 결과로 믿지 마라 |
| DB 복사 | 라이브 DB를 그냥 `scp`하면 **손상된다**(서비스가 쓰는 중). 서버에서 `sqlite3.backup()`으로 스냅샷을 뜬 뒤 받아라 |
| `bmng` 버튼 | 클래스만 있고 CSS가 없어 회색 기본버튼으로 보이고 있었다 → 색 정의 추가 |
