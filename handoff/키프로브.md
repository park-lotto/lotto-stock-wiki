## 2026-08-27 — Gemini 키 근본 수정 4건 (완료·라이브)

사장님: "왜실패하나 계속" → "근본문제 해결하고"

제작소 1단계가 "Gemini 키 풀이 전부 소진"으로 5/5 실패. **키를 늘려도 그대로**였다.
원인이 넷이었고 전부 별개다.

### ① 소진 잠금이 하루짜리 영구 낙인이었다
한 번 잠긴 키는 **날짜가 바뀔 때만** 풀렸다. 그런데 실측하니 **오전에 429였던 키가
오후엔 전부 200**이었다 — 쿼터는 시간이 지나면 회복되는데 우리 낙인만 하루를 갔다.
아침 크론(태거·백필)이 한 바퀴 돌며 잠그면 낮에 쓸 키가 없다.
→ `_mark_key_exhausted(idx, retry_after)`에 **만료시각**. 상한 6시간·하한 30초.
→ `_live_exhausted()`가 조회 시점에 만료분을 자동 해제.
→ state의 `exhausted`가 list → `{idx: 만료ts}` dict. **옛 list도 읽되 만료를 붙인다**
   (처음엔 inf로 뒀다가 "배포해도 그날은 그대로"인 걸 실측하고 고쳤다).

### ② 서버가 알려주는 재시도 시각을 안 썼다
`key_vault.retry_delay_seconds(e)`("Please retry in 45.5s")가 **함수만 있고 호출부가 없었다.**
→ 잠금 호출부 13곳이 그 값을 넘기게 배선.

### ③ 프로브가 실제 작업을 대표하지 못한다
`_probe_key_alive`는 `maxOutputTokens=1`짜리 "hi"다. Gemini는 **RPD(요청 수)와
TPD(토큰 수)가 따로**라, 텍스트 1토큰은 200인데 영상 업로드는 429다.
→ 죽은 키를 되살려 앞줄에 세우고, 로테이션이 재시도 예산을 다 쓰고 진짜 살아있는
   키에 도달 못 했다(실측: "키 [0~11] 되살림(200 확인)" 직후 12연속 429).
→ `revived_once`: 되살린 키가 오늘 또 소진되면 **다시는 안 되살린다**(경험 학습).
   프로브를 무겁게(영상 업로드) 만드는 건 비용이 더 크다.

### ④ ★회원 키 31개가 통째로 놀고 있었다
`from shopping_shorts.config import SHORTS_GEMINI_KEYS`는 **값 복사**다.
`refresh_member_gemini_keys`가 config 전역을 재할당해도 복사해 간 6개 모듈은 옛 목록을 본다.
모든 모듈이 `comment_gen._current_key_and_idx()`로 키를 받으므로 **로테이션 전체가 옛 목록**.
  실측: 합류 후 config=21인데 comment_gen=19.
  라이브 기동 로그: `[keypool] 제미니 사장님 19 + 회원 31 = 50개` — **31개가 안 쓰이고 있었다.**
→ `config._push_pool_to_importers()`가 6개 모듈에 밀어 넣는다(이미 import된 것만, sys.modules).
→ `_POOL_IMPORTERS` 명단이 썩지 않게 **테스트가 소스를 훑는다** — 새 모듈이 같은 import를
   쓰는데 명단에 없으면 실패.

### 확인된 현재 상태 (라이브)
```
[keypool] 제미니 사장님 19 + 회원 31 = 50개
[keypool] 유튜브 사장님 10 + 회원 23 = 33개
잠긴 키 → 30분 뒤 자동 해제 / live 14개
```
※ 주식(stockbrain) 키 7개를 쇼핑쇼츠에 **복사**해 뒀다(빼지 않음 — 주식 크론이 돈다).
  해시 비교로 겹침 0개 확인. env 백업: `/etc/shopping-shorts.env.bak*`
