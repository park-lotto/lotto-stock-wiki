# 레퍼런스 랭킹 — 팔로워 컷 → 활동성 선별 재설계

**날짜**: 2026-07-22
**트랙**: 레퍼런스활동선별
**상태**: 설계 확정 (사장님 승인 — 배포까지 자율 진행 지시)

---

## 문제

레퍼런스 랭킹은 "지금 실시간 제일 잘 팔리는 걸 짚어준다"는 서비스인데, **채널 선별 기준이 팔로워**다.

- 벤치마킹 엑셀 = 440개 (전부 팔로워 채워짐, 과거 Apify 프로필 조회로 채운 값)
- `load_channels()`가 `cap_channels()`로 **팔로워 내림차순 상위 200개**만 남김 (`MAX_CHANNELS=200`, 비용 상한)
- 200번째 컷 = 팔로워 7,780명. 잘린 240개도 전부 살아있는 채널 — **활동성과 무관하게 순수 팔로워로만 잘림**

결과: 69만 팔로워인데 2주째 안 올리는 채널이 상위에 남고, 5천 팔로워라도 매일 꿀템 올리는 트렌드 채널이 컷당함. **서비스 목적(신선도)과 선별 기준(팔로워)이 어긋난다.**

추가로: 죽은 채널 감지(`/api/prune/scan`)가 "이미 팔로워로 200 자른 뒤"에만 돌아, 나머지 240개는 살았는지 죽었는지 확인조차 안 됨.

## 목표

선별 기준을 **팔로워 → 활동성**으로 교체한다.

1. **생존 게이트**: 최근 `DEAD_AFTER_DAYS`(=2)일 내 업로드 없으면 사망(소프트, 복구·부활 가능)
2. **전수 센서스**: 전 채널(cap 없음)을 긁어 생존/사망 판정 + 전체 랭킹 반환. 죽은 채널 정리는 백그라운드
3. **매일 랭킹**: 살아있는(+측정대기) 채널만 긁음 → 죽은 채널 안 긁으니 비용 낭비 제거
4. 신규/등록 채널은 "측정대기(pending)"로 즉시 수집 대상 편입
5. 팔로워 컷 제거

## 비설계 (YAGNI)

- 자동 크론 센서스 — 일단 수동 버튼. 검증 후 별도 태스크로 크론 승격
- 팔로워 데이터 재수집 — 팔로워를 더는 선별에 안 쓰므로 갱신 불필요 (표시용으로만 유지)
- 하드 삭제 — 하지 않음. 모든 제거는 소프트(복구 가능)

## 데이터 모델

### 새 테이블 `channel_activity` (자동 활동성 레이어)

| 컬럼 | 타입 | 의미 |
|---|---|---|
| `username` | TEXT PK | 정규화 소문자 |
| `last_post_at` | TEXT null | 센서스에서 본 가장 최근 릴스 timestamp(ISO). 0건이면 미갱신 |
| `engagement_density` | REAL | 최근 릴스 댓글/조회 비율 (0~) |
| `activity_score` | REAL | 정렬용 활동점수 (아래 산식) |
| `alive` | INTEGER | 1=생존 0=사망. `checked_at` 시점 판정 캐시 |
| `checked_at` | TEXT | 마지막 센서스 시각 (datetime('now')) |

- **기존 `removed_channels`(수동 제거)는 그대로.** 사장님이 손으로 뺀 채널은 항상 제외. `channel_activity.alive`는 그 위에 얹히는 **자동** 층. 둘은 독립.
- **부활**: 죽었던(`alive=0`) 채널이 센서스에서 다시 릴스 반환 → `alive=1` 갱신. 코드상 특별 처리 불필요 — 그냥 upsert.

### 상태 3분류 (선별 규칙)

정규화 username 기준:
- `alive=1` → **생존** → 포함
- `channel_activity`에 행 없음 → **측정대기(pending)** → 포함 (신규/등록 채널이 여기 = 다음 수집에서 즉시 긁혀 측정)
- `alive=0` → **사망** → 제외
- `removed_channels`에 있음 → **수동 제거** → 항상 제외 (alive 무관)

## 활동점수 산식

`activity_score` = 정규화 안 한 단순 합성 (센서스가 채널당 1~2개 릴스만 보므로 가볍게):

```
engagement_density = comments / max(views, 1)        # 참여밀도
recency_factor     = max(0, 1 - age_hours / (DEAD_AFTER_DAYS*24))   # 최근일수록 1
activity_score     = engagement_density * (1 + recency_factor)
```

- 채널이 여러 릴스 반환 시 릴스별 점수의 **최댓값**을 채널 점수로.
- 속도(delta/accel)는 매일 랭킹에서 반복 스냅샷으로 누적되는 값이라 센서스 단발 점수엔 안 넣음. 매일 랭킹 정렬은 기존 `apply_grades`/`sort_by` 그대로 유지.

## 두 개의 수집 흐름

### ① 센서스 `/api/census` (수동 버튼, index.html)

```
1. 마스터 목록 = load_channels()(엑셀 전체, cap 없음) ∪ discovered − removed_channels
2. fetch_reels(전 채널, only_newer_than=DEAD_AFTER_DAYS일, results_per_channel=CENSUS_RESULTS_PER_CHANNEL=2)
3. build_items + apply_grades → 즉시 전체 랭킹 반환 (화면에 모두 반영)
   └ 릴스 0건 채널 = 사망 후보 → 응답에 "정리 대상" 목록으로 함께 반환
4. background_tasks (응답 후, "정리를 뒤에서"):
   - 릴스 반환 채널: channel_activity upsert (last_post_at·density·score·alive=1, checked_at=now) → 부활 포함
   - 0건 채널: channel_activity upsert (alive=0, checked_at=now)  ← 소프트 사망. 하드삭제 없음
5. 반환: {ok, count, items(전체랭킹), dead(정리대상), alive_n, dead_n, revived_n}
```

- 비용: 매일이 아니라 사장님이 버튼 누를 때만. 전 채널 1회 = 지금 하루 수집(200)의 약 2.4배를 가끔.

### ② 매일 랭킹 `/api/collect` (기존, 선별만 교체)

```
collect(): channels = select_tracked(load_channels(), discovered, removed, dead_set)
  → 생존+측정대기만, 사망·수동제거 제외, cap은 활동/안전상한만 (팔로워 컷 없음)
  이후 fetch_reels·build_items·apply_grades·save_run 전부 기존 그대로
```

## 코드 변경점 (기존 파일, 새 개념 최소)

| 파일 | 변경 |
|---|---|
| `config.py` | `DEAD_AFTER_DAYS=2`, `CENSUS_RESULTS_PER_CHANNEL=2`, `MAX_TRACKED=300`(활동 안전상한). `MAX_CHANNELS`(팔로워 컷)는 선별에서 미사용 처리 |
| `store.py` | `channel_activity` 테이블(CREATE) + `upsert_activity()`·`activity_map()`·`dead_usernames()`·`alive_usernames()` 메서드 |
| `channels.py` | `load_channels()` 팔로워 cap 제거 → 전체 반환. 신규 `select_tracked(excel, discovered, removed, dead_set, max_channels)` = union(discovered 앞)·dedup·removed 제외·**dead 제외(pending·alive 포함)**·MAX_TRACKED 안전상한. `cap_channels`는 유지하되 미사용(기존 테스트 보존) |
| `service.py` | `collect()`이 `select_tracked` 사용. 신규 `census()` = 전 채널 스캔·전체 랭킹 반환·활동성 upsert(부활 포함) |
| `app.py` | `POST /api/census` 엔드포인트(정리는 `background_tasks`). ranking_only(무료) 게이트에서 census는 데이터변경이므로 제외(유료 경로) |
| `static/index.html` | "전수조사(센서스)" 버튼 → `/api/census` 호출 → 기존 랭킹 렌더 재사용, 하단에 "정리 대상" 표시 |

- **`merge_tracked`는 건드리지 않는다** — 기존 테스트 4건 보존. `collect`이 그것 대신 `select_tracked`를 부른다.
- `load_channels()` 무캡 전환의 부수효과: `_known_usernames`(발굴 dedup)가 이제 440 전체를 봐서 **더 정확**해짐(기존엔 200만 봐서 잘린 240과 중복발굴 가능했음 — 개선).

## 엣지 케이스 / 에러 처리

- **2일 게이트가 3~4일 주기 좋은 채널을 죽임**: 알고도 채택(사장님 결정 — "트렌드 채널은 2일이면 충분"). 완화 = ① 소프트(복구·부활) ② `DEAD_AFTER_DAYS` 상수 하나라 나중에 7로 조정 가능
- **센서스 미실행 상태(활동 테이블 비어있음)**: 전 채널 pending → `select_tracked`가 전부 포함 → 첫 수집이 사실상 전수. 이후 센서스가 사망 마킹하며 좁혀짐. **안전한 초기 동작**(아무도 실수로 잘리지 않음)
- **Apify 실패/타임아웃**: 기존 `fetch_reels` 예외 처리 그대로. 센서스 실패 시 활동 테이블 미갱신(이전 상태 유지) — 죽은 것으로 오판 안 함
- **부활**: dead 채널이 다시 올림 → 센서스가 alive=1로 upsert → 다음 select_tracked에 자동 포함
- **신규 등록(`/api/reference/register`)**: discovered에 들어가 pending → 다음 수집/센서스에서 즉시 측정. followers=0 무관(팔로워 컷 없어짐)
