### 고친 것 — 판단을 한 곳으로
`channel_archive.block_heavy_assets(page, env=...)` **공용 함수 신설** → 6곳에서 호출.
아카이브 자신도 이 함수를 쓰게 바꿨다(기존 env명 `ARCHIVE_BLOCK_ASSETS`는 **그대로 존중** —
서버에 이미 설정돼 있으면 이름을 바꾸는 순간 조용히 무력화된다).

**왜 안전한가**: 데이터는 전부 `page.on("response")` graphql/xhr 후킹으로 받는다
(인스타 릴스·해시태그·프로필, 도우인 검색 모두 코드로 확인). 썸네일은 URL 문자열만 저장.
⚠️ **stylesheet는 절대 막지 마라**(2026-08-06 실측: CSS 막으면 무한스크롤이 죽어 372건→12건).

### 실측 검증 (Playwright, 2026-08-17)
```
차단 OFF: 8.72MB / 38응답  (script 6.61 · CSS 0.93 · image 0.50 · font 0.21 · xhr 0.03)
차단 ON : 8.01MB / 34응답  (image·font **사라짐**, xhr·document·CSS 그대로 통과)
DOM     : img의 src속성 1/1 유지 → 썸네일 URL 수집에 영향 없음
```
※이 페이지(로그인 전 랜딩)는 script가 6.6MB라 절감률 8%로 보인다. **릴스 그리드 스크롤은
이미지 비중이 압도적**이라 아카이브 실측(-48%, 채널당 26.4→13.7MB)에 가깝다.
테스트: 신설 9건 + 기존 archive·instagram 계열 = **29 passed**

### ⏭ 다음 (사장님 판단 필요)
1. **결제는 이 수정 배포 후 하루 실측을 보고 결정**하는 게 낫다. 지금 192GB를 사면 대부분 낭비.
   수정 후 293채널 × 13.7MB ≈ **4GB/일**로 추정되나 **아직 실측 아님**(402로 크롤이 멈춰 있어
   측정 불가). 결제 후 첫 수집에서 웹셰어 Stats로 확인할 것.
2. **하루 4GB도 25GB/월엔 안 들어간다**(30일 × 4GB = 120GB). 추가 최적화가 필요하다:
   - 채널 293개를 매일 전수 도는 게 맞나 → 격일·우선순위 분할이면 절반
   - 릴스 수집에 293채널 **전부** 프록시가 필요한가 → 일부만 로테이션
   - `_MAX_SCROLLS`(200)·`_STALL_LIMIT` 조정으로 채널당 스크롤 감축
   → 이건 **수집 전략 변경**이라 데이터 신선도·계정 리스크 트레이드오프. 사장님 결정 필요.
