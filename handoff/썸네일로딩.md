# 유튜브 카드 썸네일 로딩 속도 (2026-08-30)

사장님 제보: **"유튜브를 누르고 카테고리 탭을 들어가면 썸네일 로딩이 엄청 오래걸리는데"**

## 원인 — 카드 크기와 무관하게 **원본 해상도**를 받고 있었다

수집된 유튜브 8,000건이 **전량 `oardefault.jpg`**(1280×720)였다.
카드는 `.card img{width:100%;aspect-ratio:9/16}`(index.html:56)로 그리므로
**원본이 몇 픽셀이든 화면 크기는 같다** — 큰 파일은 그대로 낭비다.

같은 영상(-abOFBl05S4) 규격별 실측:

| 규격 | 크기 | 받는 시간 |
|---|---:|---:|
| **oardefault**(쓰던 것) | 168,835 B | 0.34s |
| sddefault | 52,222 B | 0.17s |
| **hqdefault**(바꾼 것) | 12,643 B | 0.16s |
| mqdefault | 6,517 B | 0.15s |

한 화면 200장(`RENDER_STEP=200`) → **32.2MB**. 브라우저는 호스트당 6개만 병렬로
받으므로 **33겹 대기줄**이 생겨 검은 칸으로 남았다.
카테고리 탭을 누르면 `RENDER_CAP`이 리셋돼(index.html:1911) 200장을 처음부터 다시 받는다
— 사장님이 겪은 지점이 정확히 이것.

## 완료 (커밋 `da82ed348`)

`_yt_thumb_downscale()` 신설(`app.py:6429`) — oardefault·maxresdefault·sddefault → **hqdefault**.

- ★**서버(프록시) 한 곳에서만 정한다**(0순위-B). 프론트 `thumbURL`에서 바꾸면
  도서관·트렌드·히트작 등 호출부(index.html에만 9곳)마다 제각각 남는다.
  프록시에서 바꾸면 **캐시 키도 새 주소로 잡혀 큰 파일을 아예 안 받는다**.
- ★화이트리스트 검사를 **통과한 뒤에** 바꾼다(`app.py:6532`) — 순서가 바뀌면
  SSRF 검사 대상이 원본이 아니게 된다.
- ★영상ID 보존 — 바뀌면 카드↔영상이 어긋난다(`렌즈썸네일_구글짝지음`과 같은 종류).
- 인스타·틱톡·핀터레스트는 손대지 않는다(회귀 0).

**라이브 실측**(서버에서 실제 썸네일 12장 다운로드):
```
oardefault : 2,624 KB / 2.93s
hqdefault  :   196 KB / 1.69s     ← 13.4배 감소
```

**덤 — 검은 카드도 준다.** `_yt_thumb_alternates` 주석의 기존 실측에 따르면
oardefault는 '영상마다 있을 수도 없을 수도 한 변형'이라 **7.5%가 404**였다.
hqdefault는 사실상 항상 있다.

## ★loading="lazy"는 넣지 않았다 — 두 번 실패한 함정

처음엔 lazy도 함께 넣으려 했으나 **코드 주석에 실측이 이미 남아 있었다**:

- `index.html:2015-2020`(2026-08-28, 랭킹 카드) — lazy 로더가 요청을 **아예 안 보낸다**.
  카드 99장 전부 `complete=false`·`naturalWidth=0`, 스크롤해 화면에 18장이 들어와도 0장.
  lazy를 떼니 즉시 떴다. **핀터레스트만이 아니라 유튜브 탭도 200장 전부 0장**이었다.
- `index.html:2193-2195`(2026-08-04, 모달 카드) — 같은 함정.

⚠️ **다시 넣지 마라.** grid + `aspect-ratio` 조합에서 lazy 가시성 판정이 실패한다.
장수를 줄이려면 lazy가 아니라 `RENDER_CAP`(이미 200으로 걸려 있다)을 조절해야 한다.
