# 영상 제작소 — 작업파일(저장·목록·복원) 설계

**날짜**: 2026-07-17 · **트랙**: 대본믹스통합 · **상태**: 사장님 결정 반영, 검토 대기

---

## 1. 문제 — 지금 작업물이 실제로 날아가고 있다

사장님 제보: *"뒤로가기 하니까 작업물이 지워지는데 영상제작소 아래 작업파일을 기억하게 해주고
내일 다시 들어와도 기록남고 그대로 진행할수있게 해줘야한다."*

**원인 확정**(실측): 작업 상태가 **`sessionStorage`에만** 있다 — `produce.html`:
```js
sessionStorage.setItem('produce_work', JSON.stringify({handoff:HANDOFF, script:STATE.script||'', ...}))
```
`sessionStorage`는 **그 탭에서만, 탭이 살아있는 동안만** 유효하다. 사이드바로 다른 페이지에 갔다 오거나
탭을 닫으면 사라진다. **"내일 다시"는 애초에 불가능한 구조다.**

## 2. 재료 실측 — 반쪽만 있다

서버 `mix_jobs`(reference.db) 실측:

| | |
|---|---|
| 총 job | **21건** |
| `given_script`(확정 대본)이 있는 job | **5건**뿐 — 옛 job은 AI가 나레이션을 쓰던 경로라 빔 |
| **매칭 전 작업** | **0건 — 서버에 아예 없다** |

**★핵심**: `mix_jobs`는 `urls_json NOT NULL` · `structure NOT NULL`이라 **매칭을 눌러야 생긴다.**
대본만 확정하고 영상을 담아둔 상태는 서버에 흔적이 없다 — **사장님이 잃어버린 게 바로 그 구간**이다.
→ **`mix_jobs` 목록만 띄우는 건 문제의 반만 푼다.**

## 3. 사장님 결정 (확정)

| 질문 | 결정 |
|---|---|
| 언제부터 서버에 기억하나 | **대본 확정하는 순간 바로** |
| 어느 수준으로 | **사이드바에 작업 목록** (누르면 그 작업으로) |
| 어디까지 복원 | **단계까지 그대로** — 떠난 자리에서 이어감 |

## 4. 설계

### 4.1 그릇 — `produce_works` 신규 테이블

`mix_jobs`를 재활용하지 **않는다**. `urls_json`·`structure`가 `NOT NULL`이라 매칭 전 작업을 못 담고,
억지로 빈 값을 넣으면 "매칭 안 된 job"이라는 유령이 생겨 기존 파이프라인(`run_mix_job`·`pollMix`)이
그걸 실제 job으로 오인한다.

```sql
CREATE TABLE IF NOT EXISTS produce_works (
    work_id      TEXT PRIMARY KEY,
    customer_id  INTEGER NOT NULL DEFAULT 0,   -- 멀티테넌시 관례(2026-07-13)
    title        TEXT,                          -- 목록에 뜨는 이름(대본 앞머리에서 자동)
    state_json   TEXT NOT NULL,                 -- 클라이언트 작업상태 스냅샷(아래 §4.2)
    job_id       TEXT,                          -- 매칭했으면 mix_jobs로 잇는 다리(없으면 NULL)
    step         INTEGER NOT NULL DEFAULT 0,    -- 떠날 때 몇 단계였나
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL
)
```

**`job_id`는 다리일 뿐** — 작업이 job을 갖기 전에도 작업은 존재한다. 이 방향(작업 → job)이라야
"대본만 있는 작업"이 자연스럽다.

### 4.2 `state_json` — 무엇을 담나

지금 `sessionStorage.produce_work`가 담는 것 **그대로** + 단계:
```json
{"handoff": [...], "script": "...", "script_src_idx": 0, "script_from_wiki": "Dayi...", "step": 0}
```
`sessionStorage`의 스키마를 그대로 쓴다 — **새 형식을 발명하지 않는다**. 복원은 기존
`_consumeProduceHandoff`가 이미 하는 일이고, 그 함수가 읽는 모양을 서버에서 가져오기만 하면 된다.

⚠️ **`deco`·`headcopy`·`voice`·`caption_style`은 담지 않는다** — 이미 `mix_jobs`에 있다(job이 주인).
두 곳에 두면 어느 쪽이 진실인지 갈린다.

### 4.3 언제 쓰나 (저장 트리거)

- **대본 확정** → 작업 생성(없으면) + 저장. 이게 사장님이 정한 시작점이다.
  ⚠️ **대본 확정 진입점이 둘이다**(실측): `useDraft(i)`(`produce.html:1104`)와 `pmUseDraft(...)`
  (모달의 "이 대본 확정 →", `:1416`). **하나만 잡으면 다른 쪽이 조용히 샌다.**
  → 둘 다 `saveWork()`를 부르므로 **`saveWork()` 안에 얹으면 두 경로가 자동으로 덮인다**(아래).
  이게 진입점을 일일이 찾아 붙이는 것보다 안전하다 — 이 트랙은 "경로를 하나 놓쳐서" 이미 두 번 데었다
  (`go()`만 보고 `jump()` 놓침 / 재매칭의 '끝'만 봉인하고 '시작' 놓침).
- 그 뒤 **기존 `saveWork()`가 불릴 때마다** 같이 서버에도 쓴다.
  `saveWork()`는 이미 **9곳**에서 불린다(실측) — **새 트리거를 발명하지 말고 그 함수 안에 얹는다.**
  ⚠️ 단 `saveWork()`는 `if(HANDOFF.length)` 같은 조건 뒤에서 불리는 자리도 있다 —
  구현 전 9곳을 전부 보고 "대본 확정 직후에 실제로 불리는가"를 확인할 것(안 불리면 그 자리에 추가).
- **디바운스 필수**: `saveWork()`는 자주 불린다(입력마다). 매번 POST하면 서버를 두들긴다 → 1초 디바운스.
  `sessionStorage` 쓰기는 지금처럼 즉시(빠른 로컬 복원용), 서버는 디바운스.

### 4.4 사이드바

`sidebar.js`의 메뉴 배열에 "영상 제작소" 아래로 **내 작업 목록**을 붙인다(하위 항목).
```
제작
  🎬 영상 제작소
     · 협탁 인테리어…      ← 2시간 전 · 1단계
     · 감자 레시피…         ← 어제 · 3단계
     + 새 작업
```
- 누르면 `/produce?work=<work_id>` → 그 작업으로 복원.
- **현재 열린 작업 표시**(어느 게 지금 건지 보여야 한다).
- 목록은 `updated_at DESC`, **최근 20건**. 그 이상은 안 보여준다(YAGNI — 필요해지면 그때).

### 4.5 복원

`/produce?work=<id>` → `GET /api/produce/works/<id>` → `state_json`을 **기존 복원 경로에 그대로 먹인다**:
```js
// _consumeProduceHandoff의 2순위(이전 작업상태 복원) 자리에 서버 응답을 끼운다
HANDOFF = w.handoff; STATE.script = w.script; ...; cur = w.step; renderSteps(); showPanel();
```
그리고 `job_id`가 있으면 `MIX_JOB = w.job_id`로 이어 붙인다 → 미리보기·편집안이 그대로 붙는다.

⚠️ **`cur`를 복원할 때 게이트를 우회하면 안 된다**(2026-07-17 C-1/C-3의 교훈).
`cur = w.step`은 `jump()`/`go()`를 안 거치므로 게이트를 건너뛴다 —
**복원 직후 `refreshNextBtn()`을 반드시 부르고**, 미리보기 상태(`preview_status`)를 서버에서
다시 읽어 `PREVIEW_STATUS`를 맞춘다. 안 맞추면 "2단계로 복원됐는데 1단계 미리보기를 안 본 상태"가 된다.

### 4.6 라우트

- `POST /api/produce/works` `{work_id?, state, job_id?, step}` → upsert. `work_id` 없으면 새로 만들어 반환.
- `GET /api/produce/works` → 최근 20건 `[{work_id, title, step, job_id, updated_at}]`
- `GET /api/produce/works/{work_id}` → `{state, job_id, step}`
- `POST /api/produce/works/{work_id}/delete` → 지우기(목록이 쌓이면 필요하다)

`title`은 서버가 `state.script` 앞 20자에서 뽑는다 — 클라이언트가 매번 보내면 어긋난다.

## 5. 화면 흐름

```
1) 대본 확정 → (자동) 작업 생성 → 사이드바에 뜸
2) 사이드바 딴 데 갔다 옴 → 목록에서 내 작업 클릭 → 그 단계로 복원
3) 내일 다시 접속 → 목록 그대로 → 클릭 → 이어서
```

## 6. 검증 (구현 계획이 반드시 포함할 것)

이 저장소는 **"통과하는데 결함을 못 잡는 테스트"가 반복**됐다. 태스크마다 뮤테이션을 돌린다.

- **대본 확정이 실제로 작업을 만드나** — 뮤턴트(생성 호출 제거)로 죽는지.
- **★복원이 게이트를 우회하지 않나** — `step=1`로 복원했는데 미리보기를 안 본 상태면
  `다음`이 잠겨 있어야 한다. **이게 C-1/C-3와 같은 종류의 구멍이 될 자리다.**
- **디바운스가 실제로 도나** — `saveWork()`를 10번 부르면 POST가 1번.
- **`mix_jobs` 오염 없음** — 작업 저장이 job 파이프라인을 안 건드리는지.
- **마이그레이션** — 신규 테이블이 기존 DB(job 21행)에서 생기는지.
- **라이브 grounding**: 대본 확정 → 사이드바 이동 → 돌아와 복원 → **화면에서 대본이 살아있나**.
  테스트 통과는 동작의 증거가 아니다(이 저장소에서 여러 번 증명됨).

## 7. 범위 밖

- **`sessionStorage` 제거** — 그대로 둔다. 서버 저장은 **추가 계층**이다(빠른 로컬 복원 + 서버 백업).
  둘을 한 번에 바꾸면 실패 시 되돌릴 자리가 없다.
- **`deco`·`voice`·`headcopy` 이중 저장** — job이 주인. 작업은 안 담는다.
- **작업 공유·협업·버전 이력** — YAGNI.
- **2단계 자막제거 확인**(별건, 사장님이 "작업파일 먼저"로 순서 정함) — 아래 §8.
