# 인스타 수집: 세션 로그인(B안) — 샤오홍슈 패턴 이식

작성일: 2026-07-29 · 트랙: AI픽자동적재

## 배경

[2026-07-28-인스타-playwright-10채널-실측.md](../plans/2026-07-28-인스타-playwright-10채널-실측.md)에서
A안(비로그인+주거용 프록시)이 게이트 불통과로 끝났다. 서버 IP 직결은 4.5초 만에 `/accounts/login/`
로그인벽으로 튕겼고, 기존 Webshare 프록시는 타임아웃. 그 결론이 "B안(부계정 세션 쿠키)으로
넘어간다"였는데, 이후 세션이 샤오홍슈 쪽으로 넘어가면서 착수가 안 됐다.

같은 날(2026-07-29) 샤오홍슈(rednote)에서 정확히 이 문제를 풀었다: 막힌 원인이 IP가 아니라
**로그인 여부**였고, 로그인 세션(storage_state)만 있으면 데이터센터 IP 직결도 그대로 통과했다
(`shopping_shorts/playwright_crawl.py` 참고). 인스타도 4.5초 만에 로그인벽으로 튕긴 것이
같은 성질일 가능성이 높아 이 패턴을 그대로 이식한다.

## 변경

- `config.INSTAGRAM_SESSION_PATH` 신규 — `REDNOTE_SESSION_PATH`와 동일한 역할.
- `instagram_playwright._scrape_one_playwright`: 세션 파일이 있으면 `storage_state`로 로드하고
  프록시보다 우선한다(샤오홍슈에서 "세션만 있으면 프록시 불필요"가 실측됐으므로). 없으면 기존
  경로(프록시/직결)로 폴백 — 롤백 스위치는 그대로 유지.
- `scripts/instagram_setup_session.py` 신규 — 로컬에서 수동 로그인 → `storage_state` 저장.
  세션 파일은 git 비추적(`.gitignore`), 서버로 옮긴 뒤 600권한으로 관리(rednote와 동일).

## 검증 전 알아둘 것 — 인스타≠샤오홍슈일 수 있다

- 인스타는 자동화 탐지가 더 공격적이다(샤오홍슈보다 부계정 정지 위험 큼) — 계정은 여유 있다고
  확인됨(2026-07-29, 사장님). 그래도 재사용 가능한 부계정으로 로그인할 것, 본계정 금지.
- 세션 만료 주기가 샤오홍슈보다 짧을 수 있다 — 실측 전까진 모른다.
- **1채널 스파이크로 먼저 확인**: 세션 로드만으로 `login_wall`이 사라지는지부터 본다. 안 되면
  A안처럼 이 경로도 폐기하고 Apify 유지로 확정한다. 낙관·비관 없이 숫자로 결정(10채널 실측과
  동일 원칙).

## 하지 않는 것

- 컨텍스트 재사용(`INSTAGRAM_PW_CONTEXTS`) 구현 — 세션 경로 성패가 먼저다.
- 서버 자동 재로그인 — 세션 만료 시 `instagram_setup_session.py` 재실행은 여전히 사람이 한다
  (샤오홍슈도 동일 운영 방식).

## 실측 결과 (2026-07-29, 당일 진행) — 예상과 다르게 흘러갔다

**"인스타≠샤오홍슈일 수 있다"가 실제로 맞았다 — 단 다른 이유로.** 처음 가설(자동화
탐지가 더 세다)은 맞았지만, 문제 지점이 예상과 달랐다.

1. **`scripts/instagram_setup_session.py`(Playwright로 직접 로그인) — 폐기.**
   사람이 직접 타이핑해도 로그인 **제출 시점**에 `/auth_platform/recaptcha/`로 튕겼다.
   `playwright-stealth` 적용, `--disable-blink-features=AutomationControlled` 추가까지
   해봤지만 계속 막혔다 — 타이핑 패턴이 아니라 **CDP(크롬 원격제어)로 브라우저가 조종되고
   있다는 사실 자체**를 Meta가 감지하는 것으로 보인다. 더 들어가려면 사람 행동을 정교하게
   흉내내는 기법이 필요한데, Meta 사기탐지 시스템과의 지속적 추격전이 되고 계정정지 위험도
   커져 여기서 멈췄다.
2. **완전히 다른 접근으로 전환 — 성공.** `scripts/instagram_cookies_from_browser.py` 신규:
   Playwright를 아예 안 쓰고, 평소 쓰는 진짜 브라우저(Firefox)에 정상 로그인한 뒤
   `browser_cookie3`로 그 브라우저의 로컬 쿠키 저장소를 직접 읽어 `storage_state`로 변환.
   로그인 자체에 자동화 흔적이 전혀 없어 캡차를 만날 일이 없다.
   - Chrome/Edge는 최신 "앱 바운드 암호화"(정보탈취 악성코드 방지용) 때문에 관리자 권한으로도
     안 됨(`Unable to get key for cookie decryption`) — 더 파고들면 실제 악성코드가 쓰는
     우회기법 영역이라 안 갔다. **Firefox는 이 제약이 없어 그대로 성공.**
   - 실측 함정: Firefox `cookies.sqlite`의 `expiry` 컬럼이 초가 아니라 **밀리초** 단위였다
     (Playwright의 `kMaxCookieExpiresDateInSeconds` 초과로 즉시 에러) — 변환 시 초과분은
     ÷1000 보정.
3. **세션 로그인 자체는 검증됨.** 이 세션으로 실제 헤드리스 수집을 재현하니 `login_wall` 없이
   인박스·파트너십 메시지함처럼 로그인 전용 데이터가 응답에 섞여 옴 — 로그인 상태 확인.
4. **별개 문제 발견·해결 — 인스타 웹의 API 자체가 GraphQL로 통합됨.** 이 코드가 작성된
   2026-07-28 이후 인스타가 REST(`/api/v1/clips/user/`)에서 통합 `/api/graphql`로 옮겨가
   `extract_reel_nodes`가 새 응답 모양(`data.xdt_api__v1__clips__user__connection_v2.
   edges[].node.media`)을 못 읽어 0건이 나왔다 — 이건 로그인과 무관하게 Apify로 갔어도
   부딪혔을 문제. 목록 응답엔 `taken_at`·`video_versions`가 없어, 처음엔 `/reel/{code}/`
   permalink를 열어 응답을 가로채봤는데 **유저의 다른 최근 게시물이 섞여 와 code 불일치 시
   발행시각이 전부 똑같아지는 버그**가 남— 이 방식은 폐기. 대신 목록에서 얻은 `pk`로
   `/api/v1/media/{pk}/info/`(구 REST 모양, `X-IG-App-ID` 헤더)를 직접 호출하는 훨씬 간단하고
   정확한 방법으로 교체.
5. **1+5채널 스파이크 결과**: nike·gymshark·zara·starbucks 전부 `ok`(top3 전부 정확한
   timestamp·videoUrl 확보), homeinon·salimhome은 `not_found`(릴스가 없는 계정으로 보임,
   로그인과 무관). **채널당 평균 5초** — Apify(채널당 8.4초)보다 빠르고 403 위험도 없다.

**다음(진짜 10채널/200채널 게이트 전)**: 실제 등록된 레퍼런스 채널 목록으로 10채널 게이트를
서버에서 돌려 성공률·소요를 재확인한 뒤 `INSTAGRAM_SCRAPER=playwright` 전환 여부를 정한다.
세션 파일(`scripts/instagram_session.json`)을 서버로 옮기고 `INSTAGRAM_SESSION_PATH` 지정하는
작업이 아직 남아있다.
