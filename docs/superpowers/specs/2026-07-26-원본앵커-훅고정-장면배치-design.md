# 원본 앵커 차용 + 훅 고정 + 결 맞춘 장면배치 — 설계

**날짜**: 2026-07-26 · **트랙**: 장면스파인 · **소재**: 제작소 믹스(레시피·제품/홈템)

## 0. 한 줄

원본 크리에이터가 **수작업으로 맞춰둔 "대사↔장면" 페어**를 통째로 차용한다.
원본에서 기능·장점·비법을 실증하는 조각(`is_key`)을 앵커로 뽑아 우리 비법 구간에 고정하고,
화면 위 대사만 우리 스토리 톤으로 교체한다. 훅에는 리스트 중 제일 좋은 장면을 고정한다.

## 1. 문제 (실측 근거)

실사용 소스 3편(책상 `ab9cf1f10d46`, 식기세척기 `video`, 세탁조솔 `video (1)`)을 프레임+화면자막으로
직접 뜯어 확인한 것:

1. **남의 CTA·워터마크가 픽셀에 박제된 채 노출된다.** 책상 영상 t=04 구간이 원본의 "궁금하시면 영상
   아래" + 빨간 화살표 CTA 장면인데 그대로 믹스에 쓰임. 대사를 덮어도 화면 텍스트·화살표는 안 지워진다.
   → 첫·마지막 세그먼트에 이런 게 집중된다(첫=썸네일·인트로, 끝=CTA·구독유도).

2. **의미매칭이 "탐색" 문제라 오배치가 난다.** 현재 파이프라인은 우리 대본을 먼저 만들고 각 비트에 맞는
   화면을 라이브러리에서 *찾는다*. 원본이 이미 완벽히 맞춰둔 정답 페어를 버리고 처음부터 다시 매칭 →
   "찢기" 대사에 도우반죽 붙는 류의 오배치(2026-07-20 job 2c9db3e2 실측).

3. **장면 순서 핑퐁(결 깨짐).** 레시피는 시간축(조리→완성)이 있어, 조리→완성→다시 조리로 배치되면
   시간이 거꾸로 흐르는 것처럼 보인다. 현재 `_chronological_respine`은 한 영상 안 시간순만 맞출 뿐
   완성/조리 성격을 구분 못 해 이 핑퐁을 못 막는다.

## 2. 핵심 통찰

**원본 크리에이터가 대사↔장면을 이미 수작업으로 완벽히 맞춰놨다.** 그 노동의 결과(실증 페어)를 차용하면
매칭을 새로 할 필요가 없다. 문제가 "화면을 찾는 탐색"에서 "정답 페어를 차용"으로 바뀐다 → 오배치 원천 제거.

실증(2026-07-26, 소스 2편 26개 세그먼트 육안 분류): `is_key` 기준으로 기능·장점·효과 실증 구간이
100% 의도대로 갈렸다. 요약이 아니라 O/X 분류라 Gemini가 안정적으로 판정 가능.

| 소스 | is_key로 잡힌 것 | 정확한 이유 |
|---|---|---|
| 식기세척기 | 넓다·큰팬·과일세척·허리안꺾음 | 말"넓은지"↔화면 가득찬 내부 (원본이 맞춤) |
| 세탁조솔 | 틈에쏙·패킹안까지·묵은때빠짐·통돌이드럼호환 | 말"쏙 들어가서"↔화면 솔이 틈에 |

두 번째 영상은 KEY가 스토리 사이에 흩어져 있어도(t=10~14 / t=18~20) 각각 정확히 잡힘을 보여줬다 →
"몰아넣기"가 아니라 **KEY를 앵커로 뽑아 재배치**가 맞다.

## 3. 확정 규칙

### 3-1. 공통 (소재 무관)

1. **첫·마지막 세그먼트 완전 삭제** — 소스가 세그먼트 3개 이상일 때만(2개 이하면 삭제 안 함).
   한 번이라도 CTA·워터마크가 들어가면 영상을 다시 만들어야 하므로 감점이 아니라 완전 삭제.
2. **좋은 장면 추출 → 겹침 없이 리스팅.** 소스 2~5개에서 임팩트 있는 장면을 뽑아 리스트화하되
   같은 장면은 겹치지 않게(soft dedup). ("완성샷을 양 끝에 고정"이 아님 — 그건 과설계였다.)
3. **훅 = 리스트 중 제일 좋은 장면 고정.** 이것만 강제. 끝을 완성샷으로 억지 회수하지 않는다.
   조각이 충분하므로 억지 반복·회수 불필요(맨 위에 한 번 더 나와도 무방하나 강제 아님).
4. **앵커(`is_key`)는 본문 한 덩어리로.** 완성/좋은 장면으로 끊지 않는다.
5. **강한 장점 2~3개만.** 장점(claim)별 dedup 후 강한 것만 — 목표 20초에 하나당 2~3초.
   6개 다 넣으면 나열식 튜토리얼이 되어 스토리가 죽는다(_STORY_RULES 위반).
6. **대사는 언제나 우리 한 스토리.** 인물1·사건1·결말1(`_STORY_DECLARE`). 소스가 5개라도
   스토리는 하나. 화면은 소스 골고루(edit_plan:350 유지).
7. **로고·모델명 박힌 컷 제외** — 브랜드가 화면에 뜨는 조각은 앵커에서 뺀다(별도 크롭/블러는 후속).

### 3-2. 소재 분기 (딱 한 가지만 다름)

- **레시피**: 앵커(조리 과정)는 **시간순**으로만. 조리 컷 사이에 완성/좋은 장면을 끼워 끊지 않는다.
- **제품/홈템**: 앵커(기능 실증)는 **강한 장점순**. 시간축이 없어 순서 자유.

### 3-3. 소스 개수별 (2~5개 믹스)

| 소스 | 앵커 풀 | 처리 |
|---|---|---|
| 2개 | 적음 | dedup 후 앵커 다 씀(부족하면 스토리 화면 비중↑) |
| 3개 | 적정 | 강한 장점 2~3개 표준 |
| 4~5개 | 풍부 | dedup이 핵심 — 유니크 장점 중 강한 2~3개만, 나머지 버림 |

> 소스가 늘어도 영상이 길어지거나 나열식이 되지 않는다. 늘어난 건 "고를 선택지"지 "넣을 개수"가 아니다.

## 4. 배치 골격

```
[추출]   소스 2~5개 → 좋은 장면 리스팅(겹침 제거) + is_key 앵커 추출 (첫·마지막 삭제)
   ↓
[훅]     리스트 중 제일 좋은 장면 = 훅 고정   ← 이것만 강제
   ↓
[본문]   나머지 좋은 장면 + 앵커(is_key)를 겹치지 않게 배치
         · 레시피 → 앵커(조리)는 시간순
         · 제품   → 앵커(장점)는 강한 순
   ↓
[CTA]    마무리 (완성샷 억지 회수 X)
```

## 5. 구현 배선 (기존 뼈대에 얹기 — 새 시스템 아님)

### 5-1. `script_extract._PROMPT` + `_assign_seg_ids` — 필드 2개 추가
Gemini 영상 분석 1회에 필드만 추가(호출 0회 증가). 기존 `has_effect`·`action`과 같은 방식.

- **`is_key`** (bool): 이 구간이 제품/도구의 기능·성능·장점·효과를 화면으로 실증하거나(넓다·크다·
  쏙 들어간다·때가 빠진다를 실제 행동/결과로 보여줌), 요리·살림의 핵심 방법을 손동작으로 보여주면 true.
  단순 도입 상황·인물 등장·감상·완성 인사·CTA·링크유도면 false. (원본이 "이 대사에 이 장면"으로
  맞춰둔 실증 페어를 골라내려는 것.) fail-open: 없으면 false.
- **`shot_role`** (str, optional): `조리`(손이 재료 다룸) / `완성`(완성 결과물이 화면 주인공) /
  `기타`. 레시피 결 맞춤 배치에만 씀. 없으면 `기타`.

`_RESPONSE_SCHEMA`의 required엔 넣지 않는다(기존 추출본 호환).

### 5-2. `edit_plan._build_inventory` — 첫·마지막 세그먼트 제외
`for seg in script.get("segments", [])` 순회 시 세그먼트 3개 이상이면 인덱스 0·마지막을 skip.
전사(full_text)는 온전히 유지 — B롤 화면 후보에서만 제외(대본 이해엔 첫/끝도 필요).

### 5-3. `edit_plan._chronological_respine` — 결 맞춤 배치로 강화
현재는 (video_id, start) 시간순만. 여기에:
- **훅 고정**: 첫 비트 primary는 respine 대상 제외(이미 꼬리 앵커 제외 로직 있음 — 대칭으로 머리도).
- **레시피 결 맞춤**: shot_role=완성 세그먼트는 본문 조리 앵커 사이에 끼우지 않는다. 조리끼리 시간순.
- **제품**: shot_role 없음 → 기존 시간순 유지 + is_key 앵커는 강한 순.

respined 플래그 방식 유지(fit 조작 안 함, ④ fit 정직화 계승). is_key 앵커는 respine 제외(앵커 고정).

### 5-4. dedup — 순수함수 신설 (2단계, 둘 다 결정적 코드·Gemini 없음)
- **장면 dedup** (§3-1.2): 좋은 장면 리스팅 시 같은 (video_id, 근접 start)·유사 scene_desc 조각 제거.
- **장점 dedup** (§3-1.5): is_key 앵커를 장점(claim=scene_desc 요지) 단위로 묶어 중복 장점 제거,
  화면 실증이 제일 선명한 하나만 남김. 남은 유니크 장점 중 강한 2~3개 선택.
둘 다 `edit_plan` 내 순수함수로.

## 6. 스코프 밖 (YAGNI)

- 크롭/블러(하단 박힌 텍스트 물리 제거)는 **별도 후속** — 이 스펙은 "안 쓰기(삭제·제외)"까지.
- 비전 기반 색감 이질감 판정(현 scene_desc 텍스트 근사) — 후속.
- 유튜브 소스 다운로드 쿠키 — 무관.

## 7. 검증 기준 (구현 후 육안)

말로 "될 것 같다"는 여기까지. 실증은 구현 후:
1. 소스 2~5개 믹스 렌더 → 첫/끝 세그먼트(CTA·썸네일) 안 나오는지.
2. 훅에 리스트 최고 장면 뜨는지.
3. 레시피: 조리→완성→조리 핑퐁 없는지(완성이 조리 뒤로 안 감).
4. 제품: is_key 장점 실증 컷이 본문 한 덩어리로, 대사만 우리 톤인지.
5. 스토리 인과·회수 살아있는지(앵커 얹어도 안 깨짐) — 가장 중요.

## 8. 리스크 / 기존 설계와의 관계

- **_STORY_RULES와 충돌 없음.** 말(대사)은 여전히 킥 감추기·CTA 미끼(변경 없음). 화면(앵커)은
  비법을 보여줘도 대사가 안 밝히면 궁금증 유지 → 상호보완.
- **다트랙 hot 주의**: `video_assemble.py`·`edit_plan.py`·`produce.html`은 반드시 트랙 격리.
- baseline 실패는 기존 것(내 변경이 깬 것 아님) 기준으로 게이트 판정.
