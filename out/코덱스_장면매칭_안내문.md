# 장면매칭 개선 — 작업 안내문 (코덱스용)

_작성 2026-09-09 · 숏템메이커(shopping_shorts) · 라이브 서비스_

---

## 0. 한 줄 요약

**대본 문장에 붙일 화면을 고르는 모델이, 그림을 한 번도 안 본다.**
남이 적어둔 글자 설명만 읽고 고른다. 이걸 고치는 게 이 작업이다.

---

## 1. 무엇을 하는 시스템인가

숏폼 영상 자동 제작기다. 흐름은 이렇다.

```
① 영상추출 : 참고 영상들을 컷으로 쪼개고 각 컷에 태그를 붙인다(장면 묘사·행위·역할)
② 대본생성 : 재료로 대본을 만든다 (문장 = "비트")
③ 영상대본MIX : 문장마다 어느 컷을 띄울지 정한다   ← ★여기가 이번 작업 대상
④~ TTS·자막·렌더
```

③의 핵심 함수는 `shopping_shorts/edit_plan.py`의 `build_edit_plan()`이다.

---

## 2. 문제 — 모델이 화면을 못 본다

`edit_plan.py`에는 이미지 전송이 **0건**이다(`Part.from_bytes`·`inline_data`·`image/jpeg` 전부 0).

모델이 화면을 고를 때 받는 건 이런 **글자 줄 목록**뿐이다(`_build_inventory`, 약 1656~1750줄):

```
[s12] (2.4s) 화면:손이 원형 물체를 집는다 | 말:… | 행위:… | 변화:… | 역할:… | 쓰임:…
[s13] (1.8s) 화면:건물 실내에서 남녀가 대화한다 | …
```

즉 **그림 대신 요약문을 읽고 고른다.** 요약이 조금만 뭉뚱그려져도(“원형 물체”) 맞는 컷을
못 고른다. 사장님 표현으로 “태깅과 대본에 맞는 게 분명히 있는데 엉뚱한 걸 배치한다”.

같은 병을 **재료 추출 쪽에서는 2026-09-09에 고쳤다**(아래 5절 참고). 매칭 쪽은 아직 그대로다.

---

## 3. 해야 할 일

`build_edit_plan`이 화면을 고를 때 **각 컷의 대표 프레임을 함께 보내라.**

### 이미 있는 부품 (새로 만들지 마라)

| 부품 | 위치 | 하는 일 |
|---|---|---|
| `frame_extract.extract_grid_frames(video_path, dest, n, phase)` | `shopping_shorts/frame_extract.py:97` | 영상을 n등분해 프레임 추출 → `[(Path, ts), ...]` |
| `frame_extract.extract_frame_at(video_path, dest, ts, filename)` | 같은 파일 45줄 | **특정 시각**의 프레임 1장 ← 컷 대표 프레임에 이 쪽이 맞다 |
| 받아둔 원본 영상 | `shopping_shorts/data/find_frames/<sha1(shortcode)[:16]>/*.mp4` | 이미 **8,489편** 있다. 새로 받을 필요 없다 |
| 프레임 캐시 | `shopping_shorts/data/frame_cache` · `frame_images` | 재사용 자리 |
| 참고할 선례 | `shopping_shorts/app.py`의 `_frames_for_source()` | 2026-09-09에 같은 일을 재료 추출용으로 붙인 코드. **이 모양을 따라라** |

### ★어느 방식으로 할지는 **이미 정해졌다** (2026-09-09 실측으로 결론)

한 job에 컷이 20~70개라 전부 이미지로 보내면 느리고 비싸다. 세 후보를 놓고
페이블·오푸스가 논의했고, **갈리던 지점을 실제로 재서** 결론이 났다.

```
후보① 글자로 추림 -> 상위 5~8개만 이미지로       (비트당 5~8장)
후보② 고른 뒤 그 한 장만 보여주고 되묻기   ← ★채택  (비트당 1장)
후보③ 여러 컷을 격자 한 장으로 합쳐 1회 호출     (칸이 작아 식별 흐려짐)
```

**②를 고른 이유 — 전부 실측이다**

| 근거 | 실측 |
|---|---|
| 되묻기 뼈대가 **이미 있다** | `edit_plan.verify_beat_screens` + 테스트 8건 |
| 프레임 뽑는 코드도 **이미 있다** | `app.py:5647` → `work/seg_thumbs/{seg_id}.jpg` 캐시 |
| 그 캐시가 실제로 쌓여 있다 | 서버에 **1,339개** |
| 소스 영상이 계획 시점에 있나 | 최근 job **10/10** 에 남아 있다 → **다운로드 지연 0** |
| 비용 | 비트당 1장(비트 8~12개). ①의 5~8배 절약 |
| ①·③의 문제 | `_build_inventory` 구조를 갈아야 해 "인벤토리 불변=회귀 0" 선을 깬다 |

**그래서 할 일은 사실상 한 줄이다:**

> `verify_beat_screens`가 지금 넘기는 **텍스트**(`scene_desc[:200]`)를
> **`work/seg_thumbs/{seg_id}.jpg` 프레임 1장**으로 바꾼다.

호출 경로만 새로 필요하다 — `_vault_call_once`는 문자열 전용이라 이미지를 못 싣는다.
이미지 싣는 패턴은 `frame_script.py:461·541`(`types.Part.from_bytes`)과
키회전 `_call_with_key_rotation`(373)에 이미 있으니 그대로 빌려라.

### ★페이블이 짚은 이 문서의 허점 (그대로 남긴다)

1. **`verify_beat_screens`는 지금 "화면 검증"이라 불리면서 텍스트만 본다.**
   이 문서가 이걸 결함으로 안 올렸었다. 고칠 대상이 바로 이것이다.
2. **검증 뒤에 또 채운다** — `verify_beat_screens`(4146) → `_fill_beat_screen_time`(4161)
   순서이고, 게다가 **`store.py:195·205`가 계획을 읽을 때마다 `_fill`을 다시 돈다.**
   plan 안에서만 검증하면 store 출구에서 무효가 된다 — **검증 출구는 store 쪽이어야 한다.**
3. `Recall@K` 지표는 ②에선 못 잰다(후보 K개를 안 만든다). 아래 10절 기준을 따라라.

### ★"좋아졌다"를 증명하는 법 (정답지 없이)

같은 job·같은 비트에 대해 **텍스트 판정과 이미지 판정 두 벌**을 찍고,
**갈린 건만** 사장님이 블라인드로 고른다(A가 맞나 / B가 맞나 / 둘 다 틀림).

- 전수 라벨링의 **1/5 이하 노동**이다
- 판정자가 사람이라 6절(정답지 없음)·5절(모델 자기채점 금지)에 안 걸린다
- 판정 근거는 이미 남는다: `fit_evidence="verify_failed"` · `verify_why`(4443~4445)
- **롤백 기준**: 갈린 것 중 이미지 쪽이 맞은 비율이 텍스트 쪽보다 **낮으면** 되돌린다

## 4. ★이미 만들어둔 것 — 반드시 먼저 읽어라

`edit_plan.verify_beat_screens()` (2026-09-09 작성, 테스트 `tests/test_verify_screens.py` 8개)

- 고른 화면이 그 대사에 맞는지 **비트마다 되묻는** 단계다.
- 지금은 **글자로만** 되묻는다 → **여기에 프레임을 넣는 게 가장 짧은 길일 수 있다.**
- 스위치: DB `settings` 테이블의 `screen_verify_enabled` (**현재 꺼져 있음**)
- 화면을 **교체하지 않는다**. 표시만 한다(이유는 5절).

## 5. ★이미 시도했다가 폐기한 것 — 되풀이하지 마라

전부 라이브 데이터로 실측한 결과다. 여기 적힌 건 **다시 해볼 필요가 없다.**

| 시도 | 결과 |
|---|---|
| 모델에게 **바로 고르라**고 하고 억지 선택을 잡아내기 | **0% 검출**. 재료가 없어도 모델은 무조건 고른다 |
| **요구를 먼저 적게** 한 뒤 맞는 컷 찾기 | **67%가 가짜 “없음”**. 문장에 갇혀 멀쩡한 컷을 기각 |
| **고르기 → 검증** (2단계) | 탈락 17%가 전부 진짜, 오탐 0 ← **이게 남았다** |
| **3표 다수결** | 83%가 같은 답. 낭비 |
| 낱말 겹침으로 **자동 재배치** | ★**방향이 반대였다.** 사람이 실제 바꾼 1,027건 대조: 버린 컷 겹침 0.82 / 고른 컷 0.73. 붙였으면 손이 더 갔다 |
| `fit`(모델 자기채점)을 품질 지표로 | **못 쓴다.** fit 5점을 사람이 1,158번 갈아치웠다 |

★**`fit`을 믿지 마라. 낱말 겹침을 기준으로 삼지 마라.** 둘 다 실측으로 기각됐다.

---

## 6. ★풀리지 않은 근본 문제 — 정답지가 없다

“무엇이 잘 맞는 배치인가”의 **기준이 이 시스템에 없다.**

- `fit` = 자기채점이라 못 쓴다
- 낱말 겹침 = 방향이 반대다
- 사람의 교체 기록 `scene_swaps` 1,027건 = **“그때 바꾼 것”이지 정답이 아니다.**
  반증에는 써도 **정답지로 부르면 안 된다**

그래서 “정확도 몇 %”를 주장하려면 **먼저 정답지를 만들어야 한다.** 없는 상태로 낸 숫자는
믿을 수 없다. 정답지 없이 개선을 주장하지 마라 — 대신 **before/after를 사람이 볼 수 있게**
나란히 내놓아라(같은 job, 같은 대본, 화면만 다르게).

## 8. 이 저장소에서 일하는 규칙 (★어기면 라이브가 깨진다)

1. **메인 폴더에서 코드 고치지 마라.** 반드시 자기 트랙 폴더에서 한다.
   ```
   py tools/track.py start <트랙명>      # .tracks/<트랙명> + track/<트랙명> 브랜치 생성
   ```
   이번 작업 트랙명 제안: **`장면프레임`**
2. 편집·git은 전부 그 폴더 안에서: `git -C .tracks/장면프레임 add -A`
3. 끝나면 **게이트를 통과해야만** 라이브로 간다:
   ```
   py tools/track.py finish 장면프레임     # 문법 → import → pytest. 실패하면 병합을 버린다
   ```
   ※ 병합 전 이미 실패 13건이 있다(기준선). **“전부 초록”이 아니라 “실패가 늘지 않았나”**로 본다.
4. **서버 파일 직접 수정 금지.** git에 안 남아 다음 배포에 덮인다.
5. `except Exception: pass`에는 **예산이 있다**(`tests/test_silent_except_budget.py`).
   조용히 넘기지 말고 이유를 stderr로 남겨라.
6. 같은 판단을 두 곳에 적지 마라. 한 곳에서만 정하고 나머지는 빌려 쓴다.

## 9. 실측 방법 (서버)

라이브 서버에 SSH로 붙어 **읽기 전용**으로 실험할 수 있다. DB는
`shopping_shorts/data/reference.db`(테이블: `produce_works`, `script_extracts`,
`scene_swaps`, `settings`).

★**서버에서 `git add`/`commit` 하지 마라** — 작업트리가 더러워지면 자동배포가 통째로 멈춘다.

## 10. 이 작업의 성공 기준

- 화면을 고를 때 모델이 **실제 프레임을 본다**(코드로 확인 가능)
- 비용·시간이 감당 가능하다(한 job 기준 추가 초·추가 호출 수를 **측정해서** 보고)
- 같은 job의 **before/after 화면 배치**를 나란히 볼 수 있다
- 기존 테스트가 늘어난 실패 없이 통과한다

**하지 말 것**: 정답지 없이 “정확도가 올랐다”고 주장하기 / `fit`을 근거로 쓰기 /
낱말 겹침으로 자동 교체 붙이기 / 검증 안 된 플래그를 라이브에 기본 ON으로 켜기.
