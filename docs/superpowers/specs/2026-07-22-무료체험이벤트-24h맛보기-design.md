# 설계 — 무료체험 이벤트 (가입 후 24h 맛보기)

- 작성: 2026-07-22 / 트랙 `회원승인`
- 후속: 회원승인 화이트리스트(대기실) + 회원관리 고도화(A+B+C)의 D/E 후속.
- 선행 설계: `2026-07-22-회원관리-이름전화결제기간-design.md`

## 목표

신규 가입자가 **사장님 승인 전에도 24시간 동안 전기능(담기·렌즈·레퍼런스·제작소)을 맛보되, 완성 렌더(제작)는 딱 1회**만 되게 한다. 24시간이 지났는데 아직 미승인이면 대기실(pending) 전면차단으로 복귀한다. 화이트리스트("사장님 승인한 사람만 사용") 모델은 유지된다 — 체험은 **한 번, 시간제한** 창일 뿐이다.

### 사장님 결정 (2026-07-22)
- 체험 기간 = **24시간**.
- 체험 범위 = **레퍼런스 + 담기·렌즈 열기 + 제작소 완성 1회**. (소재를 직접 모아 진짜 1편을 뽑는 강력한 맛보기.)
- 체험 만료 후(미승인) = **대기실(pending) 전면차단**. ranking_only 소프트랜딩 아님.
- admin 체험 배지 = **포함**.

## 핵심 통찰

두 개의 단일 초크포인트만 손대면 전 경로에 자동 적용된다.
- `access_level(customer_id)` (app.py) — 등급 판정 단일 진실원. API게이트·화면·크레딧 모두 이 함수만 본다.
- `check_and_count(cid, "render")` (app.py) — 렌더 과금 단일 초크포인트. 제작소 두 진입점(app.py:1525·4476)이 공유.

`/api/grab`(담기) 게이트는 `access_level != "full"`이면 차단인데, 체험 중엔 `full`이라 **자동 통과** — 손댈 필요 없다.

## 컴포넌트

### 1. `trial_ends_at` 컬럼 (store.py)
- `customers`에 `trial_ends_at INTEGER` (epoch초, nullable) 추가. 마이그레이션은 기존 `full_access_until`·`approved_at` 추가와 동일 패턴(`ALTER TABLE ... ADD COLUMN` + 존재검사).
- **하위호환**: 기존 pending 고객은 `trial_ends_at NULL` → §2에서 만료로 취급 → 그대로 pending. 백필 불필요.
- `get_customer`가 `trial_ends_at`를 반환하도록 SELECT·dict 확장.
- 설정값 `trial_event_hours`(기본 24) — 나중에 사장님이 `settings`로 조절 가능.

### 2. `access_level` 트라이얼 창 (app.py, approved_at 분기 내부)
```
if cust.get("approved_at") is None:
    tea = cust.get("trial_ends_at") or 0
    if now < tea:
        return "full"        # 🎁 무료체험 이벤트 창 (24h)
    return "pending"          # 대기실 (지금과 동일)
```
- `now` 인자는 기존 시그니처(`access_level(customer_id, now=None)`) 재사용.
- 승인되면(approved_at 값 있음) 이 분기를 안 타므로 기존 결제·기간(full_access_until/pro) 로직 그대로.

### 3. 렌더 1회 상한 (app.py `check_and_count`)
- 헬퍼 `_is_trial(cid, now=None)` = (`get_customer` 존재 AND `approved_at is None` AND `now < trial_ends_at`). cid==0(사장님) 제외.
- `check_and_count`에서 `op=="render"` 이고 `_is_trial(cid)`이면:
  ```
  used = st.usage_get(cid, "render", "trial")   # '오늘' 대신 고정 버킷 "trial" = 영구 카운터
  if used >= 1: return False                      # 2회째 차단
  st.usage_incr(cid, "render", "trial")
  return True
  ```
  - `usage_*` 테이블 키는 (customer, op, day-문자열). day에 `"trial"` 상수를 넣으면 **날짜로 리셋되지 않는 영구 버킷** — 새 컬럼 없이 "체험 렌더 1회 소진" 추적.
  - 전역 캡(`_global_over_cap("render")`)·실패 시 환불(`refund_credit`)은 호출부(1521·4472 등)에서 이미 걸리므로 그대로 작동. 단, 환불 대상 버킷 일치는 §3-검증에서 확인(아래).
- 렌즈·스크립트·담기는 체험 중에도 **일일 크레딧 그대로**(따로 안 막음). 사장님이 "담기·렌즈 열기"를 택했고, 이들은 이미 lens/script 일일 한도로 비용 방어됨.

#### 3-검증: 환불 버킷 불일치 리스크
`run_mix_job` 실패 시 `refund_credit(cid, "render")` → `Store.refund_daily_credit`가 **오늘(day) 버킷**을 되돌린다. 그런데 체험 렌더는 `"trial"` 버킷에 카운트했다 → 오늘 버킷은 0이라 환불이 헛돈다(체험 1회가 실패해도 소진된 채로 남음).
- **처리**: `refund_daily_credit`가 체험 사용자면 `"trial"` 버킷도 되돌리도록 하거나, 렌더 실패 경로에서 체험이면 trial 버킷을 환불. 계획 단계에서 `render_charge_day`가 실패 환불의 기준이므로, 체험 렌더 시 `create_mix_job(render_charge_day="trial")`로 넣어 **환불 대상 버킷을 일치**시키는 방식이 가장 국소적. 이 부분은 plan에서 정확한 배선을 확정한다.

### 4. 가입 배선 (store.py `create_customer`)
- `create_customer(..., approved=False)` 경로에서 `trial_ends_at = now + trial_event_hours*3600` 세팅.
- `approved=True`(사장님 직접 생성)는 `trial_ends_at` 미설정(NULL) — 이미 승인+체험(full_access_until)이라 이벤트 창 불필요.
- 구글 가입·아이디 가입 둘 다 `create_customer(approved=False)`를 타므로 **한 곳(create_customer) 수정으로 양쪽 커버**. 별도 signup 핸들러 수정 불필요(확인 필요 — plan에서 grep 검증).

### 5. admin 체험 배지 (app.py `list_customers` + static/admin.html)
- `list_customers` 응답 각 고객에 `trial` 여부 + 잔여시간 노출: `cu["trial_ends_at"]` 그대로 넘기고 프론트가 계산, 또는 `cu["trial_left_h"]` 서버 계산.
- admin.html 고객목록에서 체험 중이면 "🎁 체험중(잔여 Xh)" 배지 — 대기명단·정식승인과 시각적으로 구분. `level`은 체험 중 "full"로 나오므로 배지가 없으면 사장님이 정식회원과 헷갈린다.

### 6. 만료 화면
- 체험 만료 → pending → 기존 `_PENDING_HTML`(승인 대기 안내) 재사용.
- (선택) `_PENDING_HTML` 카피에 "무료체험이 끝났어요 — 승인/결제 후 계속 쓸 수 있어요" 한 줄. 체험 만료와 순수 대기(가입 직후 승인 전)를 굳이 구분하지 않아도 무해하나, 있으면 친절. 최소 구현에선 생략 가능.

## 변경하지 않는 것
- `/api/grab` 게이트(`!= "full"`) — 체험 중 full이라 자동 통과.
- 프리뷰(run_preview, script 크레딧) — 렌더 아님. 체험 중 일일 크레딧대로.
- 승인/결제/기간 로직(approve_customer 등) — 승인되면 트라이얼 분기를 안 탄다.

## 테스트 (pytest)
- `access_level`: 미승인+창 안 → "full" / 창 밖(now≥trial_ends_at) → "pending" / trial_ends_at NULL(기존고객) → "pending".
- 렌더 상한: 체험 중 1회 성공(True) → 2회째 False. 승인 후엔 일일 한도(2)로 복귀.
- 렌즈·스크립트: 체험 중 trial 상한 안 걸림(일일 한도만).
- 승인 전환: approve_customer 후 access_level="full"(트라이얼 아닌 결제창), 렌더 일일 한도 적용.
- 하위호환: trial_ends_at 없는 기존 pending 고객 = pending 유지.
- 환불 일치(§3-검증): 체험 렌더 실패 시 trial 버킷이 환불돼 다시 1회 가능.

## 리스크
- **환불 버킷 불일치**(§3-검증) — 가장 미묘한 부분. plan에서 배선 확정 + 테스트로 봉인.
- **체험 창 연장/재발급 없음** — 한 계정당 가입 시 1회. 재가입(같은 구글 sub) 시 `create_customer`가 안 불리고 기존 계정 로그인이면 trial_ends_at 과거 → pending. 어뷰징 방지상 의도된 동작.
