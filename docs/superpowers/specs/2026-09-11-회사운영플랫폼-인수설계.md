# 회사운영플랫폼 — 인수 설계 v1

## 1. 제품의 약속과 이번 범위

제품은 프로그램 목록을 보여주는 관리자 페이지가 아니라 '회사가 어떤 문제를 누구에게 맡겨 어떤 결과를 냈는지'를 관찰하는 운영실이다. 궁극적으로 프로그램 구매자에게 해당 사업의 조직·작업 절차·검증 체계를 설치한다. 실제 실행과 결과물이 감탄의 근거이며 장식용 AI 활동은 사용하지 않는다.

현재 승인된 구현 M1은 로컬 운영실이다. 조직·제품 탐색, 프로젝트 등록·담당 지정, 단계 진행·차단·재개·반려, 검증 기록, 이력 저장을 실제로 제공한다. 이것만으로 완전자동 회사를 완성했다고 보고하지 않는다.

M2 실제 업무 읽기 연결 → M3 제한된 AI 실행 → M4 자동 운영 → M5 고객 설치 상품화는 방향과 진입 조건만 정한 후속 단계다. 통합 대상 코드/API·예산·실행 권한이 확인되지 않았으므로 상세 구현이 끝났다는 뜻이 아니다.

## 3. 정보 구조와 화면

데스크톱: 상단 브랜드·로컬 연결상태·마지막 조회시각 / 왼쪽 회사 선택 / 중앙 조직 지도와 프로젝트 흐름 / 오른쪽 선택 업무·사건 기록. 작은 화면에서는 회사 선택 → 지도 → 업무 → 기록 순으로 세로 배치한다.

조직 지도는 대표 → 기획 책임 역할(Astra·Claude) → 실행 역할(Opus·Codex) → 팀으로 이어진다. 직급은 책임 관계, 모델은 배정 후보, 세션은 실제 실행 식별자이므로 하나로 합치지 않는다. M1 모든 AI 역할은 미연결이다. 사람 담당자 입력도 인증 계정이 아닌 수동 기록이다.

| 팀 id | 이름 | 관찰할 핵심 |
|---|---|---|
| new | 신규개발팀 | 제품 기획·신규 개발 |
| improve | 제품개선팀 | 고객 불편·UI·템플릿·성능 개선 |
| cs | CS팀 | 문의·고객 회복 확인 |
| ops | 서비스운영팀 | 실패·API 오류·복구 |
| qa | 품질검증팀 | 독립 검증·반려 |

회사 선택 시 제품·업무·이력·수익 구조가 함께 바뀐다. 팀 선택 시 해당 업무를 필터한다. 팀은 공통 카탈로그지만 각 프로젝트의 company_id를 반드시 유지한다. M1 회사 필터는 사용자 편의 기능이지 고객 테넌트 보안 경계가 아니다.

시각 방향: 아래 3-A 최신 지시를 따른다. 큰 한글 제목과 읽기 좋은 본문, 키보드 조작, 폼 label, 대화상자 포커스 복귀, 대비, reduced-motion, 390px 폭 가로 넘침 없음은 유지한다.

빈 화면에도 회사·제품·역할 구조는 보인다. 업무 0건은 실제 프로젝트가 없다는 뜻이며 '첫 프로젝트 등록'으로 이어진다. 데모 업무를 운영 실적으로 초기 생성하지 않는다. 읽기 실패 시 오류와 재시도, 마지막 성공 조회시각을 보여준다. polling은 작성 중 입력·선택·스크롤을 초기화하지 않는다.

### 3-A. 최신 이미지 피드백 — 시네마틱 운영실 (2026-09-11)

대표가 제시한 AGENT HQ 이미지 4장은 구조 참고이며 외형 승인안이 아니다. 대표는 2D 게임 같은 캐릭터·책상·부서 방과 작고 빽빽한 화면을 거절하고, 훨씬 화려하고 멋있고 생동감 있는 표현을 요청했다. 이미지의 에이전트 수/가동 수는 우리 회사 데이터가 아니며 복제하지 않는다.

**디자인 콘셉트: LIVING COMPANY / 살아 있는 회사의 아틀라스.** 실제 3D 엔진 도입 없이 먼저 CSS 깊이·레이어와 SVG 연결선으로 입체적 공간감을 구현한다. 전체를 빽빽한 카드 격자로 채우지 않는다. 모델/직원 숫자보다 '지금 무엇이 만들어지고 있는가'가 중심이다.

- 첫 화면: 넓은 어두운 공간 위에 세 회사의 큰 코어. 선택 회사는 전면, 다른 두 회사는 주변의 분명한 전환 지점. 메이커스랩 청록, HNL 따뜻한 골드, 스탁브레인 블루/바이올렛. 미연결도 아름답게 표현하되 작동하는 척하지 않는다.
- 회사 진입: 선택 코어를 중심으로 책임 역할과 5팀이 깊이 있는 레이어로 펼쳐진다. 연결선은 장식이 아니라 책임/업무 인계 관계다. 화면 위의 경로(전체 → 회사 → 팀)로 언제든 복귀한다.
- 업무 이동: 실제 새 사건 id 수신 시 해당 팀 연결선을 따라 짧은 빛의 이동 1회. polling마다 반복하거나 임의 타이머로 업무 진행을 만들지 않는다. 초기 과거 기록 로딩은 실시간 사건으로 재생하지 않는다.
- 작업 상세: 업무를 선택하면 장면 중심이 해당 업무로 이동하고, 읽기 쉬운 상세 패널에 현재 단계·담당·이유·검증·산출물이 나타난다. 코드/영상/문서는 실제 존재할 때만 프리뷰한다.
- 문제 표현: 차단은 해당 흐름의 끊김과 절제된 앰버 강조, 반려는 build로 돌아온 실제 사건 표시. 항상 문장과 아이콘을 병행해 색에만 의존하지 않는다. 화면 전체 경광등·섬광 금지.
- 매출: 제품에서 수익원으로 이어지는 별도 '사업 흐름' 보기. M1 금액은 —, 연결 미완료 레이블. 장식용 수익 카운터 금지.
- 움직임: 선택/확대/패널 전환 200~450ms를 초기 설계값으로 사용. 부드러운 공간 전환은 가능하나 실제 처리 중으로 오인될 상시 입자 이동·가짜 활동 펄스 금지. 사용자가 움직임을 끌 수 있고 prefers-reduced-motion에서 이동 효과 제거.
- 화면 질: 과도한 네온·블러·유리 카드 남용 금지. 핵심 숫자와 현재 업무는 읽을 수 있어야 한다. 확대/축소 없이 텍스트를 읽도록 적절한 정보 밀도 유지. 모바일은 동일 구조를 단순화해 기능 보존.

**검수에서 탈락할 화면:** 2D 사무실 게임, 이름만 바꾼 캐릭터 워커, 수십 개 작은 상자와 숫자로 채운 격자, 예쁜 배경 위 평범한 통계 카드만 있는 화면, 실제 사건 없이 상시 바쁘게 움직이는 화면.

현재 UI 에이전트 초안은 이 이미지 피드백 이전 산출물이다. 최종 디자인으로 승인된 것이 아니므로 실행 모델이 먼저 열어 보고 위 방향으로 개편한 뒤 G3에 제출한다. 승인된 '기능'을 보존하며 시각 구성을 강화한다. 아스트라 검수자는 데스크톱 실제 화면과 회사 → 팀 → 업무 이동을 직접 확인해야 한다.

## 4. M1 기술 경계

독립 company_ops/ 패키지. Python FastAPI/uvicorn, SQLite, HTML/CSS/vanilla JS. 새 프레임워크나 대형 빌드 체인을 추가하지 않는다. shopping_shorts/와 dashboard/의 코드·DB·라이브 프로세스를 바꾸지 않는다.

| 파일 (트랙 기준) | 책임 |

| company_ops/__init__.py | 독립 패키지 |
| company_ops/catalog.py | 회사·제품·팀·계획 역할·단계의 단일 정의 |

| company_ops/static/index.html | 화면 구조·폼 |
| company_ops/static/style.css | 시각·반응형·접근성 |

| company_ops/.gitignore | data/, .artifacts/, __pycache__/ 제외 |

기본 DB는 패키지 data/company_ops.sqlite3. COMPANY_OPS_DB 환경변수 또는 create_app 인수로 시험용 DB 분리. SQLite 연결은 요청/연산마다 열고 닫는다. WAL, busy_timeout, foreign_keys를 연결마다 설정. DDL 버전은 PRAGMA user_version=1로 추적; 재시작이 seed/프로젝트를 중복 생성하면 안 된다.

projects: id TEXT PK(UUID), company_id TEXT, title TEXT, team_id TEXT, owner TEXT, description TEXT, stage TEXT, blocked INTEGER, version INTEGER, created_at TEXT, updated_at TEXT. events: id INTEGER PK, project_id TEXT FK, company_id TEXT, kind TEXT, message TEXT, evidence TEXT, reviewer TEXT, created_at TEXT. 상태 변경과 사건은 같은 트랜잭션에서 저장. 로그 삭제·수정 API는 M1에 없다. UTC ISO8601 저장, 화면 현지시각 표시. 초기 version=1, 변경마다 +1.

원자적 버전 확인: BEGIN IMMEDIATE → 현재 행 확인 → version 비교 → 전이 조건 검증 → 업데이트+사건 INSERT → COMMIT. 실패는 ROLLBACK, 상태와 사건 모두 불변. 동시 요청은 한쪽 성공/한쪽 409가 되어야 한다. evidence/reviewer는 message에 합쳐서만 보관하지 않고 별도 필드도 보존한다.

## 5. API 계약

GET /api/state → {companies,teams,roles,projects,events,stages,integrations}. 회사/팀/역할 카탈로그는 위 정의를 따른다. companies 원소 {id,name,subtitle,products:[{name,status}],revenue:[문자열]}. teams {id,name,description}, roles {name,role,status}, stages {id,label}, integrations {name,status}. 프로젝트는 DB 필드, blocked는 boolean. 사건은 DB 필드 포함. 최신 사건 내림차순 최대 100개, 전체 이력은 GET /api/projects/{id}/events?before_id=N&limit=50으로 페이지 조회(limit 1~100). API 단에서 회사 쿼리 필터를 제공하면 알 수 없는 회사는 422로 거절한다.

POST /api/projects JSON:
```json
{"company_id":"makers","title":"장면꾸미기 사용 흐름 검증","team_id":"improve","owner":"대표","description":"템플릿 선택부터 저장·렌더까지 검증한다."}
```
응답 201 + project. company/team 카탈로그 존재 확인. 문자열 trim 후 title 1~120, owner 1~80, description 0~4000. 알 수 없는 필드 거부. intake/unblocked/version 1로 생성, created 사건 기록. 요청 예시는 테스트 데이터이며 자동 seed하지 않는다.

POST /api/projects/{id}/actions JSON:
```json
{"action":"advance","version":4,"note":"실제 사용 검증 기록","evidence":"검증 산출물 경로와 확인 결과","reviewer":"독립검증 담당"}
```
응답 200 + project. action enum, version 양의 정수. note/evidence 최대 4000, reviewer 최대 80, trim. 모든 변경의 actor는 현재 '대표 수동 입력'; reviewer 문자열은 인증·실제 독립성 보장이 아님을 UI/README에 명시한다.

오류: 존재하지 않는 project 404, stale version 409, 불가능한 전이 409, 입력/근거 누락 422, 허용 안 된 Origin/Host 요청 403 또는 host middleware의 400. JSON detail은 한글 설명. 프론트는 detail 문자열/검증 오류 배열 모두 처리. 409는 최신 상태 재조회와 재시도 안내, 입력을 무작정 지우지 않는다.

| 현재 상태 | action | 다음 | 필수 조건 |
|---|---|---|---|
| intake | advance | design | blocked 아님 |
| design | advance | build | blocked 아님 |
| build | advance | verify | blocked 아님 |
| verify | advance | done | blocked 아님, evidence·reviewer 비어있지 않고 reviewer와 owner를 trim/casefold해 비교 시 다름 |
| intake/design/build/verify | block | 단계 유지+blocked | 현재 blocked 아님, note 필수 |
| blocked | resume | 같은 단계+unblocked | note 필수 |
| verify | reject | build | blocked 아님, note 필수 |
| done | 모든 action | 거절 | 완료 기록은 이 버전에서 불변 |

blocked 중 advance/block/reject, unblocked 중 resume를 거절한다. 완료 근거 문자열 입력은 '사람이 기록한 확인'이며 시스템 자동 검수 승인이 아니다. 잘못 완료한 기록을 지우는 대신 후속 프로젝트로 정정한다. 임의 단계 변경 PUT은 만들지 않는다.

## 6. 보안·정직한 관측

127.0.0.1에만 bind. localhost/127.0.0.1 Host allowlist, 외부 Origin 쓰기 차단, Content-Type application/json 필수. 요청에 Origin이 있으면 scheme+host+port까지 현재 origin과 정확히 비교하고 null origin 거절. 브라우저 cross-site 요청도 차단. 로컬 무인증이므로 인터넷/LAN 공개 금지. API 키·임의 파일 읽기·셸 실행·외부 URL 프록시 API 금지. 사용자 텍스트는 textContent, innerHTML 삽입 금지. 근거 URL/경로는 텍스트로만 표시해 임의 파일 접근이나 javascript 링크 실행을 피한다.

M1 연결상태: 로컬 저장만 실제 관측. AI/숏템메이커 장애/결제·매출은 미연결. HTTP 조회 성공이 AI 정상가동의 증거가 아니다. 상태 갱신 중단은 마지막 조회시각과 오류로 드러낸다. 테스트 데이터·스크린샷에는 고객 정보/키를 넣지 않는다.

## 7. 다음 단계의 진입 조건 (이번 자동 착수 대상 아님)

M2 숏템메이커 읽기 연결: 실제 job/error 스키마와 현행 트랙을 읽고 read-only adapter 설계. 회사/product/source_event_id로 중복 제거, event_time과 observed_at 구분, 비밀/개인정보 최소화, 연결 끊김 표시. 고객 job 재실행·키 교체·CS 발송은 금지. 합격: 실제 실패 1건이 원본과 맞고 중복 수집해도 사건은 1건, 수집 장애도 드러남.

M3 제한 AI 실행: 실제 가용 CLI/API와 문서를 확인한 후 adapter 인터페이스를 확정한다. task_id/role_id/provider/model/session_id/run_id를 구분, 요청/진행/산출물/오류/취소/사용량 사건 저장, 허용 도구·작업 경로·timeout·재시도·비용 한도 적용. 키는 UI/DB에 넣지 않는다. 모의 adapter는 테스트 전용으로 표시. 합격: 한 실제 업무의 실행 id와 산출물·독립검수·실패/재시작 복구 증거가 연결됨. 자동 셸 명령 범용 실행은 허용하지 않는다.

M4 지속 운영: 큐·스케줄러·heartbeat·lease·중복실행 방지·dead-letter·사람 판단 대기·예산 중단을 실측 기반 설계. 책임자가 낮은 비용 워커를 선택하고 실패 때 상위 검수로 올리는 규칙을 버전 관리. 완료와 배포/고객 회복을 별도 상태로 둔다. 합격: 프로세스 장애 뒤 이력 유실·중복 과금 없이 회복, 권한 밖 실행 차단, 일일 보고가 실제 사건으로 재생성됨.

M5 설치 상품화: 사용자 인증·RBAC·tenant 격리를 서버/DB/작업공간/비밀저장소 전 층에서 검증한 뒤 공개. package manifest는 제품 버전, 역할, 워크플로, 지침 버전, adapter 요구사항, 검증 기준을 담되 운영 데이터/고객 자료/키는 제외. import preview/버전 호환/rollback/백업 복구 검증. 수익 집계는 출처·기간·통화·환불·세금·원가·내부거래 제거 정의부터 확정. 후보 수익원을 실제 매출로 표시하지 않는다.

## 8. 아스트라 재검수 범위

제품 핵심 경험 훼손, 데이터/전이/API 계약 변경, 증거 없는 완료 허용, AI 실행권한/비용/고객 영향 확대, 최종 UI·통합 동작은 상위 검수 대상이다. CSS 간격, 오타, 명확한 테스트 실패 수정은 실행 모델이 처리한다. 상세 요청·승인 판본 규칙은 별도 검수절차 문서를 따른다.
