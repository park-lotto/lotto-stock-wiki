# 쓰레드(Threads) 수집 — 핸드오프

## 무엇을 했나

쓰레드(threads.com/threads.net) 게시물을 계정 단위로 수집해 담기 재료로 쓸 수 있게 만드는
파이프라인. Task 1~7에서 수집기·이어진 글 병합·품질점수·저장(Store)·담기 메타 보강까지
코드는 전부 끝났다. Task 8(이 파일)은 병합 전 점검·실측 기록만 남기는 태스크다.

## ★설계에서 뒤집힌 것 — 다음 세션이 반드시 알아야 함

원래 설계서(`.superpowers/sdd/2026-08-17-쓰레드수집-1-담기/`)는 "쓰레드는 로그인 세션이
필요하다"고 가정했다. **틀렸다.** 실측 결과 브라우저 헤더만 갖춘 **익명 HTTP GET**으로
데이터가 전부 온다:

- 필요 헤더: `User-Agent` + `Accept` + `Accept-Language` + `Sec-Fetch-*` 계열 + `Upgrade-Insecure-Requests`
- 실측: 200 / 1,080,480바이트 응답 / `like_count` 18 / `video_versions` 19개 / 쿠팡 링크 26개 검출
- 첫 시도가 실패했던 이유: UA만 보내고 나머지 헤더(`Accept`·`Sec-Fetch-*` 등)를 안 보냈기 때문

**→ 로그인·프록시·브라우저(Playwright)·별도 서버가 전부 불필요.** 그래도 Playwright 경로
(`_context_kw`, `dump_profile_payloads`, `fetch_video_url`)는 인스타처럼 헤더 요구가 나중에
강화될 때를 대비한 폴백으로 코드에 남겨뒀다 — 지우지 마라.

## 함정 (다음 세션이 또 밟지 않게)

- **헤더 하나라도 빠지면 껍데기 응답이 온다.** UA만 보내면 실패했던 것처럼, 헤더셋 전체를
  갖춰야 진짜 데이터가 온다. 헤더를 줄이는 "최적화"를 하지 마라.
- **캐러셀(여러 장 게시물)은 `carousel_media` 안에 영상이 들어있다.** 최상위 `video_versions`만
  보면 캐러셀 영상을 놓친다.
- **인스타그램 표(스키마)는 불가침이다.** 쓰레드는 인스타와 별개 소스/저장 경로로 만들었고
  인스타 쪽 코드·테이블은 건드리지 않았다.
- **yt-dlp는 쓰레드를 지원하지 않는다.** mp4 회수는 자체 HTTP/Playwright 경로로만 가능.
- **`video_url`이 담기(mix basket) 저장 경로에 안 실린다.** `_enrich_grab`이 화이트리스트
  8키만 저장하고 `mix_basket_set_meta`가 `video_url` 인자를 안 받는다. 필요해지면 호출부
  확장이 필요하다(이번 범위 밖으로 남겨둠, 아래 "남은 일" 4번).

## 실측 (2026-08-17)

컨트롤러가 `jiniggultem` 계정 1개로 직접 실행해 확보한 값. **계정 3개 실측은 아직 안 했다** —
브리프 템플릿은 3계정 기준이지만 실제로 돌린 건 1계정뿐이다. 추정치를 채워넣지 않았다.

- 계정 1개(`jiniggultem`) 수집: 소요 1.7초, 게시물 5건, 새로 5건, 실패 0건
- 미디어 종류: 5건 전부 `media_kind=video`
- 품질 분포: 7점 3건 / 5점 2건 (0점·1~4점 없음)
- 쿠팡 링크: 3건이 이어진 글(2/2 구성)에서 앞 글로 정확히 접혀 들어감
- 담기 메타 보강(`probe_grab_meta`, 실제 게시물 URL 기준): `title`·`thumbnail`·`video_url`
  전부 실데이터로 채워짐. 잘못된 URL은 `{}` 반환. `evilthreads.com` 같은 가짜 도메인은
  차단되고 `threads.com`/`threads.net`만 정상 인식.
- 실패 케이스 구분 확인: 존재하지 않는 URL → `fetch_html 실패 status=404`(HTML 0바이트) /
  파서가 못 찾는 구조 변화 → `_fetch_profile_nodes 0건 html_len=357525 nodes=0
  (파서가 노드를 못 찾음(구조 변화 의심))` — 두 실패가 로그 문구로 구분됨.
- **mp4 회수(Playwright `fetch_video_url`)는 미검증.** 실측 게이트를 안 탔다. 정직하게
  "미검증"으로 남긴다 — 다음 세션이 실동작 확인 필요(아래 "남은 일" 3번).
- 담기 1건 종단(제작소에서 재료로 쓰였는지)은 **확인 안 함**.

## 남은 일 (다음 세션이 이어받을 것)

1. **문턱 산출** — 지금 표본은 5건뿐이라 여기서 품질 점수 문턱을 정하면 틀린다. 200~300건을
   실제로 모은 뒤 분위수로 정할 것.
2. **후속 계획 2** (이번 계획 범위 밖으로 설계서에 명시됨):
   - 키워드 검색 수집(`search_keyword`) — 검색 경로부터 실측으로 확정해야 함
   - 랭킹 탭 노출 — `ranking.build_overseas_items` 재사용 + UI 탭 추가
   - 매일 자동 수집(크론)
3. `fetch_video_url`(Playwright 경로) 실동작 검증 — 아직 아무도 실제로 안 돌려봄
4. `video_url`을 담기 저장 경로에 실으려면 `_enrich_grab` 화이트리스트와
   `mix_basket_set_meta` 시그니처 확장이 필요(필요해질 때 작업)
5. **파킹된 것**: `threads_upsert`의 SELECT-then-write 경합 — 이 저장소의 기존 관례라서
   신규 결함으로 취급하지 않고 그대로 남겨둠
