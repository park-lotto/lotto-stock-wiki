0. 한 문단 요약
────────────────────────────────────────────────────────────────────────────────

숏템메이커는 "쇼핑 숏폼 영상을 원클릭으로 만들어 주는 SaaS"다.

사용자가 참고할 영상(인스타 릴스·유튜브 쇼츠 등)의 링크를 담으면,
시스템이 그 영상들을 내려받아 → 장면을 분석·태깅하고 → 새 대본을 쓰고 →
AI 음성을 합성하고 → 원본 자막을 지우고 → 장면을 재배열해 붙이고 →
꾸미기 틀·썸네일·제목·해시태그까지 만들어 → 완성된 세로 영상(mp4)을 뽑아준다.

핵심 가치는 "편집을 몰라도 딸깍 몇 번으로 판매용 숏폼이 나온다"이며,
타깃은 영상 편집이 어려운 일반 판매자(특히 시니어층)다.

라이브 주소: https://shoppingshorts.duckdns.org
브랜드명: 숏템메이커 (이전 명칭 '숏템탑스/숏템박스'는 폐기, 2026-08-30 확정)
이전 예정 도메인: stmaker.kr

2. 사용자가 겪는 흐름 — 제작소 10단계
────────────────────────────────────────────────────────────────────────────────

화면 상단에 무지개색 단계 바(도크)가 있고, 순서대로 내려간다.
(코드 정본: produce.html 의 STEP_LABELS)

  1단계  영상추출/분석      담은 영상을 내려받아 장면 단위로 쪼개고 비전 태깅
  2단계  대본생성           소재의 내용을 바탕으로 새 대본을 쓴다(Gemini)
  3단계  영상대본MIX        대본의 각 문장(비트)에 어떤 장면을 붙일지 편성(EDL)
  4단계  TTS음성            비트별로 AI 음성 합성 + 자막 타이밍 산출
  5단계  고품질 자막제거     원본 영상에 박힌 자막을 지운다(하드섭 리무버)
  6단계  장면꾸미기          채널명·제목·조회수 등이 들어간 '틀'을 얹는다
  7단계  썸네일             표지 이미지 생성
  8단계  제목·태그          SEO 제목과 해시태그
  9단계  완성본             최종 mp4 렌더
 10단계  SNS 예약           Buffer 연동으로 예약 발행

핵심 개념 — "비트(beat)"
  대본을 문장/구절 단위로 쪼갠 것이 비트다. 비트마다
    · narration      (그 비트의 대사)
    · caption_lines  (화면에 뿌릴 자막 줄 나눔)
    · primary        (붙일 장면 = 소스 영상의 특정 구간)
    · target_seconds (목표 길이)
  가 붙는다. 이 비트 배열이 곧 '편성(edit_plan)'이며 제작의 중심 자료구조다.

핵심 개념 — "장면 스파인(scene spine)"
  예전엔 대본을 먼저 쓰고 장면을 나중에 맞췄는데, 그러면 말과 화면이 어긋났다.
  지금은 카테고리별 '스파인 템플릿'(문제→해결→결과→CTA 같은 뼈대)에
  태깅된 장면을 먼저 배치하고, 그 위에 대본을 얹는다.
  → 화면 순서가 먼저, 대사가 나중.

5. 과금·키 구조 (이 서비스의 독특한 부분)
────────────────────────────────────────────────────────────────────────────────

외부 AI를 많이 쓰기 때문에 "누구 키로 돌리나"가 곧 원가다.
그래서 회원이 자기 API 키를 등록하면 그 서비스는 포인트를 안 깎는다.

  본인 키 있음  → 그 키로만 호출. 포인트 차감 없음.
                  ★공용(본사) 키를 섞지 않는다 — 남의 돈을 쓰면 안 되므로.
  본인 키 없음  → 본사 키로 호출 + 포인트 차감.

이 설계에는 알려진 부작용이 있다:
  본인 키를 낸 성실한 고객은, 그 키의 크레딧이 마르는 순간
  공용 키로 넘어가지 못하고 **완전히 멈춘다**.
  반대로 키를 아예 안 낸 고객은 본사 키로 잘 돌아간다.
  → 2026-09-07 대응: 3단계 진입 시 키 미등록/잔액부족/키무효를
     큰 배너로 미리 알리는 장치를 넣었다(GET /api/tts/quota).

예외: Gemini만 '공용 풀 모델'이다. 회원이 키 1개를 내면 전체 풀에 합류시키고
      회원은 풀 전체를 무료로 쓴다(1개로만 돌리면 분당 한도에 바로 걸리기 때문).


────────────────────────────────────────────────────────────────────────────────
6. 개발·운영 방식
────────────────────────────────────────────────────────────────────────────────

[동시 세션 격리 — '트랙' 시스템]
  여러 작업(사람·AI 세션)이 동시에 진행되므로, 각자 별도 폴더에서 일한다.
    .tracks/<트랙명>/   ← 각 작업의 독립 체크아웃 + 전용 git 브랜치
  같은 폴더를 공유하면 '흡수 사고'(남의 미완성 코드가 내 커밋에 딸려가 라이브로
  나감)가 나기 때문이다. 규칙만으론 못 막아 폴더를 물리적으로 갈랐다.

[병합 게이트]
  py tools/track.py finish <트랙명>
    → 문법 검사 → import 검사 → 전체 pytest
    → "전부 통과"가 아니라 "병합 전보다 실패가 늘지 않았나"로 판정
    → 통과해야만 main에 병합. 실패하면 라이브는 무사.
  전역 OS 파일락으로 한 번에 하나씩만 게이트가 돌게 순번 대기시킨다.

[배포]
  서버는 main 브랜치만 추적. 크론(auto_deploy.sh)이 새 커밋을 감지해 pull.
  단 배포 시간창이 새벽 2~6시로 제한되고, 고객 접속 중이면 재시작을 연기한다.
  급하면 /home/ubuntu/DEPLOY_NOW 파일을 만들어 시간창을 무시한다.
  ※ 정적 파일(static/)은 재시작 없이 즉시 반영, 파이썬 모듈은 재시작 필요.

[검증 원칙 — 이 프로젝트의 제1 규칙]
  "실제로 돌려보고 확실할 때만 '됐다'고 한다."
  정적 검토·문법 검사·단위 테스트 통과는 확인이 아니다.
  실제 라이브 화면에서 그 버튼을 누르고 결과물을 눈으로 봐야 한다.
  (예: 2026-09-07, 배너 JS가 <script src=...> 안에 들어가 실행조차 안 됐는데
   node --check는 통과했다. 브라우저에서 typeof로 찍어보고서야 발견됐다.)

[설계 원칙 — "같은 판단을 두 곳에 적지 마라"]
  같은 결정이 코드 두 군데에 적히면 언젠가 반드시 어긋난다는 것을
  여러 번의 실사고로 확인했다. 그래서 판정처를 항상 한 곳으로 모은다.
  실제 사고 예:
    · 계정↔프록시를 두 번 정해 로테이션이 통째로 무력화
    · 설명 문구가 HTML과 JS 두 곳에 있어 HTML만 고치면 화면이 안 바뀜
    · 자막 구절 나눔이 저장 쪽과 렌더 쪽 기준이 달라 저장이 무효화됨

────────────────────────────────────────────────────────────────────────────────
8. 이 문서를 읽는 AI에게 — 맥락 요약
────────────────────────────────────────────────────────────────────────────────

숏템메이커를 한 줄로 설명하면:
  "쇼핑 숏폼을 만들기 위해, 남의 잘 나가는 영상을 재료로 삼아
   대본·음성·자막·장면·꾸미기를 자동 조립해 완성 mp4를 뽑는 파이프라인 서비스"

기술적으로 어려운 지점은 세 가지다:
  (1) 말과 화면 맞추기 — 대본 문장과 영상 장면의 의미가 어긋나면 못 쓴다
  (2) 시간 정합 — 음성 길이·자막 표시 시간·컷 길이가 프레임 단위로 맞아야 한다
  (3) 원본 흔적 지우기 — 남의 자막·워터마크를 지우고 내 것으로 갈아끼우기

사업적으로 어려운 지점은:
  (1) 외부 AI 원가 — 회원 키 위임 구조로 풀고 있으나 부작용이 있다
  (2) 소재 공급 — 크롤링이 각 플랫폼의 차단과 계속 싸운다
