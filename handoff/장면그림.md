### ★한 요청에 묶는 배치 — 만들었다가 뺐다. 그리고 뺀 이유는 **틀렸었다**

흔들린 칸들:
```

## 2026-09-10 (7) — 페이블·아스트라 교차검토에서 결함 6개가 나왔다 (전부 수정)

### 찾아낸 결함과 수정

| # | 누가 | 결함 | 수정 |
|---|---|---|---|
| ① | 아스트라·페이블 | 교체 뒤 **원본 화면 기준 지문**을 저장 → 다음 저장마다 같은 칸을 다시 물음 | 교체 뒤 새 화면 기준으로 지문 재계산 |

| ④ | ★페이블(실행으로) | `_apply_beat_sources`(store.py:168)가 **저장마다 교체를 되돌리고** 검증이 다시 교체 → 무한 왕복, alternates가 자람. **사람이 "↩ 원래대로"를 눌러도 다음 저장에 다시 바뀜 = 되돌리기 무효** | 잠긴 칸·교체된 칸은 되돌리지 않는다 |

### 왕복이 사라졌는지 실행으로 확인 (store 출구를 5번 지나게 함)
```

2회차 저장 — 화면 b / 모델 호출 0회 / 되돌릴 원본 a
3회차 저장 — 화면 b / 모델 호출 0회 / 되돌릴 원본 a

5회차 저장 — 화면 a / 호출 0회 ★사람 결정이 지켜졌다
```

### 두 AI가 공통으로 남긴 경고 (내 표현을 정정한다)
- **"20칸 자동 교체"는 실행 성공 건수지 품질 개선 20건이 아니다.** "대사와 모순 없음" ≠ "더 좋은 컷".
- **5%는 재검사 불일치율이지 오판율이 아니다.** "되돌리기가 있으니 감당 가능"은 근거가 약했다
  — 되돌리기 자체가 사장님에게 생기는 일이다.
- `candidates()`는 **첫 합격**에서 멈춘다 — "맞는 것"이지 "가장 맞는 것"이 아니다.
- 프레임은 컷 **시작 부근 한 장**이라 뒤에 나오는 동작·자막은 못 본다.
- 09-10의 2%(44칸 중 1)는 표본이 작고 소재 구성도 다르다 — 앞단 효과를 확정할 근거가 아니다.

### ⏭ 그래서 켜는 순서 (두 AI 권고)
```
1단계  screen_verify_enabled=1 만 켠다  → 표시만. fail-open이라 손해는 호출 6회/job
       며칠 관찰해 2%가 진짜인지, 경고 중 오탐이 얼마인지 본다
2단계  교체 20칸을 **원본/교체본 순서를 가리고 실제 재생**해 사장님이 개선/동급/악화로 판정
       (아스트라 제안 — 모델끼리 채점하면 같은 편향에 갇힌다)
3단계  그 결과가 좋으면 screen_verify_autofix=1
```

## 2026-09-10 (8) — 사장님 계정(admin=cid 0)에만 켠다

사장님: "내꺼만 다 켜서 해보면 안 되나" / "admin"

`screen_verify.flag_on()` 신설 — 스위치 값이
```
"1"        전체
"cid:0"    그 계정에만        ← 지금 이걸로 켠다(admin = customer_id 0)

판정은 이 함수 **한 곳**에서만 한다(검사·자동교체 두 스위치가 같은 규칙을 쓴다, 0순위-B).
`store.finalize`가 그 job의 `customer_id`를 넘긴다.

**사장님 계정에서는 1·3을 동시에** 하는 방식으로 바꾼 것이다. 고객은 영향 0이고,
사장님이 실제로 쓰시면서 개선/악화를 직접 보시는 게 곧 2단계다.
