## 2026-09-06 (회사PC) — 렌즈 검색어에 제품명 합류 + 900자 + 온도 0

사장님: **"샤오홍슈에서 원본영상을 찾는 것에 사람들이 제일 필요로 한다. 검색어를
자막을 다 보고 제품명에 가까운 내용을 검색어로 뽑아야 한다."**

### 발단 — 같은 영상인데 누를 때마다 딴 제품이 나왔다

사장님 제보: 돌돌이 → 택배칼 → **노른자분리기**. 실제 제품은 옷 먼지 끈끈이
(실리콘 롤클리너)였다.

⚠️ **내가 첫 조사에서 제품을 잘못 짚었다** — "일본 미니 택배칼"이라는 **내가 지어낸
대본**을 넣고 테스트해 "대본을 넣으면 정확해진다"고 결론냈다. 정답을 내가 흘려준
것이지 정확도가 오른 게 아니었다. 사장님이 잡아주셨다.
→ 교훈: **테스트 소재를 지어내지 마라.** 지어낸 소재는 지어낸 결론을 만든다.

### 원인 — 두 겹 (전부 실측)

**① 온도 미설정.** `cn_search_candidates`의 `GenerateContentConfig`에 temperature가
없어 기본값(확률적)으로 돌았다. 같은 프레임·같은 입력 **5회에 5회 전부 다른 제품**:
버터커터기 / 에어팟케이스 / 미니커터 / 미니칼 / 실패(빈 결과).

**② 소재가 비어 있었다.** `_lens_source_text`가 대본에서 읽는 필드는 **`full_text`
하나뿐**이고, 추출기가 **자막·화면까지 다 보고** 정해둔 `source_brief.product`를
한 번도 안 읽었다. 소재가 0자면 모델은 썸네일 1장만 보고 찍는다.

**③ (곁가지) 400자 컷.** `_lens_source_text`는 900자까지 모으는데 프롬프트가
다시 400자로 잘랐다. 쇼츠 대본은 앞이 인사·후킹이라 앞에서 자르면 제품 특징이
날아간다 — 실측: 잘려나간 112자에 '칼날·키링·안전·박스테이프'가 전부 있었다.

### 서버 실측 — product 칸은 이미 거의 다 채워져 있다 (이 작업의 근거)

```
2026-07  204건 중 product   0건 (0%)    ← 옛 추출본(source_brief 자체가 없음)
2026-08 2243건 중 product 1951건 (86%)
2026-09 1970건 중 product 1969건 (99%)
★ full_text가 0자인 280건 중 279건도 product는 채워져 있다
```
→ **무자막·무음성 영상에서 렌즈를 살리는 유일한 재료.** 백필 불필요.

### 변경 (커밋 5e8ee720c)

- `app._lens_source_text`: `source_brief.product`/`core`를 소재 **맨 앞에** 합류.
  맨 앞인 이유 = 프롬프트가 소재를 **앞에서부터** 자르므로 제품명이 절대 안 잘리는
  자리여야 한다. dict가 아닌 옛 데이터는 조용히 건너뛴다(문자열로 든 것이 있다).
- `video_analysis._LENS_PROMPT_SRC_MAX` 신설(900) — **캐시키와 프롬프트가 같은 상수**를
  쓰게 묶었다(0순위-B). 따로 두면 서로 다른 소재가 한 캐시칸을 공유해 오답이 굳는다
  (memory `reference_캐시키_불일치함정`).
- `cn_search_candidates`: `temperature=0`. 검색어는 창작이 아니라 **판독**이다.

### 검증 (전부 실행 결과)

| 항목 | 전 | 후 |
|---|---|---|
| 같은 입력 5회 | 5회 전부 다름 | **5/5 동일** |
| 제품명 합류 시 | — | 3/3 동일 + 정답(휴대용 실리콘 롤클리너 / 硅胶粘毛滚·可水洗) |
| 소요시간 | 400자 11.75초 | 900자 12.57초 (**+0.8초**, 각 3회 평균) |

- **+0.8초는 체감 0**: 이 호출은 `/api/lens/search`와 **병렬**이다(index.html:3042).
  둘 중 늦은 쪽이 전체 시간인데 렌즈 이미지검색이 보통 더 늦다.
- `_lens_source_text` 배선: 진짜 DB 왕복으로 제품명이 **맨 앞**에 오는 것 확인.
- 신규 테스트 7개. ★**사보타주로 4건이 실제로 빨개지는 것까지 확인**(가짜 단언 아님).
- `test_app_lens` 50 passed / 렌즈·비전 관련 **312 passed, 0 failed**.

## 2026-09-06 (2차) — 📝 대본 분석 후 찾기 버튼 + 담기버튼켜기 제거

사장님: **"대본분석후찾기버튼 만들고 / 담기버튼켜기빼고"**

### 먼저 규명한 것 — 렌즈는 대본추출을 **하지 않는다**

사장님 질문("렌즈검색을 누르면 대본추출까지 되는 거 아닌가")에 코드로 답했다:
- `_lens_source_text`가 DB에 하는 건 `get_enrichment`·`get_script` **읽기 두 번뿐**.
  `save_script`도 추출 호출도 0건.
- 프론트 `lensSearch`도 `/api/extract_script`를 부르지 않는다.
→ 대본추출을 안 한 영상은 소재 0자 → **썸네일 1장만** 보고 검색어를 짓는다.
  지금까지 아무 안내 없이 **틀린 답을 정답처럼** 내놓고 있었다.

### 변경 (커밋 4abe4c8d8, main 병합 c0e28af63)

- 서버 `/api/lens/cn/keywords` 응답에 **`has_source`** 추가.
  ★판정은 **서버 한 곳**(0순위-B) — 프론트가 캡션 길이로 따로 재면 서버가 DB에서
  채운 소재를 몰라 반드시 어긋난다.
  ★`src`를 try **밖에서** 초기화 — 안에서만 만들면 `_lens_source_text`가 터질 때
  `has_source`가 NameError로 500이 된다.
- 프론트 `lensExtractThenSearch()`: has_source=false일 때만 버튼 노출 →
  ①`/api/extract_script` ②성공 시 옛 후보를 **버리고** 재생성(append=false).
  옛 후보는 썸네일만 보고 지은 것이라 이어붙이면 틀린 게 남는다.
  ⚠️ **자동으로 안 돌린다** — 대본추출은 과금이라 사장님이 누를 때만.
- `📥 담기 버튼 켜기` <a> 제거(자리에 주석만 — 이 파일의 기존 관례). 기능은 `/grab`에 그대로.

### 검증

- ★프론트 함수를 **떼어내 실제 실행**: ①성공=옛후보 비움·append=false·버튼복구
  ②실패=버튼복구·에러표시·옛후보 유지·재검색 안함 ③네트워크 예외 동일 ④이중클릭 차단.
- 신규 테스트 3개(누적 53). 사보타주로 2건 빨간불 확인.
  ⚠️ **내 테스트 하나가 가짜 단언이었다** — `cn_search_candidates`를 터뜨려도 그 **앞줄**에서
  src가 이미 채워져 NameError가 안 난다. `_lens_source_text`를 터뜨리도록 고쳐 진짜 실패 확인.
- 렌즈·비전·produce **313 passed, 0 failed** / node --check rc=0.
- **배포 확인(서버 실측)**: `git log -1` = c0e28af63, `lensExtractThenSearch` 2건,
  `href="/grab" target` **0건**, 워킹트리 clean.
  ⚠️ 웹 프로세스는 02:30 기동(병합 03:07 이후) — **재시작 전이라 파이썬 변경은 아직 미적용**.
  auto_deploy가 "고객 접속 중"으로 연기 중(최대 30분). 사장님이 화면에서 확인하실 때
  안 보이면 조금 기다리거나 `sudo systemctl restart shopping-shorts`.

### ⚠️ 다른 트랙 일 — 꺼놓은 키가 풀에 남아 있다 (내 트랙 아님, 손대지 않음)

워크트리에서도 똑같이 3건 실패** = 기준선 문제(내 변경과 무관). 재실행하니

