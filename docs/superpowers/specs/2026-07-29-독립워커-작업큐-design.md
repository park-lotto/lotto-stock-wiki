# 독립워커 — 배포 재시작에 안 죽는 작업 실행기 (설계)

- 날짜: 2026-07-29 / 트랙: 해외HOT
- 한 줄: **긴 작업(믹스·해외HOT 수집)을 서버 프로세스 밖으로 빼서, 배포 재시작에 죽지 않게 한다.**

## 1. 문제

긴 작업이 FastAPI 서버 프로세스 안의 `BackgroundTasks`·`threading.Thread`로 돈다.
배포는 `systemctl restart shopping-shorts`로 이 프로세스를 죽였다 살리므로 **진행 중이던
작업이 함께 SIGKILL된다.**

2026-07-29 실측(같은 날 3건):
```
16:03:59  사장님이 해외HOT "지금 업데이트" 클릭 → 수집 시작
16:09:03  다른 트랙 배포(모션레벨훅 4940a07b8) → systemctl restart → 수집 사망
16:18:13  믹스 매칭 job SIGKILL
16:27:02  또 배포
```
화면은 "실패"를 못 띄운다. 진행 표시만 사라져 **조용히 멈춘 것처럼 보인다** — 사장님이
"되고 있나?"를 네 번 물어야 했다.

### 이미 있는 방어막과 구멍

`deploy/auto_deploy.sh`(2026-07-19)에 **"렌더 중이면 배포 연기"** 가드가 이미 있다.
좀비 가드(30분 미갱신은 죽은 것으로 간주)까지 있어 설계가 좋다. 그런데 **보는 대상이
`mix_jobs`의 렌더 상태뿐**이다:

```sql
WHERE (status IN ('rendering','removing_subtitles') OR preview_status='rendering')
```

그래서 오늘 죽은 둘은 그물에 안 걸린다:
- **해외HOT 수집** — 진행 상태를 `overseas_hot_jobs._JOB`(프로세스 메모리)에만 들고 있어
  배포 스크립트가 밖에서 볼 방법이 없다.
- **믹스 매칭 단계** — `run_mix_job`은 status가 `rendering`이 아니라 그 전 단계다.

즉 "가드가 없어서"가 아니라 **"가드가 렌더만 보고 있어서"** 생긴 사고다.

### 왜 서버 증설로는 안 되는가

증설은 **동시 실행 시 메모리 부족**만 해결한다. 배포 재시작은 서버 사양과 무관하게
프로세스를 죽이므로, 100GB 서버여도 똑같이 죽는다. 둘은 대체재가 아니라 짝이다.

## 2. 목표 / 비목표

**목표**
- 배포·재시작과 무관하게 믹스·해외HOT 수집이 **끝까지 간다**.
- 그래도 죽으면 화면이 **"실패 — 다시 시도"를 보여준다**(조용한 멈춤 금지).
- 1GB 서버에서 동시 실행으로 메모리가 터지지 않게 **한 번에 하나**만 돈다.
- 서버를 키웠을 때 **설정만 바꿔 동시 처리 수를 늘릴 수 있다**.

**비목표**
- Redis·Celery 등 외부 큐 도입 — 1GB 서버에 과하다.
- 나머지 17개 짧은 백그라운드 작업 이전 — 몇 초짜리라 죽어도 타격이 없다.
- 자동 재시도 — "실패 표시 + 사장님이 다시 누르기"로 시작한다. 자동 재시도는 무한루프
  사고 전례(`제작소작업목록` 트랙, 2026-07-2x)가 있어 이번 범위에서 뺀다.
- 작업 취소 기능 — 요구가 나온 적 없다.

## 3. 대상 (23개 중 6개)

`grep`으로 확인한 백그라운드 진입점은 23곳이다. 이 중 **긴 것 6개**만 옮긴다.

| # | 진입점 | 함수 | 파일:줄 |
|---|---|---|---|
| 1 | 믹스 생성 | `run_mix_job(job_id, db_path, work_root)` | `app.py:2146` |
| 2 | 타입 변경 | `retype_mix_job(job_id, video_type, db_path, work_root)` | `app.py:2469` |
| 3 | 최종 렌더 | `run_render(job_id, db_path, work_root)` | `app.py:2567` |
| 4 | 미리보기 | `run_preview(job_id, db_path, work_root)` | `app.py:2614` |
| 5 | 자막 제거 | `run_clean_sources(job_id, db_path, work_root)` | `app.py:2641` |
| 6 | 해외HOT 수집 | `overseas_hot_jobs._run()` | `overseas_hot_jobs.py:186` |

믹스 5개는 시그니처가 `(job_id[, extra], db_path, work_root)`로 통일돼 있어 큐 하나로 받는다.

## 4. 설계

### 4.1 큐 테이블 (`store.py`)

```sql
CREATE TABLE IF NOT EXISTS job_queue (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    task         TEXT NOT NULL,      -- 'mix'|'retype'|'render'|'preview'|'clean'|'overseas'
    args_json    TEXT NOT NULL,      -- {"job_id": "..."} / {"job_id":"...","video_type":"..."} / {}
    state        TEXT NOT NULL,      -- 'queued'|'running'|'done'|'failed'
    error        TEXT,
    created_at   TEXT NOT NULL,
    claimed_at   TEXT,
    heartbeat_at TEXT,
    finished_at  TEXT
)
```
인덱스: `(state, id)` — 대기열 조회가 이 순서다.

**메서드**
- `enqueue(task, args) -> int` — 대기열에 넣고 id 반환.
- `claim_next() -> dict|None` — **원자적으로** 가장 오래된 `queued` 하나를 `running`으로.
  `UPDATE ... WHERE id = (SELECT id FROM job_queue WHERE state='queued' ORDER BY id LIMIT 1)`
  + `RETURNING` 한 문장으로 처리한다. 워커가 여러 개여도 같은 일을 두 번 집지 않는다.
- `heartbeat(qid)` — `heartbeat_at` 갱신.
- `finish(qid, ok, error=None)` — `done`/`failed` + `finished_at`.
- `queue_status(task=None, args_match=None) -> dict` — 화면용. 내 작업의 대기 순번과 상태.
- `reap_stale(minutes=2) -> int` — `running`인데 `heartbeat_at`이 N분 넘게 안 뛴 건
  `failed`(error='워커가 중단됐습니다')로 정리하고 개수 반환.

### 4.2 워커 (`shopping_shorts/worker.py` 신규)

```python
TASKS = {
    'mix':      lambda a: mix_pipeline.run_mix_job(a['job_id'], DB_PATH, _MIX_WORK_DIR),
    'retype':   lambda a: mix_pipeline.retype_mix_job(a['job_id'], a['video_type'], DB_PATH, _MIX_WORK_DIR),
    'render':   lambda a: mix_pipeline.run_render(a['job_id'], DB_PATH, _MIX_WORK_DIR),
    'preview':  lambda a: mix_pipeline.run_preview(a['job_id'], DB_PATH, _MIX_WORK_DIR),
    'clean':    lambda a: mix_pipeline.run_clean_sources(a['job_id'], DB_PATH, _MIX_WORK_DIR),
    'overseas': lambda a: overseas_hot_jobs._run(),
}
```

루프:
1. `reap_stale()` — 죽은 흔적 정리
2. `claim_next()` — 없으면 5초 자고 1로
3. 별도 스레드로 `heartbeat` 30초마다 갱신
4. `TASKS[task](args)` 실행 → `finish(ok=True)`
5. 예외 → `finish(ok=False, error=repr(e))` + 로그. **워커는 죽지 않는다.**

`__main__`으로 실행. 종료 신호(SIGTERM)를 받으면 **현재 작업을 끝까지 하고** 종료한다
(systemd `TimeoutStopSec`을 넉넉히 준다).

### 4.3 systemd 유닛 (`deploy/shopping-shorts-worker.service` 신규)

```ini
[Unit]
Description=Shopping Shorts Job Worker
After=network.target

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/lotto-stock-wiki
EnvironmentFile=/etc/shopping-shorts.env
ExecStart=/usr/bin/python3 -m shopping_shorts.worker
Restart=always
RestartSec=5
TimeoutStopSec=1800

[Install]
WantedBy=multi-user.target
```

`Restart=always` — 워커가 죽어도 리눅스가 5초 뒤 되살린다.
`TimeoutStopSec=1800` — 재시작 시 진행 중 작업을 30분까지 기다린다.

### 4.4 서버 쪽 변경 (`app.py` 6곳)

```python
# 전
background_tasks.add_task(run_mix_job, job_id, DB_PATH, _MIX_WORK_DIR)
# 후
store.enqueue('mix', {'job_id': job_id})
```

해외HOT은 `overseas_hot_jobs.start()`가 스레드를 띄우던 것을 `enqueue('overseas', {})`로
바꾼다. **중복 방지**: 이미 `queued`/`running`인 `overseas` 작업이 있으면 새로 넣지 않고
기존 것을 알려준다(지금도 `_JOB['status']=='running'`이면 무시하는 동작이 있다 — 계약 유지).

### 4.5 화면 (`static/index.html`, `produce.html`)

- 상태 조회 응답에 `queue`를 실어준다: `{position: 2, state: 'queued'}`
  - `position` = 내 앞에 있는 `queued`+`running` 개수.
- 표시:
  - `queued` → **"앞에 N개 대기 중"**
  - `running` → 기존 진행 표시 그대로
  - `failed` → **"실패했습니다 — 다시 시도"** 버튼
- 해외HOT 진행 표시(`overseasStatus`)도 같은 규칙을 따른다.

### 4.6 배포 가드 (`deploy/auto_deploy.sh` 수정)

지금 가드는 `mix_jobs`의 여러 상태를 뒤진다. **`job_queue` 하나만 보면 되므로 단순해진다.**

```sql
SELECT COUNT(*) FROM job_queue
 WHERE state='running' AND datetime(heartbeat_at) > datetime('now','-2 minutes')
```

동작:
- 위 개수가 0 → `shopping-shorts`와 `shopping-shorts-worker` 둘 다 재시작.
- 0이 아님 → **워커 재시작만 미룬다.** 서버(`shopping-shorts`)는 이제 안에 긴 작업이
  없으므로 **그냥 재시작한다** — 배포가 작업 때문에 막히는 일이 줄어든다.

좀비 가드는 `heartbeat_at` 2분으로 대체된다(기존 30분보다 정확하다 — heartbeat는 살아있는
동안 계속 뛰므로).

## 5. 단계 (배포를 나눠서)

라이브를 흔들 수 있어 한 번에 안 바꾼다. **각 단계가 그 자체로 안전하다.**

| 단계 | 내용 | 라이브 영향 |
|---|---|---|
| **P1** | `job_queue` 테이블 + store 메서드 + 테스트 | 없음(아무도 안 씀) |
| **P2** | `worker.py` + systemd 유닛 설치·기동 | 없음(큐가 비어 있어 놀고 있음) |
| **P3** | `app.py` 6곳을 enqueue로 전환 | **여기서 실제로 바뀐다** |
| **P4** | 화면 대기순번·실패 표시 | UI만 |
| **P5** | `auto_deploy.sh` 가드 교체 | 배포 동작 |

P3까지 가면 목적(안 죽음)은 달성된다. P4·P5는 마감이다.

## 6. 실패·엣지

| 상황 | 처리 |
|---|---|
| 워커가 SIGKILL로 죽음 | systemd가 5초 뒤 재기동 → `reap_stale`이 그 작업을 `failed`로 → 화면에 "실패, 다시 시도" |
| 워커가 배포로 재시작 | `TimeoutStopSec=1800`이라 진행 중 작업을 끝내고 종료. 가드가 애초에 미룬다 |
| 큐에 같은 작업 중복 | 해외HOT만 중복 방지(4.4). 믹스는 job_id가 달라 자연히 구분된다 |
| DB 잠김(SQLite) | 기존 `Store`의 `timeout` 설정을 그대로 쓴다. 워커가 하나뿐이라 경합이 적다 |
| 작업이 영영 안 끝남 | heartbeat는 뛰므로 stale이 아니다 — **이번 범위 밖**. 필요해지면 작업별 최대시간을 둔다 |
| 워커가 안 떠 있음 | 큐만 쌓인다. P2에서 기동 확인 필수. 화면은 "앞에 N개 대기 중"으로 계속 보인다 |

## 7. 테스트

- `enqueue` → `claim_next` 왕복. `claim_next`가 **오래된 것부터** 집는지.
- **동시 claim**: 두 번 연속 `claim_next` 하면 서로 다른 작업이 나오는지(같은 걸 두 번
  집으면 안 된다).
- `reap_stale`: heartbeat가 오래된 `running`만 `failed`가 되고, 최근 것은 안 건드리는지.
- `finish(ok=False)` 시 error가 남는지.
- `queue_status`의 `position` 계산(내 앞의 queued+running 개수).
- 워커 루프: 예외를 던지는 작업이 있어도 **워커가 안 죽고** 다음 작업으로 가는지(mock).
- 회귀: 해외HOT 중복 enqueue 방지.

## 8. 나중에 (이번 범위 밖)

- 워커 여러 개 — `claim_next`가 이미 원자적이라 **유닛을 복제해 띄우면 된다**(서버 증설 후).
- 자동 재시도 — 실패 원인별 분류가 먼저다.
- 나머지 17개 작업 이전 — 필요해지면.
