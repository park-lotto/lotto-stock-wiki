### 왜 공유트리를 유지하나 (기각한 대안)

사고 기록을 분류하면 **전부 git 계층·문서 계층**에서 났고, **파일 동시편집 사고는 0건**이다. 공유트리는 각 세션이 늘 남의 최신 편집 위에서 읽고 고치게 만들어 편집을 계속 통합시킨다 — 잘 하고 있는 유일한 일이라 안 건드린다.
세션당 worktree(A안)는 `produce.html`(이틀 20회 접촉)을 6갈래로 갈라 3-way 병합을 새로 만든다 → 기각.
`produce.html` 모듈 분해(C안)는 근본책이나 6세션을 전부 멈춰야 해서 페이즈2 이후 별건.

### 실측으로 확정된 제약 (설계를 바꾼 것들)

1. **`.git/hooks/post-commit` = `git push` 무조건** → 커밋=즉시 라이브. 검증은 **push 이전인 `commit-msg`에서만** 유효.
2. **`core.hooksPath`가 이미 `.git/hooks` 절대경로로 박혀 있음** + CRLF 재정규화 `pre-commit` 가동 중 → **hooksPath 바꾸면 둘 다 조용히 죽는다.** shim으로 얹을 것.
3. **6세션이 `.git`·인덱스를 공유** → `fetch`로 "0 behind" 확인해도 몇 초 뒤 커밋 시점엔 이미 남이 밀어넣음(실측: `401fe180..80487982`). 락은 `commit`이 아니라 **`add`부터** 감싸야 한다.
4. **`raw/`는 CLAUDE.md가 PC간 공유용으로 의도 추적** → 전면 denylist 금지. "기능 트랙 커밋에 딸려오는 것"만 막고 전용 트랙(`크롤데이터`)에만 허용.
5. `git commit -- <경로> -m "..."` 형식은 실패한다(`--` 뒤는 전부 pathspec).
