# 관측판 (서버 용량 관측 화면)

## 2026-08-27 — 배너 오해 수정 + "지금 줄 서 있는 사람"

### 무슨 일이 있었나

사장님이 관측판을 보고 **"대기가 밀렸다고 나오는데 오류 아닌가"**라고 물었다.
확인해보니 오류가 아니라 **문구가 현재형으로 읽히는 문제**였다.

- 배너는 `verdict()`가 **최근 7일 최대치**로 판정한다(`max_q >= 3` → warn).
- 화면에 뜬 18은 **2026-08-25**의 최대치였는데, 문장이 "대기가 최대 18개까지
  밀렸습니다"라 **지금 밀려 있는 것처럼** 읽혔다.
- 그때 서버 실측: `job_queue`에 `queued` **0건**(done 2746 / failed 76 / running 1).
  최근 표본 8개도 전부 `queued=0`. 즉 큐는 안 막혀 있었다.

### 고친 것

1. **배너에 날짜와 지금 값을 박았다** — "대기가 2026-08-25에 최대 18개까지
   밀렸습니다(최근 7일 최대치). 지금은 대기 없습니다."
   `verdict(db, cores, now_queued=...)`로 현재값을 받는다.
2. **`waiting()` 추가 — 지금 줄 서 있는 작업을 사람 단위로 보여준다.**
   왜: "대기 8개"만으론 처방이 안 나온다. **한 명이 8개를 몰아넣었으면 1인 동시
   제한, 8명이 한 개씩이면 워커 증설** — 처방이 정반대다.
   - `job_queue` → `mix_jobs.job_id` → `customers`로 이름을 찾는다.
   - 대기시간은 `created_at` 기준. `claimed_at`이 있으면 거기까지가 대기.
   - 10분 넘으면 빨강, 3분 넘으면 노랑(고객이 '느리다'고 느끼는 지점).
3. **cid 0 = "관리자(사장님)"** — customers에 행이 없어 "(모름)"으로 나왔다.
   그대로 두면 남의 고객이 밀린 줄 알고 엉뚱한 처방을 한다.
4. **job_queue 컬럼이 모자라도 목록이 통째로 비지 않게** 있는 컬럼만 고른다.

### 검증한 것

  (`박2 #12 / 관리자(사장님) #0` 정확히 나옴, `parklotto12@gmail.com #2` 2건 784초).
- 브라우저 렌더 확인(대기 있음 / 없음 두 상태 + 상세 펼치기). 콘솔 에러 0.
  ★첫 렌더에서 "3명이 3개" ← 표 합계 8개와 어긋남을 잡았다. `rows`(limit에 잘림)로
  세던 것을 `by_customer` 합으로 고쳤다.
- `pytest shopping_shorts/tests/test_capacity_watch.py` **15 passed**(5건 추가).
- 라이브 반영 확인: 서버 커밋 `1bf1659f1`, `09:20:02 shopping-shorts 재시작완료`.
