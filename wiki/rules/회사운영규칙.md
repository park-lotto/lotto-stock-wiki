# 회사 운영규칙

> 버전: 0.1 · 작성일: 2026-09-11
> 근거: 사장님과의 회사 구조·AI 조직·사업 상품화 대화 및 새 규칙 문서 작성 요청.
> 상태: 합의한 방향을 정리한 초기 운영 기준. 문서 작성이 AI 조직·자동화 시스템의 가동을 의미하지 않는다.
> 적용: 메이커스랩·에이치엔엘글로벌·스탁브레인의 회사 지도, 조직 설계, 운영 자동화, 개발 및 상품화.

## 1. 문서의 역할

- 저장소 작업·트랙 격리·배포·실측 검증 절차의 원본은 [CLAUDE.md](../../CLAUDE.md)다. 이 문서는 그 절차를 대체하지 않는다.
- 회사 운영 원칙과 조직 기준은 이 파일에서 관리한다. 같은 판단을 다른 규칙 파일에 복제하지 말고 링크한다.
- 현재 사업 사실, 합의한 설계, 검토 중인 제안, 실제 구현·가동 상태를 구분한다.
- 새 규칙은 기존 항목과 대조해 추가·수정하고, 변경 이유와 근거를 변경 이력에 남긴다.
- 이 문서는 실행 권한을 일괄 부여하지 않는다. 이미 승인된 업무 범위와 권한은 유지하며 불필요하게 재확인을 요구하지 않는다.

## 2. 사업의 목적

메이커스랩이 자동화 프로그램을 직접 개발하고 실제 사업에서 운영한다. 고객은 실제 실행 과정과 결과물을 보고 원하는 프로그램을 구매하며, 해당 프로그램을 운영하는 조직·업무 흐름·운영 지침까지 자신의 회사에 설치한다.

- 첫 고객은 자동화 사업을 만들고 운영하려는 사람이다.
- 제품의 중심 경험은 회사 지도에서 AI가 실제로 일하고, 단계별 검증을 거쳐 결과를 내는 모습을 보는 것이다.
- 첫 운영 검증 대상은 실제 고객이 사용하는 숏템메이커다. 매일 보완되는 제품과 고객 장애 대응을 우선 연결한다.
- 향후 프로그램별 설치 패키지는 프로그램, 역할, 업무 흐름, 지침, 검수 기준, 필요한 연결, 버전을 포함하도록 설계한다.
- 고객마다 계정·자료·실행 기록·비용을 분리한다. 패키지를 이식할 때 원래 회사의 고객 데이터나 비밀정보를 복제하지 않는다.
- 처음부터 외부 고객에게 제공할 제품을 고려하되, 실제 업무 한 흐름을 끝까지 검증하면서 확장한다.

- 숏템메이커 첫 달 약 4천만 원의 **수익**은 사장님 제공 정보다. 매출·순이익 등 회계 정의와 증빙은 미확인이다. 공개 실적이나 확정 매출 수치로 전환하지 않는다.
- 기존 UPM의 장기 사용, 월 77,000원, 입출고·엑셀·바코드 및 고객 종속 문제는 사장님이 제시한 경쟁시장 인식이다. 경쟁사 기능·가격·전환 난이도는 개발 전략 수립 시 확인한다.
- 회사, 제품, 제품을 운영하는 조직을 구분한다. 개발사·운영사·구매 고객이 다른 경우를 표현할 수 있어야 한다.

## 4. 목표 조직과 책임

아래는 구축할 조직 기준이다. 현재 가동하는 AI 직원 목록으로 표시하지 않는다.

| 층위 | 배치 방향 | 책임 |
|---|---|---|
| 대표 | 사장님 | 사업 목표·우선순위·주요 의사결정 |
| AI 공동 책임자 | 아스트라·클로드 | 사장님이 미처 생각하지 못한 아이디어와 개발 방향 제시, 대안 검토, 실행 전략과 결과 책임 |
| 팀·프로젝트 실행 리더 | 오푸스·코덱스 등을 업무에 맞게 배치 | 작업 분할, 워커 구성, 인계·진행 관리, 검증 증거 취합 |
| 워커 | 과제별 필요한 역할 | 정해진 범위에서 조사·설계·구현·분석·실행, 결과물 제출 |
| 독립 검수 | 품질검증팀의 검수 역할 | 요구 충족·회귀·실제 사용 결과 확인, 불합격 사유와 증거 제출 |

- 직책·역할·모델·실행 세션을 구분한다. 모델을 바꾸더라도 역할의 책임·업무·이력은 유지한다.
- 아스트라·클로드는 공동으로 검토하되 각 프로젝트에는 최종 취합·보고를 맡는 책임자 한 명을 지정한다.
- 모델별 세부 배치는 사용 가능성과 실제 작업 결과를 확인해 정한다. 이름만으로 품질을 보장하지 않는다.
- 워커는 필요한 작업이 있을 때 구성한다. 상시 활동하는 것처럼 연출하거나 불필요한 작업을 생성하지 않는다.
- 워커 생성 시 업무 범위, 결과물, 완료 조건, 작업 공간, 의존 작업, 사용 권한, 실행 한도를 지정한다.

## 5. 매일 운영할 팀

| 팀 | 일상 업무 | 인계·보고 |
|---|---|---|
| 신규개발팀 | 승인된 신규 제품 개발, 사업 기회 조사, 시제품 검증 | 아이디어와 근거, 대안, 구현·검증 결과 |
| 제품개선팀 | 기존 제품 UI·기능·템플릿·성능 개선, 고객 불편 검토 | 변경 이유, 실제 미리보기, 효과와 남은 문제 |
| CS팀 | 문의 분류, 불편 수집, 처리 추적, 답변 준비 및 허용된 응대 | 해결 여부, 반복 문의, 개발·운영팀에 전달할 근거 |
| 서비스운영팀 | 고객 작업 실패·API 오류·지연 감시, 허용된 복구, 재발 관찰 | 고객 영향, 원인, 조치, 실제 회복 증거 |
| 품질검증팀 | 변경사항·주요 고객 흐름·산출물 검증, 결함 반려 | 통과·실패·미확인 범위, 검증 증거 |

- 운영 장애가 제품개선 과제를 계속 밀어내지 않도록 장애 대응과 계획된 개선의 담당·진행 상태를 분리한다.
- 팀별 실행 시각, 감시 주기, 처리 목표, 동시 작업 수, 비용 한도는 실측과 운영 설정으로 정한다. 이 문서에서 임의 확정하지 않는다.
- 스케줄러·감시 도구·실행 환경이 실제 연결되기 전에는 '매일 자동 운영 중'이라고 보고하지 않는다.

## 6. 아이디어와 개발 흐름

책임자는 지시를 분배하는 것에 그치지 않고 사용자 문제·운영 근거를 바탕으로 더 나은 제품 방향을 제안한다.

1. 문제와 목표: 사용 흐름·고객 불편·관련 근거를 확인한다.
2. 방향 제안: 필요한 대안을 비교하고 추천 이유·단점·검증 방법을 제시한다.
3. 설계: 실제로 비교할 수 있는 시안이나 대표 사례를 만든다.
4. 실행 계획: 작업, 담당, 의존 관계, 단계별 완료 조건을 정의한다.
5. 구현: 격리된 작업 공간에서 진행하고 결과와 변경 내역을 남긴다.
6. 독립 검수: 구현자의 보고에 의존하지 않고 기능·회귀·결과물을 확인한다.
7. 실제 사용 검증: 해당 기능을 실제 흐름으로 실행한다. 미확인 범위를 숨기지 않는다.
8. 배포·관찰: 기존 저장소 배포 절차와 권한을 따르고, 배포 후 결과까지 확인한다.

- 새 아이디어 목록과 승인된 실행 과제를 구분한다. 승인된 범위의 일상 판단을 매번 대표에게 되묻지 않는다.
- 검수 실패는 원인·근거·재검증 조건과 함께 해당 담당자에게 되돌린다.
- AI 간 합의는 품질의 증거가 아니다. 실제 사용 결과와 독립 검증을 우선한다.
- UI·템플릿을 바꿀 때 편집뿐 아니라 저장·재열기·최종 산출물까지 영향을 확인한다.

### 첫 대표 사례: 숏템메이커 장면꾸미기

사장님이 설명한 진행 과제는 장면꾸미기 UI 변경과 템플릿의 간편한 적용이다. 현행 코드·트랙·진척은 착수 시 확인한다.

- 책임자: 현재 불편과 새로운 사용 방식의 대안을 제안한다.
- 실행 리더: UI·템플릿 구조·실제 적용 작업을 필요한 워커에 배정한다.
- 검수: 장면 선택·템플릿 적용·편집·저장·최종 렌더와 기존 기능을 확인한다.
- 대표 화면: 왜 이 방향인지, 어떤 시안인지, 누가 무엇을 검증했는지, 실제로 어디까지 됐는지를 보여준다.

## 7. 운영·장애 대응 흐름

감지 → 사건 접수 → 고객 영향과 근거 수집 → 원인 분석 → 허용된 복구 또는 개발 과제 → 실제 회복 확인 → 결과 보고·재발 방지.

- 동일 원인의 반복 실패는 관련 사건으로 묶고 영향을 추적한다.
- 사용량 제한·인증 문제·외부 서비스 장애·코드 오류를 구분한다. 증상만으로 계정 고장 등을 단정하지 않는다.
- 고객 작업 재실행은 중복 과금·중복 결과물·데이터 변경 여부를 확인해 처리한다.
- 재시도에는 한도·중단 조건·다음 담당자를 둔다. 무한 반복으로 해결된 것처럼 보이게 하지 않는다.
- 고객 응대·환불·유료 자원 변경·대체 서비스 사용·배포는 해당 업무에 이미 부여된 권한을 따른다. 새 권한이 필요한 조치는 근거와 실행안을 준비해 대표에게 올린다.
- 복구 완료에는 실제 작업 상태·서비스 응답·산출물 등 회복 증거가 필요하다.

## 8. 업무 기록과 대표 보고

모든 실행 업무에는 다음 정보를 남긴다.

- 업무 식별자, 소속 회사·제품·팀, 목표와 발생 원인.
- 책임자, 실행 담당, 검수 담당, 의존 작업과 다음 담당자.
- 현재 단계, 시작·갱신 시각, 최근 행동, 대기·실패 이유.
- 근거 자료, 결과물, 검증 결과, 사용량·비용의 출처와 집계 상태.
- 다음 행동, 대표 판단 필요 여부, 이미 부여된 권한의 범위.

대표는 전체 과정을 볼 수 있어야 하지만, 관찰이 매 단계의 승인 요구를 의미하지는 않는다.

| 보고 종류 | 내용 |
|---|---|
| 진행 보고 | 지금 하는 일, 완료된 단계, 막힌 이유, 다음 행동 |
| 판단 요청 | 결정할 사안, 근거, 선택지와 영향, 책임자 추천 |
| 결과 보고 | 바뀐 점, 실제 실행·검증 증거, 남은 위험·미확인 사항 |
| 일일 운영 보고 | 처리한 문제, 진행 중 개발·개선, 미해결 사항, 비용, 다음 업무 |

## 9. 회사 지도·UX 원칙

- 미래지향적이고 센스 있는 경험으로 실제 AI 개발·운영이 돌아가는 모습을 보여준다.
- 사장님은 만화·게임 같은 사무실 표현과 지나치게 딱딱한 관리 화면 모두를 원하지 않았다. 최종 시각 디자인은 아직 확정하지 않았다.
- 회사 → 팀 → 프로젝트 → 책임자·워커 → 실제 결과물을 따라볼 수 있어야 한다.
- 움직임은 배정·실행·인계·검수·완료 등 실제 사건에 연결한다. 대기·오류·미연결·관측 지연을 숨기지 않는다.
- 설계된 역할과 실제 실행 중인 직원을 구분한다. 시안·예시 데이터는 명시한다.
- 공개 시연은 공개 가능한 실행 기록과 결과물만 사용한다. 내부 고객 자료·개인정보·비밀정보는 노출하지 않는다.
- 실행 상태와 결과를 저장해 회사의 하루와 개별 작업을 나중에 따라갈 수 있도록 설계한다.

## 10. 매출과 운영 성과

- 회사별 실제 매출원과 비용 구조를 확인하고 설정한다. 가정한 구독·광고·외주 수익을 현재 사실로 표시하지 않는다.
- 매출·입금·비용·이익을 구분하고 기간·통화·집계 기준·출처·갱신 시각을 표시한다.
- 데이터 미연결은 0으로 표시하지 않는다. 회사 간 거래의 중복 합산을 방지한다.
- 금액 계산은 명시된 계산식과 코드로 수행한다. AI는 자료 분류·해석·개선 제안을 돕는다.
- 프로그램·업무·담당팀을 실적 근거와 연결한다. 근거 없는 'AI 직원의 매출 기여액'이나 수익 보장은 만들지 않는다.

## 11. 계속 갱신하는 방법

1. 새 결정이나 운영 교훈이 나오면 관련 조항을 먼저 찾는다.
2. 합의된 원칙은 해당 조항에 반영한다. 아직 결정되지 않은 제안은 아래 미결 목록에 둔다.
3. 날짜·수정 항목·이유·근거를 변경 이력에 남긴다. 폐기한 원칙은 현재 규칙과 함께 적용되지 않게 정리한다.
4. 실행 보고나 사건별 긴 기록은 각 작업 기록에 남기고, 이 문서에는 재사용할 원칙만 반영한다.
5. 새 세션에서는 이 문서와 관련 핸드오프를 읽은 뒤 현재 코드·서비스 상태를 다시 확인한다.
