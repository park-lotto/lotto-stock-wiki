## 1. 문제

한 PC에서 6개 Claude 세션이 **같은 폴더·같은 `.git`·같은 인덱스**로 같은 앱을 개발한다.

**흡수(absorption)**: 파일이 디스크에 하나뿐이라, 먼저 커밋하는 세션이 **다른 세션의 미완성 코드까지** 자기 커밋에 담는다. 그리고 `post-commit`이 무조건 `git push` → 3분 뒤 라이브. **반쪽짜리 코드가 그대로 서버로 나간다.**

## 2. 폐기: 락 / 신호등 (선행 설계의 페이즈2)

선행 설계 §4.2는 `tools/safe_commit.py`의 파일 락으로 `add`~`commit` 구간을 직렬화해 흡수를 막으려 했다. **이 접근은 원리적으로 작동하지 않는다.**

```
옆 세션이 app.py를 반쯤 고쳐놓음 (미커밋)
  → 내가 락 획득 ("커밋합니다, 대기")
  → 옆 세션 멈춤
  → git add app.py
  → ★ 디스크의 app.py에는 옆 세션의 반쪽 코드가 이미 들어 있다
  → 그대로 커밋·push·라이브
```

락은 **"언제 커밋하나"**만 조율한다. **"파일 안에 무엇이 들어 있나"**를 바꾸지 못한다. 사용자가 제안한 "커밋 전 신호등"도 같은 이유로 무력하다.

> **결론**: 흡수의 기전은 **타이밍이 아니라 공유 파일**이다. 폴더를 나누면 락이 불필요해지고, 폴더를 안 나누면 락이 무력하다. → `track.py`(claim/list) · `commit-msg` 훅 · `safe_commit.py` 계획 **전부 폐기**.

## 3. 해법

1. **트랙마다 자기 폴더** (`git worktree`) + 자기 브랜치 → 흡수가 **물리적으로 불가능**
2. **태스크 단위로 main 병합** (하루 이상 끌지 않는다)
3. **병합 게이트**: 병합 결과가 import·테스트를 통과해야만 커밋 → 라이브
4. 사용자 명령은 둘: `트랙 시작` / `트랙 끝`

---

## 4. 왜 게이트가 세트인가 (폴더 분리만 하면 반쪽)

폴더 분리는 흡수를 없애는 대신 **의미적 충돌(semantic conflict)을 키운다.**

```
A 트랙: app.py의 함수 이름을 바꿈
B 트랙: (며칠 전 버전을 보고) 그 함수를 부르는 새 코드를 씀
  → 텍스트가 안 겹치니 git이 충돌 없이 깨끗하게 병합
  → main이 ImportError
  → 병합 = 즉시 push = 3분 뒤 서버 다운
```

지금은 공유트리라 B가 A의 변경을 **즉시 보면서** 작업한다(원치 않는 통합이지만 어긋남은 안 쌓인다). 분리하면 B는 **옛 버전을 며칠 보고** 작업하므로 어긋남이 누적된다.

선례: memory `feedback_origin_main_broken_by_half_commit` — 반쪽 커밋으로 origin ImportError, 서버가 dirty로 옛 커밋에 정체돼 있어 안 터지다가 force-deploy가 노출시킴.

**게이트 없이 폴더만 나누면 사고 하나를 없애고 다른 사고를 키운다.**

## 5. 실측된 제약 (설계를 좌우함)

### 5.1 ★ `post-commit`이 게이트를 무력화한다

```sh
$ cat .git/hooks/post-commit
#!/bin/sh
git push
```

**병합도 커밋이다.** 순진하게 `git merge track/X` 하면:

```
merge → 커밋 생성 → post-commit 발동 → git push → 서버 3분 뒤 pull
                                          ↑ 게이트는 아직 돌지도 않았다
```

**게이트가 통과하기 전에 이미 라이브다.** 게이트가 존재할 이유가 사라진다.

→ **해법**: `git merge --no-ff --no-commit`으로 **커밋 없이 병합만** 한다. 워킹트리·인덱스에는 병합 결과가 들어오지만 커밋이 없으니 훅이 안 돈다. 게이트를 그 상태에서 돌리고, **통과해야만 `git commit`**(그때 훅이 push).

```
git merge --no-ff --no-commit track/X   # 커밋 없음 → 훅 안 돎
  → 게이트(import + pytest)
  → 통과: git commit          → post-commit이 push → 배포
  → 실패: git merge --abort   → 원상복구, 라이브 무사
```

### 5.2 `core.hooksPath`는 절대 건드리지 않는다

```sh
$ git config core.hooksPath
C:\Users\TheRose\Desktop\로또의 주식\.git\hooks    # 절대경로로 이미 박혀 있음
```

여기엔 CRLF 재정규화 `pre-commit`(2026-07-09 사고 대응)과 위 `post-commit`이 산다. 경로를 바꾸면 **둘 다 조용히 죽어** CRLF phantom-modified 사고와 배포 정지가 동시에 재발한다.

### 5.3 브랜치·배포

- git은 **같은 브랜치를 두 워크트리에 체크아웃하지 못한다** → 트랙마다 `track/<이름>` 브랜치 필수.
- 서버는 `main`만 추적한다 → **병합해야 배포된다.** 작업 중엔 라이브 반영이 없다(§8 감수사항).
- 트랙 브랜치에서 커밋하면 `post-commit`이 그 브랜치를 origin에 push한다. **무해하다** — 서버는 안 보고, 백업 효과만 있다.

### 5.4 디스크·DB

- `.git`은 **2.1GB이고 워크트리끼리 공유**한다. 폴더당 추가 비용은 체크아웃뿐.
- **이미 워크트리 3개를 쓰고 있다**(`git worktree list`로 확인) — 새로운 방식이 아니다.
- `shopping_shorts/data/`는 **gitignore** → 새 폴더는 **빈 DB로 시작**한다. 로컬 확인이 필요한 트랙은 DB를 복사해 오거나 서버에서 확인해야 한다(§8).
- 크롤봇은 **원본 폴더의 `raw/`에만** 쓴다. 트랙 폴더의 `raw/`는 stale — 코드 트랙엔 무관.

## 6. 명령 (사용자가 배울 것은 이 둘뿐)

### `트랙 시작 <이름>`
```
py tools/track.py start 보이스
```
1. `main`을 최신화(`fetch`)
2. `git worktree add ../lotto-보이스 -b track/보이스 origin/main`
3. 안내 출력: 그 폴더에서 Claude Code를 열라고

### `트랙 끝 <이름>`
```
py tools/track.py finish 보이스
```
1. 트랙 폴더가 **clean인지 확인** — dirty면 중단(커밋 먼저 하라고 안내)
2. 원본 폴더(`main` 워크트리)에서 `git fetch && git merge --ff-only origin/main`
3. **`git merge --no-ff --no-commit track/보이스`**
   - 충돌 → 중단하고 사람에게 보고(어느 파일인지). 사람이 해결 후 재실행.
4. **게이트 실행**(§7)
5. 통과 → `git commit` (post-commit이 push → 3분 뒤 배포) → `git worktree remove` + 브랜치 삭제
6. 실패 → `git merge --abort` → **게이트 출력을 그대로 보여주고 중단.** 라이브는 무사.

### `트랙 목록`
```
py tools/track.py list
```
`git worktree list` + 각 트랙 브랜치가 main보다 몇 커밋 앞섰는지(= 얼마나 오래 안 합쳤는지) 경고.

## 7. 게이트 (`tools/merge_gate.py`)

병합된 워킹트리 상태에서 순서대로 실행. **하나라도 실패하면 전체 실패.**

1. `python -m compileall shopping_shorts -q` — 문법
2. `python -c "import shopping_shorts.app"` — **import 체인**(의미적 충돌의 주 검출기)
3. `python -m pytest shopping_shorts/tests -q` — 테스트

> **기준선 문제**: 현재 전체 pytest에 **25 failed**가 있다(모션효과 트랙이 관측·인과로 자기 탓 아님은 증명, 원래 깨져 있었는지는 미확인). 게이트가 "전부 green"을 요구하면 **모든 병합이 막힌다.**
>
> → **기준선 방식**: 게이트는 "**병합 전보다 실패가 늘지 않았는가**"를 본다. 병합 전 실패 목록을 먼저 수집하고, 병합 후와 비교해 **새로 깨진 테스트가 있으면 실패**. 기존 실패는 통과시키되 로그에 남긴다.
> 25 failed의 정체는 별도로 규명해야 한다(이 설계의 범위 밖, 후속).

## 8. 감수사항 (정직하게)

1. **작업 중 라이브 테스트 불가.** 병합해야 서버에 올라간다. 보이스(작업대 귀 튜닝)·장면라이브러리(서버 ffmpeg)처럼 서버 grounding이 필수인 트랙은 **더 자주 병합**해야 한다.
2. **병합 충돌이 사람 손을 부른다.** 두 트랙이 같은 줄을 고치면 git이 멈춰 세운다. 번거롭지만 **보인다** — 지금은 조용히 덮여서 라이브로 나간다.
3. **새 폴더는 빈 DB.** 로컬에서 데이터가 필요한 트랙은 준비가 필요하다.
4. **오래 끌면 위험.** '끝나면 병합'의 '끝'이 3일이면 divergence가 폭발한다. `트랙 목록`의 경고가 이걸 감시한다.

4단계 전까지는 기존 방식이 그대로 돈다. **되돌리기 쉽다** — 워크트리를 지우고 원래대로 쓰면 된다.

## 10. 에러 처리

- **트랙 폴더 dirty** → 중단. `git status` 출력을 그대로 보여주고 "커밋 먼저" 안내.
- **병합 충돌** → 중단. 충돌 파일 목록 + `git merge --abort` 안내. 자동 해결 금지(사람 판단).
- **게이트 실패** → `git merge --abort` + 실패한 단계와 출력 전문. **부분 병합 상태로 두지 않는다.**
- **원본 폴더가 dirty** → `raw/`·`data/` 등 봇 산출물이면 무시하고 진행, 코드 파일이면 중단·보고.
- **워크트리 이미 존재** → 중단, 기존 폴더 경로 안내(덮어쓰지 않는다).

## 11. 테스트

- `track.py start` — 폴더·브랜치 생성, 중복 시작 거부, 이름 검증
- `track.py finish` — dirty 거부 / 충돌 시 abort / **게이트 실패 시 커밋이 안 생기는지**(이 설계의 심장) / 성공 시 커밋 생성
- `merge_gate.py` — 기준선 대비 신규 실패 검출, 기존 실패는 통과, import 실패 검출
- **실전 grounding**: 실제 트랙 하나로 시작→커밋→끝을 돌려 `git log`에 병합 커밋이 생기고 서버에 반영되는지 확인. 그리고 **일부러 ImportError를 넣고 게이트가 막는지** 확인(합성 테스트만으로 완료 처리하지 않는다 — memory `feedback_verify_with_real_data`).
