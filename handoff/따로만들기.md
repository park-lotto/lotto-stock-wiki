## ★실측으로 확정된 것 (추측 금지 — 여기서 두 번 틀렸다)

### 1. "따로 만들기"가 작업을 안 만들던 진짜 원인 (라이브 DB로 확정)
클론 job 3개는 **정상**이었다(각자 다른 edit_plan = A/B/C안, 각자 job_id).
문제는 `produce_works` 3행이 전부 `step=0` · `title=원본대본`이었고,
**저장 시각(15:49)이 클론 시각(15:29)보다 20분 늦었다** = 클릭 때가 아니라
**새로고침 뒤에 덮어써진 것**.

뿌리: `/produce` 새로고침 → `_bootAccountLatestOrLocal` → `_consumeProduceHandoff`
(sessionStorage 경로)가 **`cur`(단계)도 `MIX_JOB`도 복원하지 않는다**(handoff·script·
work_id만). 그 상태로 끝의 `saveWork()`가 `step:0`을 서버의 멀쩡한 값 위에 덮었다.
→ 고침: ① 복원만 했으면 저장 안 함 ② work_id를 알면 서버 레코드를 이어받음(`_restoreWork`)

⚠️ **오진 이력**: 처음엔 `_restoreWork`의 `stepLocked(cur)` 되감기를 의심해 테스트를
   썼는데 **이미 통과**했다. 서버 경로(`?work=`)는 멀쩡했고 범인은 로컬 경로였다.

### 2. 채널명이 안 바뀌는 이유 = 이름이 빈 게 아니라 **기록 자체가 없음**
```
아카이브 518채널 / reel_history에 있음 434 / 그중 이름있음 433
이름 없는 85채널 중 84개가 archive_state=done → 재크롤 대상에서 영구 제외
```
`pick_targets`가 `− done − gone` 차집합이라 done은 다시 안 긁는다.
→ `52ead6f20`으로 **앞으로 크롤하는 채널**은 해결. 옛 84채널은 별도 작업 필요(아래 ⏭).

커버리지(카드 기준, 채널 기준 아님):
| 기준 | 한글로 뜨는 비율 |
|---|---|
| 전체 릴스 78,265 | 68% |
| 조회수순 첫 화면 60장 | 68% |
| **댓글순(기본 정렬) 60장** | **80%** |

### 3. ⏱ 길이가 안 채워지던 이유
`duration_backfill._targets()`가 **`last_run`(랭킹 화면)만** 훑어서 아카이브는
**영원히 대상이 아니었다**. 78,265건 중 길이 아는 205건은 랭킹에 우연히 겹친 것뿐.
→ 아카이브를 대상에 추가(조회수 DESC 상위 `ARCHIVE_SCAN_LIMIT=600`).
회당 40건·성공률 54%라 상위 카드부터 서서히 채워진다.

### 4. 자동배포는 폴링이다
크론 `*/1`(오늘 3분→1분). SSH로 즉시 찔러도 **고객 접속 중·제작 작업 중이면 어차피
재시작을 미루므로**(auto_deploy.sh 설계) 주기만 줄이는 게 맞다.
정적파일(html·js·css)은 `FileResponse`/`StaticFiles`가 요청마다 디스크를 읽어
**재시작 없이 즉시** 반영된다(app.py:8619). 파이썬 코드만 재시작을 기다린다.

## 검증 방식 메모 (이 트랙에서 효과 본 것)

**문자열 검사만으로는 못 잡는다** — 실제로 두 번 잡혔다:
- `"_pushWork()" in body`는 통과하는데 런타임에선 `STATE.script`가 안 바뀌었다
  (슬라이스 안 `let CAND_LIST`가 `global.CAND_LIST`를 섀도잉 → `.find()`가 undefined)
- 그래서 **카드 템플릿을 node로 실제 렌더**해 확인하는 패턴을 썼다
  (`test_scene_first_ui_js.py` 슬라이스 드라이버 방식)
- 신규 테스트는 **반드시 옛 코드에서 실패하는지 확인**(`git stash` / `git show HEAD:파일`).
  안 하면 가짜 green이다.

⚠️ `finish` 게이트는 이 트랙 내내 **pytest를 건너뛰었다**(numpy 미설치, rc=2).
   "게이트 통과"는 테스트가 돌았다는 뜻이 아니다 — 관련 스위트를 직접 돌릴 것.
