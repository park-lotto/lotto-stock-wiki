# 영상제작소 — 대본·영상믹스 단계 통합 설계

날짜: 2026-07-15
대상: `shopping_shorts/static/produce.html` (+ 저장 다리용 `app.py` 라우트 1개)
라이브: https://shoppingshorts.duckdns.org (systemd `shopping-shorts`)

---

## 1. 문제 (Why)

지금 영상제작소는 8단계 마법사 `대본 → 영상 → 자막제거 → TTS → 꾸미기 → 썸네일 → SEO → 최종검수`인데,
**1단계(대본)와 2단계(영상믹스)가 개념적으로 분리**돼 있어 "대본 뽑는 곳"과 "영상 믹스하는 곳"이
따로 노는 느낌이다. 실사용은 늘 이어져 있다:

- **케이스 A (대부분)**: 영상 2개 → 1번에서 대본 뽑고, 1+2번을 화면으로 믹스
- **케이스 B**: 영상 1개 → 그 영상에서 대본 뽑고, 그 1개를 여러 믹스효과로 다른 영상처럼 변형

넘어온 영상은 결국 **대본 소스이자 화면 소스**다. 어떤 걸 대본으로 쓸지·화면으로 쓸지는
그때그때 보고 정한다. 지금의 "영상마다 📝대본용/🎬화면용 역할을 미리 배정"은 이 유연함을 막는다.

## 2. 목표 (What)

넘어온 영상들을 **재료 풀(pool)**로 보고, 한 화면에서:
1. 풀에서 **대본 뽑을 영상**을 골라(기본 후보=1번, 강제 아님) 대본 추출·생성·확정
2. 같은 풀에서 **화면에 쓸 영상**을 담아(1개 단독 변형도, 여러 개 믹스도) 확정 대본에 맞춰 렌더

대본 뽑기는 단순 텍스트 추출이 아니라 **대본 즐겨찾기(도서관)의 기능 전체**
(구조분석 표시 + 요소별 유지/변형 생성 + 초안 편집·재생성·버전이력)를 그대로 쓴다.

## 3. 두 경로, 하나의 대본 엔진 (핵심 아키텍처)

레퍼런스 내부 페이지(유튜브/틱톡/인스타 등)에서 대본을 확보하는 경로는 둘이고, **대본 생성/디벨롭
로직은 동일한 공용 엔진**(`script_generate` + `/api/wiki/*` 라우트 + 도서관 생성 모달)이다.

| 경로 | 목적 | 위키 저장 | 학습 반영 |
|------|------|-----------|-----------|
| 레퍼런스 → **대본 즐겨찾기(도서관)** | 자산 축적·학습 | 항상 | O (element_stats) |
| 레퍼런스 → **영상제작소 직행** | 바로 제작 | 선택(다리) | 저장 시에만 O |

→ **직행이어도 "⭐ 위키에도 저장" 버튼 하나**로 학습에 반영할 수 있게 다리를 둔다(사장님 결정).
제작 중 발견한 좋은 구조를 학습에서 놓치지 않기 위함.

## 4. 학습 파이프라인 — 현황 점검 결과 (2026-07-15 검증)

**매일 자동 반영이 실제로 돌고 있음 — 정상.**
- 크론: 서버 `0 4 * * *` → `shopping_shorts.daily_batch` (`/tmp/shopping_shorts_daily_batch.log`), 매일 04:00 실행 확인.
- `daily_batch.run()` = `backfill_structures`(구조분석 채움) + `recompute_element_stats`(카테고리×요소 클러스터링).
- 서버 `reference.db` 실측: `script_extracts` 45건(category 32·구조 34), `element_category_stats` **81행**
  (가전9·레시피26·생활용품28·인테리어18) — 학습 데이터 실제 축적됨.
- `wiki/save` 시 `_relearn_category`(BackgroundTask)로 **저장 즉시 그 카테고리 재학습**(크론 안 기다림)도 이미 있음.

**단 하나의 누수**: `script_extracts.category`가 **NULL인 13건**은 `distinct_extract_categories()`에
안 잡혀 학습에 반영 안 됨. → 이번 저장 다리에서 **category를 반드시 실어** 누수를 막는다(아래 6.3).

## 5. UI 설계 — B안(좌 영상풀 · 우 결과) + 도서관 모달 재사용

### 5.1 단계 구조 변경

`STEPS`를 `["대본","영상",...]` → **`["제작소","자막제거","TTS","꾸미기","썸네일","SEO","최종검수"]`**
로 바꾼다. 기존 step0(대본)·step1(영상)의 두 패널을 **하나의 "제작소" 패널(step0)로 병합**.
뒤 단계(자막제거~최종검수)는 dataset step 번호만 1씩 당겨 그대로 유지. **기능·백엔드 무변경.**

### 5.2 제작소 패널 = 좌우 2단

```
┌─ ① 제작소 ────────────────────────────────────────────┐
│  ◀ 영상 풀(넘어온 영상)         │  결과 ▶              │
│  ┌───────────┐ ┌───────────┐   │  ✅ 확정 대본          │
│  │ 영상1 [▷] │ │ 영상2 [▷] │   │  "감자전 레시피…"     │
│  │ 📝뽑기    │ │ 📝뽑기    │   │  [✏️수정] [🧬조합]     │
│  │ 🎬담기 ✓  │ │ 🎬담기    │   │  [⭐위키에도 저장]     │
│  └───────────┘ └───────────┘   │  ─────────────────    │
│                                 │  🎬 화면 담김: 영상1   │
│  (URL 직접추가 입력칸)          │  (1개=순서편집/2+=믹스)│
└───────────────────────────────────────────────────────┘
                  ▼ 다음: 자막제거
```

- **왼쪽 = 영상 풀**: 넘어온 영상(HANDOFF)들을 세로 카드로. 각 카드에 `📝뽑기`, `🎬담기`(토글) 두 버튼.
  역할 드롭다운(script/footage) 제거 — 버튼 두 개가 곧 역할이고 **겸용 허용**(같은 영상 📝+🎬 동시 가능).
  기존 URL 직접입력칸(순서편집·믹스)도 이 왼쪽 하단에 유지.
- **오른쪽 = 결과**:
  - **확정 대본** 영역: 현재 STATE.script를 카드로. 수정/조합/재생성 진입 + `⭐ 위키에도 저장`.
  - **화면 담김** 영역: 🎬 담긴 영상 목록 + "1개=순서편집 / 2개+=믹스" 안내. 기존 2단계 `MIX_JOB` 실행 로직 재사용.

### 5.3 📝뽑기 = 도서관 생성 모달 재사용

`📝뽑기` 클릭 → **도서관(library.html)의 `gen-modal` 구조를 그대로 가진 모달**을 띄운다.
- 모달 안: 구조분석 요약 + 요소별 유지/변형(카테고리·랜덤) 토글 + 모드 A/B + `runGen`(초안 N개) +
  초안별 편집(textarea)·지시문 재생성(전체/부분)·버전이력. **= 도서관과 동일 UX.**
- 먼저 대본이 없으면 `/api/produce/extract_from_url`로 추출 → 그 대본을 "원본"으로 구조분석해 모달 채움.
- 초안 중 하나에서 **"이 대본 확정 →"** 누르면 모달 닫고 `STATE.script`에 반영, 오른쪽 결과에 표시.
- 여러 영상에서 각각 📝뽑기 가능 → 각 확정 후보를 오른쪽에서 교체/비교(마지막 확정이 STATE.script).
- 수동입력·제미니 직접생성 모드도 이 모달의 탭 또는 별도 진입으로 유지(기존 3모드 흡수).

**재사용 방식**: 도서관 모달의 HTML/JS(`openGen`/`runGen`/`refineDraft`/`toggleHistory`/`element_options`
로드 등)를 produce.html에 이식하되, 초안 카드에 **"확정" 버튼**을 더한다(도서관엔 복사만 있음).
백엔드(`/api/wiki/generate`,`/draft/refine`,`/draft/edit`,`/draft/history`,`/element_options`)는 그대로 호출.

## 6. 백엔드 변경 (최소)

### 6.1 신규: URL 기반 위키 저장 (다리)
현재 `/api/wiki/save`는 `load_last_run()`에 의존 → 즐겨찾기 경유로 제작소 직행한 영상은
last_run에 없어 저장 불가. **`/api/produce/save_to_wiki` 신설**:
- body: `{url, shortcode?, script_text, structure?, category?, name?}`
- 대본은 클라이언트가 확정한 `script_text`를 그대로 사용(재추출 안 함). 구조는 없으면 `analyze_structure`.
- 영상 영구보관(`_WIKI_MEDIA_DIR`)은 url로 `download_any` 1회(실패해도 대본·구조는 저장 — 기존과 동일).
- `store.save_to_wiki` + `save_extract_structure` + `_relearn_category`(BackgroundTask) 재사용.
- **category 필수 전달** → NULL 누수 방지(4장). 없으면 클라이언트가 영상 카테고리/사용자선택으로 채움.

### 6.2 `extract_from_url`에 category 전달 (선택적 개선)
`/api/produce/extract_from_url`의 `store.save_script(code, result)`가 category를 안 넘김 →
`save_script(code, result, category=body.get("category"))`로 보완(호출부가 category 알 때만).

### 6.3 그 외 백엔드
없음. 생성·디벨롭·믹스·렌더 라우트 전부 기존 것 재사용.

## 7. 컴포넌트 경계

| 단위 | 책임 | 의존 |
|------|------|------|
| 영상 풀(왼쪽) | HANDOFF 카드 렌더 + 📝/🎬 버튼 상태 | HANDOFF 배열, saveWork() |
| 대본 모달 | 구조분석+생성+디벨롭+확정 (도서관 이식) | /api/wiki/generate·draft·element_options, extract_from_url |
| 결과(오른쪽) | 확정 대본 표시 + ⭐위키저장 + 화면담김 목록 | STATE.script, /api/produce/save_to_wiki |
| 화면 믹스 | 담긴 영상 → MIX_JOB 실행(기존) | 기존 2단계 로직 그대로 |

각 단위는 독립적으로 이해·테스트 가능하게 유지. produce.html이 이미 크므로(1383줄) 대본 모달
이식 시 함수를 명확히 분리(도서관 것과 이름 충돌 없이).

## 8. 범위 밖 (YAGNI)

- 여러 확정 대본 "동시 보관·비교 그리드" — 마지막 확정만 STATE.script. 교체로 충분.
- 자막제거/TTS/꾸미기/썸네일/SEO 로직 변경 — 단계 번호만 당김, 내용 무변경.
- 도서관(library.html) 자체 변경 — 이번엔 제작소만. (모달 코드는 이식이지 공유 리팩터 아님)

## 9. 테스트 / 검증

- **단위**: `/api/produce/save_to_wiki` 신규 라우트 — url 저장 → wiki_list에 등장 + category로 element_stats 재학습 호출됨(스모크).
- **통합(실렌더 grounding)**: 라이브에서 실제 즐겨찾기 영상 2개 넘겨 → 영상1 📝뽑기(모달 생성·디벨롭·확정)
  → 영상1+2 🎬담기 → 다음 단계로 넘어가 실제 MIX_JOB 매칭까지 도달 확인. (격리 말고 실제 경로)
- **누수 확인**: ⭐위키저장 후 서버 `element_category_stats`에 그 카테고리 행 증가 확인.

## 10. 리스크

- produce.html 단일 파일 대공사(step 병합 + 모달 이식) → **중복 id/함수명 충돌**이 최대 위험
  (도서관과 produce에 같은 이름 함수 존재 가능). 이식 시 네임스페이스 분리 필수.
- 단계 번호 시프트(dataset step) 누락 시 뒤 단계 패널이 안 뜸 → 병합 후 전 단계 클릭 검증.
