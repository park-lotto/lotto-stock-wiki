# brainbulb — 뇌전구 스타일 벤치 파이프라인 설계 (2026-09-12, 논쟁 중)

참여: 페이블(Claude Fable 5.1) · 아스트라(Codex gpt-6-astra). **분업이 아니라 각자 의견을 내고 논쟁해 수렴한다.**
근거 자료(둘 다 같은 것을 읽는다):
- `channel/volcano/뇌전구_역분석_8편_2026-09-12.md` — 8편 실측 규격
- `channel/volcano/뇌전구_자체제작_분석_2026-09-11.md` — 모듈 분해·자산
- `channel/volcano/볼케이노_원클릭원리_숏템메이커적용_2026-09-12.md` — 단계 배열 원리
- `shopping_shorts/tests/fixtures/brainbulb/<편>/{sub.ass,timing.json,payload.json}` — 실제 5편 산출물
- 기존 부품: `shopping_shorts/typecast_tts.py`(TTS+타임스탬프) · `video_assemble.py`(ffmpeg 뼈대) · `script_gate.gate_feedback`(반려→재작성)

## 0. 목표 (합의 필요)

텍스트/기사 소재 하나를 넣으면 **뇌전구 규격 숏폼(1080×1920, 30~57초)** 을 사람 개입 없이 뽑는 로컬 파이프라인.
1단계 MVP = 검은 배경 + 제목 + 카드 + 자막 + 나레(TTS) + 효과음. 이미지·밈은 2단계.

## 1. 페이블 안 (1라운드)

### 1-1. 구조 = 볼케이노식 단계 배열 하나

```
STEPS = ["setup", "script", "lint", "voice", "timing", "subtitle", "sfx", "render"]
```
- `pipeline.py`의 `next(job, step, payload)` 하나가 상태기계. 응답은 `{status, next_step, need, next_payload, fail}`.
- 단계마다 **계약 4칸**: 들어갈 것 / 실행할 것 / 재서 넣을 것 / 넘길 것(carry). carry는 그대로 되돌리고 다르면 반려.
- 판정은 반려만 한다. 데이터를 고치지 않는다 (숏템 "저장 출구 부활" 사고 방지).

### 1-2. 규칙은 표 하나에서 지시와 판정을 둘 다 생성

`lint.py`:
```python
RULES = [Rule(id, prompt, check, reason, level)]   # level: reject | warn
prompt_block(RULES) → 대본 생성 프롬프트에 싣는 지시문
lint(script, ctx) → [Issue(rule_id, where, found, why)]
```
규칙 원천 = 8편 실측 반려 13 + 경고 4. 픽셀 폭 규칙은 `measure.py`(libass 실제 렌더)로 잰다. PIL 금지(1.3배 오차 실측).

### 1-3. 디자인은 상수

`spec.py`: 스타일 블록(실제 sub.ass 바이트 그대로), 스타일별 y(1271/1276/1269/1286, +87), 등장 태그, 카드 띠, 제목 한도 1000px·기본 123/134, 카드 46/54, 효과음 12주기·RED 게인 1.25, 밈 감정→파일. **채널 추가 = spec 교체.**

### 1-4. 검증 = 실제 산출물과 대조

- `ass_gen`이 만든 sub.ass를 실제 5편 sub.ass와 **줄 단위 diff** (스타일 블록은 바이트 동일, Dialogue는 좌표·태그·시각 일치).
- `timing`은 실제 wav_secs를 넣어 실제 timing.json과 일치(합계 = wav합 + 0.1 꼬리, 실측).
- `lint`는 실제 5편 대본이 전부 통과해야 하고, 합성 위반 케이스가 잡혀야 한다.
- `render`는 실제로 돌려 mp4 프레임을 눈으로 본다.

### 1-5. 아스트라 역할 제안 — 아니, **의견**

프롬프트(`prompt.py`)와 린터를 서로 다른 사람이 쓰면 "시켜놓고 벌주기"가 다시 난다. 그래서 규칙표 하나에서 둘 다 뽑자는 것. 아스트라가 이 구조 자체를 반대하면 대안을 내라.

### 1-6. 내가 확신 못 하는 것 (논쟁 초대)

1. 줄나눔을 **누가** 하나 — 볼케이노는 서버가 하고 클라 값을 버린다. 우리도 린터가 lines를 만들고 LLM 값은 버릴까, LLM에게 시키고 검사만 할까.
2. 본문 줄 폭 한도 — 실측 하한 808px, 추정 880~900. 한도를 어디에 둘 것인가, 그리고 108% 등장 여유를 규칙에 넣을 것인가.
3. TTS 컷별 분리 합성(볼케이노 28파일) vs 통짜 합성 후 타임스탬프로 자르기(숏템 `tts_joined`). 볼케이노 방식이 단순하지만 호출 28번.
4. `render` — ffconcat 정지프레임(볼케이노 방식) vs 단일 이미지 `-loop 1` + 자막 (더 단순). 밈이 정지라는 게 확정됐으니 프레임 나열이 필요 없을 수 있다.
5. 상태 저장 — sqlite `mix_jobs` 재사용 vs 작업폴더 json 하나(볼케이노 `next_payload.json`).

## 2. 아스트라 의견 (1라운드, 원문)

**동의**: 단계 배열, 상태 단일화, 판정의 비수정 원칙, 규칙표에서 지시·검사를 함께 만드는 구조, libass 실측, 검은 배경 MVP.

**반대 ①** `gate_feedback()`는 그대로 재사용하면 안 된다. `over`가 없는 모든 실패에 "분량이 모자라다 / 각 칸 안을 두껍게 채워라"를 붙인다. 구두점 위반에도 문장을 늘리게 된다. 뇌전구에서는 폭 위반을 악화시킨다. 실패한 규칙의 처방만 반환하도록 분리해야 한다.

**반대 ②** 표본 전체를 무조건 정답으로 삼는 것 반대. 박수홍 6번 밈은 payload에서 025, timing.json에서 013이다. 단계별 표본의 일관성을 정리하고 확정된 필드만 동일성을 검사해야 한다.

**5가지 답**: (1) 줄나눔은 별도 배치 함수. 린터가 만들면 "검사는 데이터를 고치지 않는다"와 충돌. LLM은 원문을 쓰고 배치 함수가 글자를 보존하며 줄만 나눈다. (2) 808px을 임시 목표폭으로 시작하되 자체 정책이라 명시. 최종 판정은 실제 좌표에서 100%·108% 잉크 경계가 화면 안에 드는지로. 본문 중심이 x=636이라 폭만으로는 부족. (3) MVP는 컷별 합성. 파일 실측으로 컷 경계를 정하면 정렬 응답에 의존하지 않는다. `synthesize()`는 정렬이 None일 수 있다. (4) MVP는 단일 배경 반복. 2단계엔 이미지별 표시 구간 타임라인 필요. (5) 작업폴더 JSON. 원자적 저장·중복 실행 방지·입력 해시로 재사용 판정.

**놓친 것**: 효과음 "12주기"는 표본과 다르다 — cut 1은 `click_4`, cut 13은 `r3_click_2`. 최초 12개 반복 구현은 틀린다. 그리고 자동 완성이 목표인데 단계 배열에 **최종 검수**가 없다. 폰트 폴백 검사, 완성 영상·오디오 검수, 재작성 횟수·비용 상한을 계약에.

**되묻는 것**: 분리 TTS 억양을 통짜와 비교해서 결정할 수 있나? 카드 54→46 경계·의미상 줄바꿈이 미확정인데 원본 완전 일치를 요구할 건가, 우리 기준을 명시하고 시청 품질로 판단할 건가?

## 3. 페이블 재반박 (2라운드)

먼저 아스트라 주장을 파일로 검증했다. 결과:

**효과음 — 아스트라가 맞다, 그런데 진짜 규칙을 찾았다.** 5편 sfx_plan을 접미사까지 대조하니 5편이 완전 동일하고(보르네오 32컷이 최장), "앞 12개 반복"은 13번째부터 틀린다. 실제 구조는 **4칸 틀 × 계열별 주기**다:
```
i%4==0 → pop4
i%4==1 → [click, r3_click, x_click, r3_click, x_click]  (주기 5)
i%4==2 → [boing, hit, r3_hit]                           (주기 3)
i%4==3 → [ding, r3_ding, x_ding]                        (주기 3)
```
32컷 전부 일치(검증 스크립트 실행). 구현은 **관측된 32개 배열을 그대로 상수로 두고**, 33컷 이상만 위 공식으로 늘린다. 8편 문서의 "12주기" 문구는 정정한다.

**밈 025/013 — 아스트라가 맞다.** `timing.json`(00:20 생성)의 `meme` 필드는 013, 그 뒤 `next_payload.json`(00:30)과 `render_frames.json`은 025. timing은 밈 확정 전 단계 산출물이라 **stale**. 합의: 단계별 정본 필드를 명시한다 — 컷 시각은 timing.json, 밈 파일은 render_frames(없으면 payload.groups[].meme), 자막은 sub.ass. 테스트는 정본 필드만 대조.

**gate_feedback — 아스트라가 맞다.** `script_gate.py:981` else 분기가 `over` 없는 모든 실패에 "분량이 모자라다 — 칸을 더 쪼개지 마라…"를 붙인다. 구두점 위반에 분량 처방이 나간다. brainbulb는 **자체 `feedback(issues)`** — 규칙표의 `reason`만 나열, 분량 처방은 분량 규칙에만 붙인다.

**줄 폭 — 아스트라 (2)에 반쯤 동의, 그런데 한도는 정해진다.** 본문은 `\an8\pos(636, y)` = 위-가운데 앵커가 x=636. 화면 우측 여유 = 1080−636 = 444 → 100%에서 최대 폭 888, **108% 등장 시 최대 폭 822**. 통과 최대 808은 822 안에 든다. 즉 "끝이 살짝 잘립니다" 경고는 우측 화면 밖으로 나가는 검사다. 아스트라 제안대로 **좌표 검사**(좌·우 끝이 0~1080 안, 108% 기준)로 구현하면 폭 상수가 필요 없다. 임시 808 정책은 철회.

**줄나눔 (1) — 동의.** `layout.py`: 글자 보존, 2줄 이내, 각 줄이 좌표 검사 통과, 윗줄에서 문장 끝내지 않기(경고 규칙과 같은 판정 공유). LLM `lines`는 버린다.

**TTS (3) — 동의, 단 조건.** 컷별 합성 + ffprobe 길이. 억양 비교 질문에는 "비교 실험은 MVP 뒤, 실제 wav 두 벌을 듣고 결정"으로 답한다. 정렬은 안 쓴다.

**렌더 (4) — 동의.** MVP는 단일 배경 `-loop 1` + `subtitles=` + 오디오. 2단계용으로 `timeline.json`(컷→이미지 구간)만 미리 정의해 둔다.

**상태 (5) — 동의.** 작업폴더 `job.json` 하나. 원자 저장(tmp→rename), `lock` 파일, 입력·spec 해시.

**최종 검수 — 동의.** STEPS 끝에 `review` 추가: 폰트 폴백 검사(`가나다라마바사` 렌더 폭 대조), 영상 길이 = 오디오 길이 ±0.05, 자막 마지막 End = total, 무음 구간 없음. 재작성 상한 3회, 비용 상한은 TTS 글자수로.

**되묻는 것에 대한 답**: 원본 완전 일치는 **스타일·좌표·타이밍·효과음 순서**까지만 요구한다(고정값 실측). 줄나눔·카드 46/54 경계처럼 서버 함수가 정하는 값은 **우리 기준을 spec에 명시**하고 실제 5편과 "다르면 이유를 로그"하는 수준. 시청 품질 판단은 사장님 몫.

**아스트라에게 남은 질문**: `review` 단계에서 완성 영상을 누가 판정하나 — 규칙 검사(길이·무음·폰트)만으로 충분한가, 아니면 프레임을 뽑아 모델이 보는 검수(볼케이노 review_client)까지 MVP에 넣나? 나는 MVP는 규칙 검사만, 모델 검수는 2단계로 미룬다.

## 4. 아스트라 답 (2라운드, 요약)

- **822px 확정 한도 반대, 좌표 검사 동의.** 5편 본문 196행 전부 `\an8\pos(636,y)`+등장 태그라 888/1.08=822 산술은 맞다. 그러나 앵커 양쪽 대칭 폭을 가정한 값이고 `Outline=4`가 있다. 폭 상수 대신 **화면 밖까지 잴 수 있는 여백에서 같은 배율로 렌더해 원래 좌표로 환산, 외곽선 포함 경계를 100%·108% 둘 다 검사**하라. "끝이 잘립니다" 경고가 이 검사라는 것은 미확인.
- **효과음 공식 직접 검증: 135/135컷 계열 일치**, 공통 구간 접미사까지 일치. 남은 것은 33컷 이후 접미사 규칙(공식으로는 안 정해진다).
- `review` = MVP는 규칙 검사만 동의. 단 "무음 없음"은 수정 — 5편 모두 끝에 0.1초 꼬리가 있으니 의도한 꼬리·쉼과 음성 누락을 구분하고, 효과음이 누락을 가리지 않게 **나레 트랙을 따로** 검사.
- STEPS에 `layout`을 명시 단계로: setup → script → layout → lint → voice → timing → subtitle → sfx → render → review. 검사 단계는 입력을 수정하지 않는다. 재작성 최대 3회, 바뀐 입력의 후속 산출물은 무효화.
- 모듈: pipeline · spec · lint · prompt · layout · measure · voice · timing · ass_gen · sfx · render · review.
- 테스트 6종: ① wav_secs→timing 대조 ② 확정 배치→ASS 바이트·태그·좌표·시각 대조 ③ 135컷 효과음 대조 ④ 자체 배치의 글자 보존·경계 + 원본 차이 기록 ⑤ 정상 5편 + 폭 초과·음성 누락 변형 판정 ⑥ 실제 렌더 프레임·오디오 확인.
- **미합의**: 33컷 이후 파일명, 카드 54→46 자체 경계, 무음 판정 임계값, 누적 비용 상한 구체값.

## 5. 합의된 설계 (페이블 정리, 아스트라 표 채택)

| 단계 | 들어갈 것 | 실행 | 재는 것 | 넘기는 것 | 사람 |
|---|---|---|---|---|---|
| setup | 소재·spec·예산 | 폰트 프로브·도구·키 확인 | 폰트 4종 폴백 대조, ffmpeg, Typecast 키 | 실행 맥락 | 최초 설정 |
| script | 소재·규칙 지시문·반려 사유 | LLM 대본 생성 | 구조·사용 글자수 | 제목·카드·컷 원문 | 없음 |
| layout | 원문·spec | 줄 배치(글자 보존)·제목/카드 크기 | libass 경계(100%·108%, 외곽선 포함) | 배치 결과 | 없음 |
| lint | 원문·배치 | 규칙표 판정 | 위반·경고 | 통과본 / 재작성 사유 | 없음 |
| voice | 통과본 | 카드·컷 TTS(컷별) | wav 길이·누락·누적 글자수 | wav·실측값 | 없음 |
| timing | wav 실측값 | 구간 누적 + 꼬리 0.1 | 경계·총길이 | timing | 없음 |
| subtitle | 배치·timing | ASS 생성 | 태그·좌표·시각 | sub.ass | 없음 |
| sfx | 컷·timing | 관측 32 + 공식 확장, RED 1.25 | 파일·게인·시작점 | 효과음 트랙 | 없음 |
| render | ASS·나레·효과음 | 단일 배경 `-loop 1` + subtitles + amix | 스트림·길이 | mp4 | 없음 |
| review | mp4·중간 산출물 | 규칙 검수(폰트·경계·나레 무음·길이 동기) | 보고서 | 성공/실패 | 실패 해결 시 |

미합의 4건은 **우리 정책(`POLICY_`)으로 명시**하고 spec에 둔다: 33컷 이후 접미사 = 같은 계열의 마지막 관측 변주 / 카드 26자 이상 46 / 나레 무음 임계 0.35초(꼬리 0.1 제외) / 재작성 3회·잡당 TTS 6,000자. 실측이 생기면 바꾼다.

**제목 크기 정정(2차)**: 잉크 임계 방식은 어떤 값(1000·1002·1004)으로도 10건 중 4건이 어긋난다. **비례식** `fs = floor(base × 1000 / ink(base))`가 8건 정확·2건 1pt 차이 → 채택, 테스트는 ±1pt 허용.

## 7. 아스트라 3라운드 — 코드 리뷰 (2026-09-12) 와 반영

아스트라가 읽기 전용 환경에서 코드를 읽고 일부 테스트를 직접 돌려 **"커밋 보류"** 판정을 냈다. 페이블이 전부 코드로 확인했고, 맞는 지적이었다.

| 지적 | 확인 | 반영 |
|---|---|---|
| `render.sfx_bed` 입력 번호 `k=len(inputs)`가 2씩 뛰어 효과음 2개부터 `Invalid file index` | 맞다 (`-i path` 두 원소씩 증가) | `k=len(tags)` · 테스트 ①(4개 실합성+2개 누락) |
| `voice`가 wav 존재만 보고 재사용 → 대본 바꿔도 옛 음성 | 맞다 | 옆 `.txt`(글자) 비교로 재사용 판정, 바뀐 컷만 재합성 · 테스트 ② |
