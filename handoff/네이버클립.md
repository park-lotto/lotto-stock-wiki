## 무엇을 왜 만들었나

핀터레스트 옆에 **🟩 네이버클립** 탭(관리자 전용)을 신설했다. 국내 숏폼이라 번역 없이
바로 참고한다. 사장님 목적은 **"뷰티에서 어떤 영상이 비슷하게 터지는지"** 보는 것.

수집 경로 — **무료·로그인/프록시/브라우저 전부 불필요, HTTP 2번이 전부**:

```
① 목록  s.search.naver.com/p/clip/4/api/tab/more
        ?query=<키워드>&ssc=tab.m_clip.all&start=N        ← 서명·쿠키 없이 200, 24건/페이지
② 상세  creatorhub-api.naver.com/api/v7.0/clipviewer/card
        ?seedMediaId=<32자 ID>&serviceType=CLIP&mediaType=VOD   ← 인증 없이 200
        → 정확한 조회수·좋아요·댓글·발행시각 + mp4 직링크(1080x1920까지)
```

---

## ⚠️ 다음 세션이 반드시 알아야 할 함정 5개

```
□ yt-dlp는 이 경로를 못 쓴다(Unsupported URL). yt-dlp가 아는 tv.naver.com/v/{clipNo}는
  옛 서비스고, 지금 클립은 clip.naver.com + 32자 mediaId 기반의 별개 서비스다.

□ 목록 API의 sort 파라미터는 넣어도 무시된다(rel/date/view/popular 전부 같은 순서
  = RELATED 고정). 인기순은 우리가 조회수로 정렬한다.

□ 파서는 썸네일 img를 앵커로 삼는다. data-media-id를 순서대로 세면 어긋난다 —
  실측 '뷰티' 1페이지: 속성 id 24개 중 2개는 vod 없는 껍데기라 상세가 통째로 빈다.

□ 1차 정렬은 목록의 반올림값('14.7만') 기준이라, 상세로 정확값(146,844)을 받은 뒤
  **다시 정렬**해야 한다. 안 하면 '인기순'이 거짓말이 된다.

□ mp4 URL에는 만료가 붙는다(hdnts=exp=...). 저장해 두고 나중에 받으면 실패한다 —
  받을 때 ②를 다시 부른다.
```

  수확이 23→6건으로 줄다가 신규 0으로 끝난다. **늘리려면 키워드를 쪼개야 한다.**

## 🔧 운영 메모 (헛짚기 방지)

**"아무것도 안 뜬다" 제보가 오면 순서대로 봐라:**

```
① 데이터가 있나 — 코드가 아니라 데이터가 0건일 수 있다.
   실사고 2026-08-30: 탭은 열렸는데(GET /api/reference 200) POST collect가
   **한 번도 안 눌린 상태**였다. 빈 목록이 정상 동작이었다.
   확인: sudo journalctl -u shopping-shorts | grep naverclip

② 데이터 저장 위치 = reference.db 의 **settings 테이블**, key = `last_run::naverclip`
   (last_run 테이블이 아니다 — 거긴 인스타 전용 id=1 한 줄뿐).
   확인:
     python3 -c "import sqlite3,json;c=sqlite3.connect('file:shopping_shorts/data/reference.db?mode=ro',uri=True);
     print(len(json.loads(c.execute(\"select value from settings where key='last_run::naverclip'\").fetchone()[0])['items']))"

③ 화면 기본 탭이 **48시간 히트작**이다. 수집분은 최근 몇 달치가 섞여 있어
   대부분 필터에 걸린다 — **역대 히트작**으로 바꿔서 봐야 다 보인다.

④ 프로세스가 옛 코드일 수 있다. auto_deploy가 **고객 접속 중이면 재시작을 미룬다**
   (MAX_DEFER_SEC=1800, 30분 넘으면 강제). 디스크 코드 ≠ 도는 코드.
   확인: systemctl show shopping-shorts -p ActiveEnterTimestamp
```
