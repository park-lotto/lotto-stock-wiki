# 실시간 시장 브리핑 피드(딸깍 대시보드 5번째 칸) — 설계

## 배경

`dashboard/market.html` 최상단은 코스피/코스닥 지수·수급, 글로벌 지표, 순위 4칸으로
구성돼 있다. 여기에 5번째 칸을 추가해, 일하다가 이것만 봐도 "지금 시장이 어떤
상태인지" 명확히 파악할 수 있는 실시간 이슈 브리핑 피드를 만든다. 사용자가 이번
기능에서 가장 신경 쓰는 부분("가장 신경써야하는 부분")이므로, 배관(파이프라인)보다
브리핑 텍스트의 명확성·신뢰도가 최우선이다.

## 목표

1. 일반 구독자가 전문용어 없이 읽어도 "지금 뭐가 어떻게 되고 있는지" 이해할 수
   있는 짧은 브리핑 항목을 실시간으로 쌓는다.
2. 근거 없는 뇌피셜(AI 환각)을 피한다 — 모든 브리핑은 실제 숫자(지수/수급 변화)나
   실제 뉴스/원자 근거에 기반해야 한다.
3. 기존 인프라(market_flow 데이터, news_feed, atoms.db)를 최대한 재사용해
   신규 리서치 파이프라인을 처음부터 새로 만들지 않는다.

## 아키텍처 — 3층 구조

```
[감지층]  market_flow 임계치 감시 (무료·즉시) ─┐
[수집층]  news_feed + 오늘 atoms.db 원자 스캔 ──┼─→ [종합층] Gemini 브리핑 카드 생성 ──→ [피드 저장] ──→ [API] ──→ [프론트 5번째 칸]
```

### 1. 감지층 — 임계치 기반 속보 (AI 비용 0)

기존 30초 주기 `_prewarm_worker`가 이미 `market_flow` 데이터를 갱신하고 있다.
같은 사이클에서 직전 스냅샷과 비교해 다음 임계치를 넘으면 즉시 "🔴 속보" 원시
이벤트를 하나 만든다(AI 호출 없음, 숫자만 비교):

- 코스피/코스�드 등락률이 직전 체크 대비 **1%p 이상** 움직임 (예: -0.5%→-1.8%)
- 외국인 또는 기관 **누적 순매수 부호가 전환**됨 (매도→매수 또는 반대)
- 프로그램 순매수가 직전 체크 대비 **500억원 이상** 변동

이 이벤트는 `{ts, type:"raw_alert", metric, from, to}` 형태로 큐에 쌓인다 —
아직 사람이 읽을 문장이 아니라 "종합층"의 입력 재료다.

**비교 기준선**: 메모리 변수(예: `_briefing_last_metrics`, `_last_good_mf`와 같은
프로세스-전역 dict 패턴)에 직전 체크의 지수 등락률/수급 부호/프로그램 순매수 값을
저장해두고 매 사이클마다 갱신한다. **서버 재시작 직후 첫 사이클은 비교 기준선이
없으므로 무조건 스킵**(값만 저장하고 알림은 발생시키지 않음) — 안 그러면 재시작 시
"0 → 현재값"이 전부 급변으로 오탐된다.

### 2. 수집층 — 기존 자산 재사용

- `news_feed`(20분 주기, 이미 있음): 상위 섹터 테마뉴스·종목뉴스
- `atoms.db` 오늘자 원자 중 `signal in (bullish,bearish,catalyst,risk)` 또는
  `asset_level='market'`인 것 — 텔레그램/리포트에서 이미 들어온 실시간 시황 코멘트
  (예: 태린이아빠류 채널의 "반도체 10일선 이탈, 비중 축소" 같은 실시간 판단)

신규 코드는 이 둘을 조회하는 짧은 헬퍼뿐, 크롤링/수집 로직은 전혀 새로 안 만든다.

### 3. 종합층 — Gemini 브리핑 카드 생성

**주기**: 독립된 두 트리거가 같은 종합층 함수를 호출한다.
1. 고정 타이머 — 12분마다 1회(속보가 없어도 뉴스/원자 흐름을 정기 점검)
2. 이벤트 트리거 — 감지층이 🔴속보를 큐에 넣는 순간 즉시 1회 추가 호출

두 트리거 모두 **직전 AI 호출로부터 60초 이내면 스킵**(쿨다운 공유) — 같은 순간
여러 임계치가 동시에 넘어도, 또는 고정 타이머와 이벤트 트리거가 겹쳐도 API 중복
호출 안 되게.

**입력**: 최근 감지층 이벤트(있으면) + 최근 수집층 뉴스/원자 몇 개 + 직전 브리핑
카드 1~2개(맥락 유지용, 같은 얘기 반복 안 하게).

**프롬프트 원칙**:
- 전문용어 최소화, 일반인이 이해하는 말투("외국인이 오전 내내 팔다가 정오부터
  매수로 돌아섬" O, "프로그램 델타 헷지 청산" X)
- 반드시 입력 데이터에 있는 사실만 — 추측성 원인 분석은 "~로 보임/추정" 명시
- 굵은 헤드라인 1줄(15자 내외) + 설명 1~2문장
- 새로 쓸 게 없으면(감지 이벤트도 없고 뉴스도 조용하면) 카드를 만들지 않는다
  (침묵도 정보다 — 매 12분마다 억지로 뭔가 쓰지 않음)

**모델**: 기존 `_summary_keys()` + `GEMINI_TEXT_MODELS`(`gemini-2.5-flash` 우선,
`gemini-3-flash-preview` 폴백) 그대로 재사용. 신규 API 키 불필요.

### 4. 저장 — `output/market_briefing.json`

`output/flow_history.json`과 같은 패턴(일별 append). **리셋 시점**: 그날 첫 폴링
사이클에서 저장된 `date`가 오늘과 다르면 `items`를 비우고 새로 시작 — 기존
`_flow_day` 로직과 동일한 규칙(자정이 아니라 "날짜가 바뀐 뒤 첫 폴링 시점"에
리셋되므로, 서버가 자정에 안 떠있어도 다음 폴링 때 정상 리셋됨):

```json
{
  "date": "2026-07-03",
  "items": [
    {"ts": "09:47", "severity": "red", "headline": "코스닥 급락 전환",
     "body": "코스닥이 오전 내내 완만하던 흐름에서 갑자기 -4%대로 밀렸습니다. 외국인 매도가 동시에 강해지고 있어요.",
     "kind": "ai_brief"},
    {"ts": "09:32", "severity": "gray", "headline": "외국인 순매도 전환",
     "body": null, "kind": "raw_alert"}
  ]
}
```

- `severity`: red(속보)/yellow(관찰)/gray(참고, AI 미처리 원시이벤트)
- `kind`: `raw_alert`(감지층 원시, body 없을 수 있음) / `ai_brief`(종합층 생성,
  headline+body 채워짐)
- 하루 최대 항목 수 캡(예: 200개) — 무한 누적 방지

### 5. API — `GET /api/market_briefing`

오늘자 `items`를 최신순으로 반환. 프론트가 30초 주기로 폴링(기존 `loadMarketFlow`
패턴과 동일 주기 재사용).

### 6. 프론트 — market.html 5번째 칸

- 최신 항목이 위, 아래로 스크롤 가능한 리스트
- 항목마다: 시각 + 심각도 아이콘(🔴/🟡/⚪) + 굵은 헤드라인 + 회색 설명 1~2줄
  (raw_alert처럼 body 없는 항목은 헤드라인만, 톤 낮춰서 작게 표시)
- 텍스트가 기본. 향후(이번 스펙 범위 밖) 미니 스파크라인·관련종목칩 추가 가능하도록
  항목 데이터 구조에 여지는 남겨두되, 이번엔 구현 안 함(YAGNI)

## 에러 처리

- Gemini 호출 실패/쿼터 소진 → 종합층 스킵, 감지층 raw_alert만 계속 쌓임(피드가
  완전히 멈추진 않음, 품질만 낮아짐)
- `news_feed`/`atoms.db` 조회 실패 → 해당 입력만 빈 배열로 취급, 종합층은 감지층
  이벤트만으로도 카드 생성 시도
- 파일 쓰기 실패(디스크 등) → 메모리에만 유지, 다음 폴링 때 재시도(기존
  `_last_good_mf` 패턴처럼 조용히 넘어감)

## 테스트

- 감지층 임계치 로직: 순수 함수로 분리해 유닛테스트(직전값·현재값 fixture로
  1%p/부호전환/500억 케이스 각각 검증)
- 저장소 일별 리셋 로직: 날짜 바뀌면 items 비워지는지 유닛테스트
- API 응답 형식: FastAPI TestClient로 `/api/market_briefing` 스키마 검증
- 프론트 렌더: 항목 배열 주면 DOM에 시간순으로 올바르게 그려지는지(자동화 테스트
  범위 밖이면 최소 브라우저 수동 확인)
- Gemini 호출 자체는 실제 API 의존이라 유닛테스트 대상 아님 — 프롬프트 입력 구성
  함수(뭘 모아서 프롬프트에 넣는지)까지만 테스트, 실제 생성 결과 검증은 수동
