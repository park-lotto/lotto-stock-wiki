# 내보내기캡컷

## 2026-09-02 — ★진짜 원인: 응답 상태를 안 봐서 에러 본문을 mp4로 저장했다

사장님 추가 제보: **"캡컷 가면 폴더만 있고 빈 통이래"** — 이 한마디로 원인이 갈렸다.

```js
const buf = await (await fetch(a.url)).arrayBuffer();   // ← 401·404여도 그냥 진행
```

`fetch`는 401·404에 **예외를 던지지 않는다.** 그래서 에러 본문(24바이트 JSON)을
`cut_00_0_hook.mp4`라는 이름으로 그대로 썼다. 캡컷은 그 파일을 읽지 못하니
**폴더는 있는데 빈 통**이 되고, 우리 화면엔 `✅ 캡컷으로 보냈어요`가 떴다.
69K짜리 00:00 프로젝트도 이걸로 설명된다 — draft JSON + 24바이트 쓰레기 수십 개.

실측: `curl /api/mix/capcut_asset/76665d680876/beat_00.mp3` → **401, 24바이트**.
(비로그인 curl이라 401 자체가 고객 원인이라고 단정하진 못한다. 게이트는 로그인 세션이
있으면 통과시킨다 — 세션 만료·디스크 정리로 인한 404도 같은 증상을 낸다.
어느 쪽이든 **조용히 성공이라 말하던 것**이 버그다.)

### 고친 것
- `res.ok` 검사 — 실패하면 그 자리에서 멈추고 **상태코드와 할 일**을 고객 말로 알린다
  (401 → "로그인이 풀렸습니다", 404 → "서버에서 재료가 사라졌습니다. 완성본을 다시 만들어 주세요")
- 2048바이트 미만이면 깨진 파일로 보고 중단 — 200인데 내용이 에러인 경우를 잡는다

### 검증(실브라우저, 4경로)
| 경우 | 결과 |
|---|---|
| 401 | `재료를 받지 못했습니다(c0.mp4, 서버응답 401 — 로그인이 풀렸습니다…)` + 중단, 쓰레기 파일 0개 |
| 404 | `…404 — 서버에서 이 재료가 사라졌습니다. 완성본을 다시 만들어 주세요` + 중단 |
| 200인데 24바이트 | `재료가 깨져서 왔습니다(c0.mp4, 24바이트)` + 중단 |
| 정상 | `✅ 다 보냈어요 (재료 6개)`, 파일 7개(JSON 1+재료 6) |

## 2026-09-02 — 캡컷 보내기 진행표시 추가

### 제보
고객: "캡컷으로 보내면 안된다" — 캡컷 프로젝트가 **69.0K / 00:00**(검은 썸네일).
정상 건은 20.3M / 00:17. 즉 **draft JSON만 들어가고 mp4·mp3가 안 들어간 상태**.

### 실측
- 서버 조립본은 정상: `mix_jobs/76665d680876/capcut/영양사 친구가…/`에
  beat_00~07.mp3 + cut_*.mp4 = 합 65MB, 2026-09-02 16:43 생성 (SSH 확인)
- 내 PC `C:\capcutproject\CapCut Drafts` 에는 오늘 만들어진 draft 0건 → 고객 PC 얘기가 맞음
- 코드(`produce.html` `sendToCapCut()`): JSON을 먼저 쓰고, 그 뒤 에셋 수십 개를
  한 개씩 fetch→write. **그 동안 화면에 아무 표시가 없었다.** 완료 alert만 맨 끝에.

### 한 것
`sendToCapCut()`에 진행표시·이탈방지 배선 (`produce.html`)
- `#btnCapCut` / `#ccProgress` 신설, 버튼은 진행 중 스피너+비활성
- `📤 영상 재료 보내는 중… 12 / 47` + 진행바 + "창 닫지 마세요" 안내
- `beforeunload`로 완료 전 이탈 경고
- **에셋 0개면 성공이라 하지 않고 중단**(작업번호까지 노출) — 빈 프로젝트 원인 후보 하나를 봉인
- 실패 시 "중간에 끊겼습니다" + 에러 원문을 화면에 남김
- `finally`의 `renderExport()`가 exportBox를 다시 그려 표시가 날아가므로 결과 문구를 복원

### 검증 (2026-09-02, 실제 크롬에서 실행)
로컬 `python -m http.server 8777`로 produce.html을 띄우고, `showDirectoryPicker`·`fetch`를
가짜로 바꿔(형태는 실제 File System Access API 그대로) `sendToCapCut()`을 **onclick과 같은
형태로** 호출해 관찰. `alert`은 스텁으로 막았다(진짜 alert이 뜨면 자동화가 통째로 멈춘다).

| 경로 | 결과 |
|---|---|
| 정상(재료 12개) | 진행바 0→92% 12스텝, 버튼 스피너+비활성, 쓴 파일 14개(JSON 2+재료 12), 완료 문구 `✅ 다 보냈어요 … (재료 12개)` |
| 재료 0개 | `❌ 보낼 영상 재료가 하나도 없습니다 — 관리자에게 알려주세요(작업번호 testjob123)` + 중단 |
| 5번째에서 끊김 | `❌ … 재료 12개 중 4개까지 갔습니다 …(네트워크 끊김)` — 실제로 4개 성공 후 실패, 숫자 일치 |
| beforeunload | 등록/해제 카운트 0 (누수 없음) |
| renderExport 재그리기 | 결과 문구가 살아남음(복원 로직 동작) |

⚠️ `test_dom_owner_budget`이 막았다 — #ccProgress를 3개 함수가, #btnCapCut을 2개가
덮어쓰는 모양이었다(정당한 가드다). `_ccState` 하나 + `_ccRender()` 하나로 모아 통과.
⚠️ 첫 테스트에서 **실패 문구에 진행 개수가 안 나오는** 결함을 잡아 고쳤다(`_ccDone`/`_ccTotal`을

⚠️ 아직 안 해본 것: **진짜 캡컷 폴더에 쓰기**(폴더 선택 권한은 사람 클릭이 필요).

### 함정 기록
`produce.html`은 **CRLF와 LF가 섞여 있다**(전체 CRLF 17,074줄인데 `sendToCapCut` 구간은 LF).
여러 줄 문자열로 치환할 때 개행을 확인하고 맞춰라.
또 Bash heredoc이 `\n`을 `\n`으로 줄여 파이썬 소스에 도달하므로, JS 소스의 리터럴 `\n`을
치환 대상으로 쓸 땐 `chr(92)+'n'`으로 조립해야 한다.
