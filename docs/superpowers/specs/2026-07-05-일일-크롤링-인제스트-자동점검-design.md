# 크롤링 인제스트 자동점검·자동수정 파이프라인 (v2) — 설계

## 배경

2026-07-05, 지난 세션(H)에서 텔레그램 news_relay 버그를 수정한 뒤 "오늘 인제스트 잘 됐는지"를
수동으로 확인하다가 실제 문제 2건을 발견했다:

1. `그로쓰리서치특징주` 채널 — raw 파일이 **로컬에 한 번도 존재한 적 없음**
2. `실시간주식뉴스` 채널 — 마지막 raw 파일이 **07-03에서 정체**(atoms.db엔 오늘 날짜로 원자가
   찍혀 있었지만, 이건 옛 07-03 파일을 오늘 재처리한 것일 뿐 새 콘텐츠가 아니었음 — `created_at`
   기준 신선도 판단은 착시를 일으킨다)

기존 `daily_verify.py`(2026-07-03 구축, v1)는 `telegram`/`news`/`report` **소스 단위 합계**로만
신선도를 보기 때문에, 22개 채널 중 하나가 완전히 죽어도 나머지가 정상이면 합계엔 안 잡힌다.
사용자는 "왜 이걸 내가 매일 수동으로 확인해야 하냐"며 완전 자동화를 요청했고, 브레인스토밍을
통해 다음을 확정했다: **채널 단위 탐지 + 코드 버그는 전부 자동수정 + 서버 배포까지 자동** —
단, 텔레그램 플랫폼 리드 제한처럼 코드로 원천적으로 못 고치는 문제는 사람에게 넘긴다.
또한 "문제 = 비즈니스가 막히는 것"이라는 원칙에 따라, 하루 1회 배치가 아니라 **인제스트
슬럿마다(5회/일) 즉시 감지→수정→배포**까지 트리거하는 실시간에 가까운 구조로 간다.

## 기존 자산

  stockbrain 서비스상태+텔레그램 보고. 크론 `45 21 * * *`.
- `pipeline/atoms/telegram_channels.json` — 22개 텔레그램 채널 레지스트리(type/trust/url).
  채널 단위 탐지의 유일하게 명확한 등록처.
- Windows 작업 스케줄러 `LottoStock_SlotIngest_Main`/`Report` — 08:10/12:10/15:10/18:10/21:10
  인제스트 슬럿.
- `scripts/sync_crawl_to_server.py` — SSH/SCP 패턴 참조(`KEY`, `HOST=ubuntu@3.39.179.148`).
- 원격 크롤러 코드 `/home/ubuntu/kmong/crawling_bot/`(이 git 레포와 무관한 별도 코드베이스,
  `crawlers/telegram_crawler.py`, `config.yaml`, `crawlingbot.service`).
- `claude -p` 로컬 헤드리스 호출(Max 구독, API 과금 없음) — `docs`의
  `2026-07-04-시황-브리핑-엔진-design.md`에서 검증된 패턴을 재사용.

## 범위 (v2)

**포함:**

1. **채널 단위 신선도 탐지** — `telegram_channels.json`의 22개 채널 각각에 대해
   `raw/telegram/{날짜}_{채널명}.md` 파일명의 날짜만으로 최신성 판단(atoms.db `created_at`
   사용 안 함 — 재처리로 인한 착시 방지). 판정 2종:
   - `never_synced`: raw 파일이 한 번도 없음 → 최고 심각도
   - `stale`: 최신 파일 날짜와 오늘의 gap이 임계치(채널별 `freshness_days`, 기본 2일) 초과.
     `telegram_channels.json`에 채널당 옵션 필드 `freshness_days`를 새로 추가(없으면 기본값
     2 적용) — 원래 게시 빈도가 낮은 채널(예: 주공고급수집)의 오탐을 줄이기 위함.
   - 뉴스/리포트/블로그/유튜브는 이번 범위 밖(기존 daily_verify의 소스단위 방식 유지 — 채널
     레지스트리 구조가 텔레그램만큼 명확하지 않음, YAGNI).

2. **슬럿마다 즉시 트리거** — 08:15/12:15/15:15/18:15/21:15(기존 인제스트 슬럿+5분)에
   `daily_ingest_autopilot.py --slot` 실행. 이상 없으면 조용히 종료(텔레 알림 없음, 로그만).
   이상이 있고 **오늘 이미 진단한 적 없는 채널**이면 아래 3~5단계 전체 트리거.

3. **2단계 진단→수정** (`claude -p`, 로컬 Max 구독):
   - **진단 전용 호출**(Edit 권한 없음): cwd=레포 루트. 원인이 로컬 코드(`pipeline/atoms/`)인지,
     원격 크롤러(`/home/ubuntu/kmong/crawling_bot/`, SSH로 로그·코드 열람)인지, 코드로 근본
     해결 불가능한지 구조화된 결과로 판정:
     `{root_cause, target: local|remote_crawler|unfixable, fix_plan, requires_destructive_action}`
   - **수정 호출**(Edit+Bash 권한, target에 따라 로컬 또는 SSH로 원격 파일까지): `unfixable`이거나
     `requires_destructive_action=true`면 여기서 멈추고 바로 5번(에스컬레이션)으로.
   - **폭주 방지 캡**: 수정 diff가 3개 파일 초과하면 자동커밋 취소, 에스컬레이션 처리.

4. **검증+배포**:
   - pytest 전체 스위트 통과 확인(기존 `run_pytest_check` 재사용). 실패 시 커밋 안 하고
     에스컬레이션.
   - `target=local`: git commit(`[autopilot-auto-fix]` 태그)+push. 수정된 파일이 정적
     allowlist(`server.py`, `dashboard/`)에 속할 때만 SSH `git pull`+`systemctl restart
     stockbrain`까지 진행 — 그 외 경로(예: `pipeline/atoms/` 순수 로컬 인제스트 스크립트)는
     커밋·push만 하고 서버 배포는 스킵.
   - `target=remote_crawler`: 덮어쓰기 전 원본 파일을 로컬에 백업 저장 → SCP로 수정본 전송 →
     `systemctl restart crawlingbot`.
   - 배포 후 헬스체크(`systemctl is-active`). 실패 시 자동 롤백(local=git revert+재배포,
     remote_crawler=백업 파일 재-SCP). 롤백 후에도 실패하면 즉시 사람 호출(최고 우선순위).
   - 모든 자동수정은 `wiki/log.md`에도 한 줄 자동 기록.

5. **미해결 항목 영속 추적 + 에스컬레이션**:
   - `pipeline/atoms/autopilot_state.json` — 날짜별 초기화 안 함. 각 이상 항목을
     `{channel, 최초감지일, 최근확인일, 상태: 자동수정완료|에스컬레이션, 미해결일수}`로 계속 누적.
   - 재진단(LLM 호출)은 이미 에스컬레이션된 채널에 대해 **하루 1회로 스로틀**(같은 문제로
     슬럿마다 5번 헛수고 안 함).
   - **보고는 다르다**: 슬럿 알림은 신규/상태변화만. **21:45 일일 요약에는 미해결
     에스컬레이션 항목을 매일 빠짐없이 포함**하고 미해결일수를 표시("그로쓰리서치특징주 —
     3일째 미해결"). raw 파일이 다시 나타나 자동 해소되면 "✅ 해결됨(N일만에)"로 한 번
     보고 후 목록에서 제거. 즉 문제는 자동으로 조용히 사라지지 않는다.

6. **텔레그램 리포트 2종**:
   - 슬럿 알림(이상 있을 때만): 어느 슬럿/채널/원인/조치결과(자동수정완료 또는 사람판단필요).
   - 21:45 일일 요약(기존 daily_verify 후신): pytest 전체회귀+서비스상태+오늘 슬럿별
     집계(감지/자동수정/에스컬레이션 건수)+미해결 에스컬레이션 리마인드.

7. 기존 `daily_verify.py`의 21:45 크론을 이 시스템의 일일 요약으로 교체.

**제외(v2 범위 밖, 명시적으로):**

- 파괴적 작업(데이터 삭제·DB 레코드 drop·force-push 등)의 자동수정 — LLM이 스스로 안전하다고
  판단해도 오케스트레이터 코드가 `requires_destructive_action` 플래그를 보고 무조건
  에스컬레이션시킨다. 이건 사용자 설정("모든 버그 자동수정")과 무관하게 고정된 하한선.
- 뉴스/리포트/블로그/유튜브의 채널단위 탐지(위 참조, 나중에 같은 패턴으로 확장 가능).
- 서버 자체 네트워크 장애 감지(v1과 동일한 이유로 원리적 불가 — 서버 안 체커는 서버가
  죽으면 아무것도 못 함).
- Claude Max 토큰이 로컬·원격에서 동시에 쓰이는 상황 자체는 이번 설계에 없음(진단·수정은
  로컬에서만 `claude -p` 호출, 서버는 SSH로 명령만 보냄) — `reference_claude_max_on_server`에서
  겪은 토큰 스테일 리스크가 애초에 발생하지 않는 구조.

## 아키텍처

```
[Windows Task Scheduler]
  08:15 / 12:15 / 15:15 / 18:15 / 21:15  → daily_ingest_autopilot.py --slot
  21:45                                   → daily_ingest_autopilot.py --daily-summary

daily_ingest_autopilot.py
  ├─ check_channel_freshness()       — 채널별 raw 파일명 날짜 기반 판정 (순수함수)
  ├─ load_state() / save_state()     — autopilot_state.json 영속 추적
  ├─ should_diagnose(channel, state) — 오늘 이미 에스컬레이션+미해결이면 스킵
  ├─ diagnose(channel)               — claude -p 진단 전용 호출 → JSON 파싱
  ├─ apply_fix(diagnosis)            — claude -p 수정 호출(로컬 or SSH) → diff 파일수 캡 체크
  ├─ run_pytest_check()              — 기존 daily_verify.py에서 재사용
  ├─ deploy(diagnosis)               — target별 분기(git 배포 or SCP+재시작)
  ├─ health_check(target)            — systemctl is-active
  ├─ rollback(target, backup)        — 실패시 자동 원복
  ├─ send_slot_alert(...)            — 텔레그램(이상 있을 때만)
  └─ send_daily_summary(...)         — 텔레그램(21:45, 미해결 리마인드 포함)
```

순수 판정 함수(신선도 계산, 캡 체크)와 부수효과(LLM 호출, git/SSH, 텔레그램 발송)를 분리해
유닛테스트 가능하게 한다 — v1과 같은 원칙.

## 안전장치 요약

| 장치 | 목적 |
|---|---|
| 진단/수정 2단계 분리 | 파괴적 작업 여부를 LLM 자율판단이 아니라 오케스트레이터 코드로 강제 차단 |
| diff 3파일 캡 | 대형 오작동/폭주 수정 방지 |
| pytest 게이트 | 회귀 없는 수정만 배포 |
| 배포 후 헬스체크+자동롤백 | 배포 실패가 서비스 다운으로 이어지지 않게 |
| 에스컬레이션 하루 1회 스로틀 | 같은 문제로 슬럿마다 5번 헛수고 방지 |
| 영속 상태 추적+일일요약 강제포함 | 미해결 문제가 조용히 묻히지 않게 |

## 에러 처리

- 개별 체크 함수 실패(예외) → "측정불가"로 표시, 전체 실행은 안 죽음(v1과 동일 원칙).
- `claude -p` 호출 실패/타임아웃 → 진단 실패로 간주, 그 슬럿은 에스컬레이션(사람 판단 필요)
  처리하고 다음 슬럿에서 재시도.
- SSH/SCP 실패 → 배포 실패로 간주, 커밋은 이미 됐어도 서버 미반영 상태로 텔레 보고(다음
  수동 배포 필요 명시).

## 테스트

- 채널 신선도 판정(`never_synced`/`stale`/정상) — 경계값 포함 유닛테스트, 파일명 파싱 fixture.
- `should_diagnose` 스로틀 로직 — 상태 파일 fixture로 스킵/재시도 조건 검증.
- diff 파일수 캡 체크 — mock diff로 통과/차단 경계 검증.
- 배포 분기(local/remote_crawler) — target별로 올바른 함수 호출되는지 mock.
- 롤백 로직 — 헬스체크 실패 시나리오에서 revert/백업복원 호출 확인.
- 일일요약 조립 — 미해결 항목 누적/일수 표시/해소시 제거 포맷 확인.
- `claude -p` 호출 자체는 실제 서브프로세스 mock으로(비용·비결정성 때문에 유닛테스트에서
  실호출 안 함), 통합검증은 배포 후 수동 1회(v1과 동일 원칙).
