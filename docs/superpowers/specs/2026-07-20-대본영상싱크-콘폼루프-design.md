# 대본·영상 싱크 — 콘폼(conform) 루프 설계 (2026-07-20)

> 작성: Fable 세션(설계 리뷰). 구현: Opus 세션에 인계.
> 트리거: **"믹스 싱크 콘폼루프 구현 이어서"**

## 0. 리뷰 결론 — "대본 먼저 vs 영상 먼저"는 가짜 이분법

사장님 딜레마: *대본 먼저 하면 영상이 안 맞고(얼림·슬로모), 영상 먼저 하면 대본이 이상하고.*

리뷰 판정: **어느 쪽도 마스터로 두지 않는다. 층을 나눈다.**

| 층 | 주인 | 이유 |
|---|---|---|
| **서사** (무슨 얘기, 훅→전개→CTA) | **대본** | 제미니가 자유롭게 잘 씀. 영상선행이면 클립 쪼개짐에 문장이 끌려가 "대본이 이상해진다"(사장님 직감이 맞음) |
| **시간** (각 문장 몇 초) | **영상** | 클립 실길이가 예산. 늘리면 슬로우크롤, 얼리면 멈춤 — 둘 다 이미 실측으로 기각됨 |
| **표면** (문장을 몇 자로 다듬나) | **콘폼 루프** | 뜻 유지한 채 길이만 재단. 제미니 리라이트 + 그 비트만 재TTS |

### 전면 영상선행(A안)을 기각한 근거 (코드 검증)

1. **영상 레버는 이미 끝까지 당겨져 있다.** `video_assemble.py:_plan_beat_clips`는
   primary+alternates를 **전부 소진한 뒤에야** 부족분을 슬로모/freeze로 채운다.
   "쓸 영상이 남았는데 얼린다"가 아니다 — 진짜로 영상이 모자란 것이다.
2. 부족분을 영상으로 더 채우는 두 경로는 둘 다 함정:
   - 매칭 구간 `[start,end]` 밖으로 확장 → **유출 버그 재발**("각 클립은 자기 구간을 절대 넘지
     않는다(유출 0)"는 다색 소스 실측 후 일부러 박은 가드다. P1, 2026-07-19)
   - 매칭 안 된 딴 영상 갖다 붙임 → 자막·화면 **맥락 붕괴**
3. A안은 produce 위저드 전면 개편(1단계=대본 확정이 UX의 축) + 대본 품질 하락 리스크.
   콘폼 루프는 기존 구조의 ~20% 변경으로 같은 싱크 품질에 도달한다.

### 왜 지금 구조에서 콘폼이 싸게 되나 (기반 검증됨)

- TTS가 **비트별 개별 mp3**(`mix_pipeline.py:_synthesize_beats` → `beat_N.mp3`)
  → 한 문장만 리라이트해 그 비트만 재합성하면 된다. 전체 재TTS 불필요.
- 말속도 실측 상수 존재: `edit_plan.py:_SYLLABLES_PER_SEC = 5.7`(음절/초, 성우 14명 실합성 측정)
  → "이 문장을 약 N초(≈N×5.7음절)로" 리라이트 목표를 정확히 줄 수 있다.
- 부족분 계산은 `_plan_beat_clips`가 이미 한다(`shortfall`).

## 1. 파이프라인 변경 (콘폼 루프)

기존: `대본 → 매칭 → TTS → [부족하면 슬로모 1.15배 + freeze]` ← 멈춤의 근원

변경: `대본 → 매칭 → TTS → **비트별 콘폼** → 조립`

각 비트에서 `budget = Σ(primary+alternates 구간 길이) × _MAX_SLOWMO`:

```
tts_dur ≤ budget          → 그대로 (지금도 문제없는 경우)
tts_dur >  budget          → ① 제미니 리라이트: "뜻·역할(훅/전개/CTA) 유지, 약 budget초
                               (≈budget×5.7음절)로 줄여 써라" (비트당 최대 1회)
                            ② 그 비트만 재TTS → 재측정
                            ③ 그래도 초과분 남으면: freeze는 최후수단, 비트당 ≤0.8s
                               (켄번즈 홀드 — 오늘 만든 _extend_with_frozen_motion 재사용)
마지막 비트 특례            → 대사 끝 + 1초 자연 여운(freeze 아니라 소스 실재 프레임이 남으면
                               그만큼 1배속 재생, 없으면 켄번즈 홀드 1초) — 사장님 아이디어
```

주의:
- 리라이트는 **표면만** 바꾼다(정보·순서·역할 유지). 자막 세그먼트(`_caption_segments`)는
  리라이트된 문장으로 다시 뽑는다.
- 편집안 화면(beats 목록)의 narration도 리라이트 반영 — 화면·소리·자막 3자 일치.
- 리라이트 실패(제미니 오류/길이 미달)면 조용히 ③으로 폴백. 렌더가 죽는 것보다 짧은 홀드가 낫다.
- `_MAX_SLOWMO=1.15`는 유지(자연 속도 보호). 콘폼이 제대로 돌면 freeze는 거의 안 나온다.

## 2. 구현 태스크 (Opus용)

- T1 **측정·리포트**: 비트별 `tts_dur` vs `budget` 계산을 `mix_pipeline`에 노출.
  편집안 API에 `sync_gap` 필드 → 화면의 "매칭 N/5" 옆에 근거 표시 가능.
- T2 **리라이트 함수**: `edit_plan.py`(또는 인접)에 `conform_narration(narration, target_sec)`
  — 제미니 호출, `_SYLLABLES_PER_SEC` 기반 목표, 결과 검증(목표±20% 아니면 실패 반환).
- T3 **콘폼 패스**: TTS 후 조립 전, 초과 비트에 T2 적용 → 그 비트 재TTS → beats에 반영
  (narration·tts_path·_caption_segments 갱신).
- T4 **마지막 비트 여운 1초** + freeze 상한 0.8s 가드(`_speed_and_freeze` 호출부).
- T5 **테스트**: 기존 스타일(실소스 슬라이스/유닛). 콘폼 성공·실패 폴백·마지막 여운·freeze 상한.
  기준선 실패 2건(test_mix_pipeline render, test_sidebar_works no_fetch)은 이 작업과 무관.

## 3. 리스크

- 리라이트가 뜻을 바꿀 위험 → 프롬프트에 "정보 삭제 금지, 압축만" + 검증 게이트(±20%).
- 재TTS 비용/지연 → 초과 비트에만, 비트당 1회 상한.
- 위저드에서 사용자가 이미 확정한 대본이 바뀌는 UX → 편집안 화면에 "⏱ 길이 맞춤" 배지로 표시
  (몰래 바꾸지 않는다).
