# 사용자 키 등록(BYOK) + 포인트 차감 — 설계

**작성**: 2026-08-17 (회사PC) · 트랙 `키등록포인트`
**상태**: 설계 확정, 구현 대기

---

## 1. 목적

숏템박스는 지금 **모든 외부 API 비용을 사장님이 부담**한다. 사용자가 늘수록
비용이 선형으로 늘어 서비스가 성립하지 않는다. 두 갈래로 해결한다.

| 사용자 유형 | 방식 | 사장님 비용 |
|---|---|---|
| 키를 직접 받을 수 있는 사람 | 자기 키 등록 → 그 작업은 무료 | 0 |
| 키를 못 받는 사람 (60대 등) | 포인트 충전해서 사용 | 포인트가 커버 |

> 사장님 원문: *"60대 이상은 그런거 못하고 그냥 비용내고 하게"*, *"알려줘도 못하는사람많음"*

**포인트가 기본 통화이고, 키 등록은 포인트를 아끼는 선택지다.** 등록을 강요하지 않는다.

### 배경 — 왜 지금인가

- **회원이 아직 0명이다.** 유예기간·공지·기존 회원 배려가 전부 불필요하다.
  처음부터 차감이 켜진 상태로 출시한다. 나중에 무료 사용자에게 과금을 시작하는
  것보다 압도적으로 쉽다.
- 선행 기록: `handoff/제미니과금.md` §⏭3 "사용자 Vertex 등록 UI"가 이 작업이다.

## 4. 데이터 설계

### 4-1. 신규 테이블 `customer_keys`

기존 `settings` 테이블은 `key TEXT PRIMARY KEY`라 **customer_id 축이 없어 재사용 불가**
(`store.py:622-627`). 신규 테이블을 만든다.

```sql
CREATE TABLE IF NOT EXISTS customer_keys (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    customer_id  INTEGER NOT NULL,
    service      TEXT NOT NULL,      -- 'gemini' | 'vmake' | 'elevenlabs' | 'youtube'
    key_enc      TEXT NOT NULL,      -- Fernet 암호문
    key_hash     TEXT NOT NULL,      -- sha256 앞 16자 — 소진표시·중복검사용 식별자
    label        TEXT,               -- 화면 표시용 마스킹 (AQ.Ab8RN••••kz1MA)
    status       TEXT NOT NULL DEFAULT 'unknown',  -- 'ok'|'bad'|'exhausted'|'unknown'
    checked_at   INTEGER,            -- 마지막 검증 시각 epoch
    created_at   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_ck_cust ON customer_keys(customer_id, service);
CREATE UNIQUE INDEX IF NOT EXISTS ux_ck_dup ON customer_keys(customer_id, service, key_hash);
```

- `ux_ck_dup` — 같은 사용자가 같은 키를 두 번 넣는 것을 DB 레벨에서 막는다
- `key_hash` — **인덱스 대신 쓰는 식별자.** §7 함정 참조

### 4-2. 암호화 유틸 (신규)

현재 프로젝트에 **양방향 암호화가 없다** — `cryptography` 미설치, `requirements.txt`
10개 패키지에 암호화 라이브러리 없음. 비밀번호는 pbkdf2 해시(단방향), 세션은 HMAC 서명뿐.

**신규**: `shopping_shorts/keycrypt.py`

```python
encrypt(plain: str) -> str      # Fernet 암호문
decrypt(token: str) -> str      # 복호화
mask(plain: str) -> str         # 'AQ.Ab8RN••••kz1MA' 표시용
fingerprint(plain: str) -> str  # sha256[:16] — 식별자
```

- 마스터키: `/etc/shopping-shorts.env`의 `BYOK_MASTER_KEY` (git 미포함)
- **마스터키가 없으면 키 등록 기능 전체를 끈다** — 평문 저장으로 조용히 폴백하지 않는다
- `requirements.txt`에 `cryptography` 추가

### 4-3. 포인트 — 기존 `points_ledger` 확장

**새로 만들지 않는다.** 이미 존재하고 FX 렌더에서 돌고 있다(`app.py:9358 FX_RENDER_COST = 10`).

```sql
-- 기존 (store.py:752), 스키마 변경 없음
points_ledger(customer_id INTEGER, delta INTEGER, reason TEXT, created_at TEXT)
```

- 잔액 = `SUM(delta)` (`store.py:4476 points_balance`)
- 래퍼 `shopping_shorts/points.py` — `balance`/`add`/`deduct`/`refund` 그대로 사용
- **소수점 단가 문제**: `delta`가 INTEGER다. 0.1P를 표현할 수 없다.
  → **내부 저장은 100배 정수(1P = 100)로 하고 화면에서만 나눈다.**
  기존 FX 10P 데이터가 있으므로 마이그레이션 시 ×100 환산 필요.
- 신규 `reason` 값: `charge`(충전) · `vmake`(자막제거) · `mix`(영상제작) ·
  `tts`(목소리) · `lens`(렌즈) · `script`(대본) · `*_refund`(실패 환불)

## 5. 키 조달 경로 수정

### 5-1. 핵심 원칙 — 한 곳에서만 정한다

CLAUDE.md 0순위-B: *"같은 결정을 두 번 적지 마라"*. 계정↔프록시가 5벌로 적혀
로테이션이 통째로 죽은 사고가 있었다.

**단일 진입점을 만든다**: `shopping_shorts/keyroute.py`

```python
def keys_for(customer_id: int, service: str) -> tuple[list[str], bool]:
    """(사용할 키 목록, 사용자 키인가) 반환.

    사용자 키가 있으면 그것만. 없으면 사장님 풀.
    ★폴백 없음 — 사용자 키가 소진돼도 사장님 키로 안 넘어간다.

```

호출부는 이 함수만 쓴다. 키를 고르는 판단이 **여기 한 곳에만** 존재한다.
두 번째 반환값(`is_user_key`)으로 포인트 차감 여부가 결정되므로,
**키 선택과 과금 판단이 짝으로 움직인다** (따로 정하면 반드시 어긋난다).

## 6. 포인트 차감 배선

### 6-1. 차감 지점

| 라우트 | op | 현재 | 조치 |
|---|---|---|---|
| `POST /api/produce/mix/clean` (`app.py:3736`) | `vmake` | **검사 없음 (구멍)** | **신규 차감** |
| `POST /api/produce/mix/start` (`app.py:2675`) | `mix` | `check_and_count("render")` | 포인트 추가 |
| `POST /api/lens/search` (`app.py:4857`) | `lens` | `check_and_count("lens")` | 포인트 추가 |
| 대본추출 (`app.py:1694,1871,8195`) | `script` | `check_and_count("script")` | 포인트 추가 |
| TTS 생성 | `tts` | 없음 | 신규 차감 |

### 6-2. ★ 최우선 — 자막제거 구멍

`POST /api/produce/mix/clean`에 **크레딧 검사가 전혀 없다.** 게다가
`_ensure_clean_sources`(`mix_pipeline.py:1257`)가 **소스 1편당 VMake 1콜**을
ThreadPool로 동시 발사한다. 소스 3개 = 500원 × 3 = **1,500원이 한 번에 나간다.**

→ 차감은 **소스 개수만큼** 해야 한다. `job` 하나에 1회가 아니다.

```
필요 포인트 = 5P × (청소 안 된 소스 개수)
```

캐시된 소스는 재과금 0 (`mix_pipeline.py:1264` 기존 동작 유지).

### 6-3. 차감 순서 (실패 시 손해 방지)

```
1) keys_for(cid, service) → 사용자 키면 차감 스킵
2) 사장님 키면: 잔액 확인 → 부족하면 402 (작업 시작 안 함)
3) 선차감
4) 작업 실행
5) 실패하면 환불 (points.refund)
```

기존 렌더 환불 패턴(`store.py:4236 refund_daily_credit`)과 같은 구조.
⚠️ 유료게이트 핸드오프에 기록된 함정 — **환불이 과금 안 한 호출자까지 돌면
카운터가 갉힌다.** 차감한 job에만 환불 표식을 남긴다.

### 6-4. 일일 상한은 유지

포인트와 **별개로** `check_and_count`를 그대로 둔다. 사장님 지시:

## 7. ★ 함정 — 반드시 지킬 것

### 7-1. Gemini 소진표시가 인덱스 기반이다 (최대 위험)

```python
# comment_gen.py:68
live = [i for i in range(len(SHORTS_GEMINI_KEYS)) if i not in exhausted]
```

`exhausted`에 담기는 건 **키가 아니라 순번**이다. 사용자별 키풀이 생기면
"3번 소진"이 **누구의 3번인지 구분되지 않는다.**

**조치**: 상태파일을 인덱스가 아니라 **`key_hash` 기반**으로 바꾸고,
사용자별로 분리한다. `data/shorts_gemini_state.json` 하나를 13개 모듈이 공유하는
구조 자체가 위험하다(주석 `comment_gen.py:74`에 이미 사고 기록 있음).

관련 메모리: `reference_키소진표시_오탐` — 아침 크론이 잠그면 하루 종일 안 풀림.

### 7-2. 검증에 SDK `models.list`를 쓰지 마라

`comment_gen.py:95` 주석에 실측 기록이 있다. `client.models.list()`는 지연 페이저를
돌려주고 클라이언트가 먼저 닫혀 **살아있는 키도 전부 실패**로 보인다.
→ **REST 직접 호출**로 판정한다 (`_probe_key_alive` 패턴 재사용).

### 7-3. 판정은 문자열이 아니라 실데이터로

CLAUDE.md 0순위-B. `challenge` 문자열이 CSS 변수명에 걸려 오탐한 사고가 있었다.
키가 살아있는지는 **실제 응답**으로만 판정한다.

### 7-4. 소수점 포인트

`points_ledger.delta`가 INTEGER다. 0.1P를 못 담는다.
→ 내부는 100배 정수, 화면에서만 나눈다. **기존 FX 10P 데이터 마이그레이션 필요.**

### 7-5. 마스터키 없으면 기능을 끈다

암호화 키가 없다고 평문 저장으로 폴백하면 안 된다. 조용한 폴백은
"되는 줄 알았는데 안 되는" 사고를 만든다. 기능 자체를 비활성화하고 경고한다.

### 7-6. 테스트에 고정 날짜를 쓰지 마라

메모리 `reference_테스트_시한폭탄_침묵except` — 고정 날짜 테스트는 며칠 뒤
반드시 깨진다. 포인트·소진 상태는 날짜를 타므로 상대 시각으로 쓴다.
