# 유튜브 썰쇼핑 채널 효과음 패턴 — 실측 분석 (2026-08-29)

> 목적: "이븐쇼핑같은 채널들 효과음 어떻게 구현하지?"에 대한 **측정 근거**.
> 추측이 아니라 오디오를 뜯어 잰 값이다. 재현 방법도 아래 적어둔다.

## 한 줄

**효과음은 대본의 '역할'이 아니라 화면의 '컷'에 붙는다.** 컷 55개 중 52개(95%)에
소리가 있고, 타점은 컷 경계 그 자리(Δ중앙값 −12ms)다.

---

## 1. 분석 대상 — 셋 다 가짜 앱UI 썰쇼핑 포맷

| | 채널 | 길이 | 컷 수 | 장면길이 중앙값 |
|---|---|---|---|---|
| V1 | **이븐쇼핑** (영어더빙판) | 28.5s | 25개 | 0.95s |
| V2 | **긍정템** | 17.5s | 21개 | **0.80s** |
| V3 | **공가미 꿀템** | 19.6s | 9개 | 1.52s |

- V1 화면에 `조회수 235만 \| 댓글 697개`가 **그려져 있다**(실제 지표 아님) — 메모리
  `reference_유튜브썰쇼핑_두장르`의 "가짜 앱UI+가짜 조회수" 그대로.
- 셋 다 상단 고정 제목 + 그 아래 한 줄 자막이 컷마다 바뀌는 구조.

## 2. ★핵심 — 효과음은 컷에 붙는다

```
V1 이븐쇼핑   컷 25개 중 소리 동반 23개  (92%)
V2 긍정템     컷 21개 중 소리 동반 20개  (95%)
V3 공가미     컷  9개 중 소리 동반  9개  (100%)
──────────────────────────────────────────
              컷 55개 중 52개 = 95%
```

**타점(52쌍 실측)**

| 지표 | 값 |
|---|---|
| Δ 중앙값 | **−12ms** |
| Δ 평균 | +2ms |
| 컷보다 먼저 / 나중 | 27개 / 25개 (**반반**) |
| \|Δ\| < 100ms | 30개 (58%) |
| 25 / 50 / 75 분위 | −61 / −12 / +107 ms |

먼저·나중이 반반이라는 게 결정적이다 — **경계에 맞춘 것**이지 앞이나 뒤에 미룬 게 아니다.

## 3. 효과음의 두 계열 (주파수로 갈린다)

| 계열 | 대역 | 지속 | 쓰임 |
|---|---|---|---|
| **반짝 / whoosh** | 8–16 kHz | **20~200ms** (중앙값 ~50ms) | 압도적 다수. 컷마다 |
| **붐 / 임팩트** | 20–120 Hz | 20~390ms | 강조 컷에만 간헐적 |

**밀도**: 이븐쇼핑 40건/분 · 긍정템 38건/분 · 공가미 **9건/분**.
→ 컷이 빠른 채널일수록 효과음도 빽빽하다(장면길이 0.80s ↔ 1.52s와 짝).

**길이가 짧다는 게 중요하다.** 대부분 20~200ms라, "효과음이 비트보다 길면 다음
비트로 흘러넘친다"는 알려진 한계(스펙 §4.3)는 **실질적으로 문제가 안 된다** —
0.2초짜리가 0.8초 칸을 넘칠 수 없다.

## 4. ★검출 방법 (재현용) — 정답파일로 먼저 검증하고 써라

효과음은 **소리**라서 프레임(그림)으로는 안 보인다. 오디오를 직접 떠야 한다.

```
1) 오디오 추출:  ffmpeg -i video.mp4 -vn -ac 1 -ar 48000 -f f32le -
2) 스펙트로그램: 40ms 창 / 10ms hop, numpy rfft (scipy 없어도 된다)
3) 판정 = 두 대역의 **온셋**(갑자기 커지는 지점)
     고역 8~16kHz : 반짝·whoosh
     저역 20~120Hz : 붐
   주변 ±1초의 로컬 배경 대비 4.5~5배 이상 + 직전 60ms 평균의 2.5배 이상
4) 컷 경계: ffmpeg select='gt(scene,0.30)',showinfo 의 pts_time
```

### ⚠️ 여기서 두 번 틀렸다 — 반드시 정답파일로 먼저 재라

| 시도 | 결과 | 원인 |
|---|---|---|
| 1차 (백분위 임계) | **0건** | 효과음이 소수라 95분위가 효과음 **위**에 잡힘 |
| 2차 (고역만 6~16kHz) | **0건** | 테스트음이 2.5kHz라 **보는 대역이 틀림** |
| 3차 (집중도+온셋) | 5/5 정확 | 합성 정답파일로 검증 후 통과 |

**합성 정답파일 만들기** (이걸 먼저 통과해야 실제 영상에 쓴다):

```bash
# 목소리 대역 노이즈 위에 정해진 시각으로 소리를 얹는다
ffmpeg -f lavfi -i "anoisesrc=d=10:c=pink:a=0.06" -af "highpass=f=300,lowpass=f=3000" voice.wav
ffmpeg -f lavfi -i "anoisesrc=d=0.3:c=white:a=0.5" -af "highpass=f=8000,afade=..." whoosh.wav
ffmpeg -f lavfi -i "sine=f=60:d=0.3" -af "volume=0.9,afade=..." boom.wav
# adelay로 1.50 / 4.00 / 6.30초에 심고 amix → 검출기가 그 시각을 찾아내는지 본다
```

검증 결과: whoosh 1.47/6.27(정답 1.50/6.30), boom 3.97(정답 4.00) — **30ms 이내**,
그리고 **음성만 있는 파일에서는 0건**(오탐 없음).

> ⚠️ 배경음악이 깔린 실제 영상은 집중도 기준선이 20 → **82**로 뛴다. 상대 임계값을
> 그대로 쓰면 0건이 나온다. 로컬 배경 대비로 재야 한다.
> ⚠️ 강한 이벤트 일부는 음악의 하이햇일 수 있다(원본 무음 트랙이 없어 완전 분리는 불가).
> 다만 **컷 정렬 95%**는 음악만으로는 안 나온다 — 음악 비트는 컷과 무관하게 흐른다.

## 5. 우리 시스템에 뭘 바꿨나

`shopping_shorts/scene_match.py`

```python
# 종전: 훅만 컷 경계, 나머지는 "last"(칸의 마지막 자막)
_SFX_POSITION = {"hook": "transition"}

# 지금: 역할 무관 컷 경계 (2026-08-29 라이브 f77d9a98a)
_SFX_POSITION = {}
_SFX_POSITION_DEFAULT = "transition"
```

`last`("문장을 맺는 자리")는 **우리 추측**이었고 실측은 장면이 바뀌는 자리라고 말한다.
기본값만 바꿨고 `last`는 칸마다 손으로 고를 수 있게 그대로 남겼다.

**실렌더 검증**: 칸 경계 3.0/6.0/9.0s → 결과물에서 2.96/5.96/8.93s에 울림.

## 6. 재료 관점 — 역할 7종보다 전환음 몇 개가 먼저다

현재 `_ROLE_FALLBACK`은 역할 7종(훅·반전·비법공개·반응·전환·CTA·본문)에 효과음을
매달지만, **실측 영상들은 역할과 무관하게 같은 계열 소리를 컷마다 돌려 쓴다.**

```
전환음(반짝/whoosh) 3~5개  ← 컷마다 로테이션. 이것만으로 90% 재현
임팩트(붐)         1~2개  ← 강조 칸에만
```

⚠️ **자산이 0개면 UI가 효과음 줄을 아예 안 그린다**(`scene_lab.html:2251`).
→ 타점만 고쳐서는 화면에 아무 변화가 없다. **소리 파일 등록이 선행 조건.**

분석에 쓴 검출기는 세션 스크래치패드에 있었고 영구 보관하지 않았다. 위 §4의
알고리즘(40ms/10ms + 두 대역 온셋 + 로컬 배경 대비)이면 다시 만들 수 있다.
**만들면 반드시 §4의 합성 정답파일로 먼저 검증하고 써라** — 안 그러면 0건을
받고 "효과음이 없다"고 잘못 결론 내린다(실제로 두 번 그럴 뻔했다).
