## A. [재발 3회 + 4회째 예약됨] node -e 명령줄 상한 (WinError 206)

**이력**: 6d7add362(07-25 sidebar) → d784d7e67(07-29) → e2b462c40(08-18). 세 번 다
"터진 그 파일만" 임시파일 실행으로 바꿨다. **공용화를 안 해서** 지금도 남아 있다:

```
실측(2026-08-19 grep): node -e 직접 호출 잔존 6파일
  test_channel_btn_targets.py · test_fx_wizard_js.py · test_grab_logic_version_takeover.py
  test_lens_korean_filter.py · test_send_target_work.py · test_url_card.py
```
JS가 몇 줄만 늘어도 32,767자 상한에 걸려 **CreateProcess WinError 206**으로 죽는다
(0.4초 만에 죽으면 로직이 아니라 길이다 — memory `reference_node_e_명령줄상한`).

**해결방안(오푸스)**:
1. `shopping_shorts/tests/js_harness.py` 신설 — JS를 **임시파일**(.js, .mjs 금지)로 쓰고
   `node <파일>`로 실행하는 `run_js(code) -> (rc, out, err)` 하나.
   이미 임시파일로 바뀐 테스트(d784d7e67·e2b462c40이 고친 것)의 구현을 **그대로 옮겨라**
   — 새로 짓지 마라(0순위-B).
2. 잔존 6파일을 전부 그 헬퍼로 이관.
3. **재발 차단 가드**: `test_no_node_dash_e.py` — tests/ 전체를 grep해
   `"node", "-e"` 패턴이 있으면 실패시키는 테스트(위반 파일명을 메시지에 나열).
   이 가드가 없으면 4회째는 시간문제다 — 세 번의 이력이 증명한다.

## B. [사흘간 긴급 4건] 2단계 대본생성 — 성공경로가 무방비

**이력**(같은 기능 영역, 연속):
```
08-15 aec0af237  장면 편집 통째로 안 뜸 — 칸 길이 함수가 병합 중 지워짐
08-16 354105612  재료 보강이 대본 생성을 통째로 막음("내가 낸 사고")
08-16 5c49ce8f6  dict를 문자열로 다뤄 500 — /api/wiki/generate (사장님 6회 클릭)
08-17 429fcce1f  _scene_block NameError 500 — 같은 영역
```
근본(메모리 `reference_바꾸기_한칸재생성`에 이미 진단돼 있었다): **"테스트가 전부
422/404라 성공경로 마지막 줄에 도달 못 함"**. 각 긴급수리가 사후 테스트를 넣긴 했다
(test_generate_material.py 등 — 확인함). 그러나 그건 그 버그의 재발만 막지,
**다음 신종 500**은 못 막는다. 넷 다 "성공경로를 끝까지 한 번 달리는 테스트"가
있었으면 게이트에서 걸렸다.

**해결방안(오푸스)**:
1. **성공경로 스모크 3종** 신설 — 실데이터 모양의 fixture(추출 9KB·source_brief **dict**·
   장면 세그먼트 포함)로 아래를 **200 끝까지** 달린다. AI 호출은 응답 모양 그대로 mock:
   - `/api/wiki/generate`(대본 생성) — 최다 사고 지점
   - `/api/produce/mix/plan`류 2단계 진입 경로(정확한 라우트는 produce.html에서 확인)
   - `run_mix_job` extract→plan 구간(EDL 생성까지)
2. fixture는 **라이브에서 떠온 실제 job의 모양**을 쓴다(지시서 §1-A의 job_id들 참조,
   extract_json 9,091자짜리). 손으로 지은 미니 fixture는 dict/str 함정을 재현 못 한다 —
   5c49ce8f6이 바로 그렇게 새 나갔다.
3. 이 3종은 finish 게이트에서 **반드시 돈다**(기존 pytest에 포함되면 자동).

## D. [재발 2회+] 씨앗 오염·캐리오버 — 복원 경로가 여럿

f17d63a6f + 00811a290(08-18, 같은 날 2건) + 메모리 `reference_저장가드_미확정작업`
("복원 경로 3개면 하이드레이션 함수 하나로"). s2.seed에 옛 작업이 살아남아 담은 영상과
무관한 대본이 나오는 사고(메모리 `reference_제작소_씨앗오염` — handoff는 멀쩡, seed만 오염).

**해결방안(오푸스)**:
1. produce.html에서 작업 상태를 **복원하는 경로를 전수 조사**해라(새 작업·핸드오프 수신·
   자동 로드·크로스기기 싱크). 각 경로가 seed·script·씨앗 밴드를 **각자** 만지는지 확인.
2. 하이드레이션 함수 **하나**로 모으고, 그 함수의 계약을 "모르는 값은 **비운다**"로 고정
   (캐리오버 원천 차단 — 저장가드 메모리의 결론과 동일).
3. 회귀 가드: "옛 작업 로드 → 새 작업 시작 → seed가 비어 있다"를 잡는 슬라이스 테스트.

## E. [재발 2회] 전역변수·TDZ로 화면 통째 공백

2ea8fea47(07-25 window ReferenceError) → 730003b39(08-18 render() TDZ, **전 플랫폼
랭킹 공백**). ★`node --check`는 TDZ를 못 잡는다(문법은 유효, 런타임 오류 —
메모리 `reference_render죽으면_전화면공백`). 슬라이스 하네스는 함수 부분집합만 평가해
전역 참조를 놓친다(4dbe559b4가 그 사례).

**해결방안(오푸스)**:
1. index.html·produce.html의 **핵심 render 경로를 실제로 실행**하는 스모크 하네스 —
   최소 mock DOM(필요 id만)으로 `render(items)` 한 번 호출해 예외 없음을 확인.
   A의 `js_harness.py`를 그대로 쓴다(임시파일 실행).
2. 슬라이스가 아니라 **파일 전체를 로드**해야 TDZ·전역참조가 잡힌다. window 미정의
   참조는 typeof 가드 관례(메모리 `reference_슬라이스하네스_window금지`)를 따른다.

## F. [구조적] 조용한 실패 — except:pass류 226개

실측: app.py **146** · store.py 47 · mix_pipeline.py 33 · video_assemble.py 8 ·
edit_plan.py 13. 이미 실사고 2건이 이 패턴에서 났다(SQL 오류 삼켜 히트작 라이브 0건 —
메모리 `reference_테스트_시한폭탄_침묵except` / 08-03 EDL 실패가 조용히 DB에만 쌓여
다음날까지 아무도 몰랐다 — mix_pipeline 주석).

**해결방안(오푸스)** — ⚠️ **일괄 수정 금지**(146개를 한 번에 고치면 그 자체가 대형 회귀):
1. **신규 금지 가드부터**: 새 커밋에 bare `except:` / `except Exception: pass`가 **늘면**
   실패하는 테스트(현재 개수를 기준선으로 파일별 상한 고정 — 늘어나는 것만 막는다).
   기준선 방식은 finish 게이트가 이미 쓰는 개념이라 어색하지 않다.
2. 회수는 **사고 경로만 선별**: 제작소 본류(run_mix_job 호출 사슬 + /api/produce/*)에서
   ①DB 쓰기 ②과금·환불 ③상태 전이를 감싼 것만 골라 `print(..., file=sys.stderr)` 사유
   로깅을 붙여라. 최근 사고 해결이 빨랐던 건 전부 **사유 로그를 심어둔 덕**이었다
   (adopt `who=채이홈 reels=0` 실례).
3. 나머지는 건드리지 마라 — 부가기능의 조용한 실패는 설계 의도인 곳이 많다(주석 확인).

## G. [래치] prewarm failed_empty — 일시 오류가 영구 실패가 된다

`prewarm.py:143` — `KeyPoolExhausted`만 롤백하고, 그 외(구글 5xx 포함)는
`failed_empty`(155행)로 기록돼 attempts를 태운다. **라이브 실측: 시도소진(≥3) 9건** —
다시 담기 전엔 영영 재시도 안 된다. 분포:
```
x15 예열 다운로드 실패(douyin yt-dlp) · x16 전사 결과 없음 · x5 인스타 해석 실패 …
```
"전사 결과 없음" 중 일부는 진짜 무자막이지만, **구글 5xx도 같은 칸에 태워진다**
(메모리 `reference_제작소_씨앗오염` ⏭ — 그때 남긴 미해결 건이 이것이다).

**해결방안(오푸스)**:
1. `extract_auto` 실패를 **영구/일시로 갈라라**: HTTP 5xx·타임아웃·429는
   KeyPoolExhausted와 같은 취급(attempts 미소진·다음 크론 재시도). 진짜 빈 전사
   (음성·자막 없음 확정)만 failed_empty로.
2. 이미 물린 9건: 일시 오류 계열(douyin 다운로드 등)만 `produce_autoload.attempts`를
   리셋하는 일회성 복구를 배포에 실어라(무자막 확정 건은 그대로).
3. 가드: "5xx 예외 → attempts 안 늚"을 고정하는 테스트.
