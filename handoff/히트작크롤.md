## 2. 태깅 — 조회수 높은 순으로 바뀜 (2026-08-09 배포)

### 무엇이 바뀌었나

종전은 **채널 라운드로빈**이었다: '미태깅이 많이 남은 채널' 순으로 돌고 그 채널
안에서만 조회수순. 그래서 전체 순위와 무관하게 태깅됐다 — 큰 채널의 40위가 작은
채널의 1위보다 먼저 붙었다.

지금은 **채널을 무시하고 전체에서 조회수 DESC**로 집는다(`run_global`).
기본 모드이므로 그냥 실행하면 조회수순이다:

```
python3 -m shopping_shorts.archive_tagger                 # 조회수순(기본)
python3 -m shopping_shorts.archive_tagger --mode channel  # 구 방식(채널 라운드로빈)
```

라이브 검증: 첫 배치가 398만~383만(muk_joongsa·ggul_yang·min.ddo_o 등 혼재).

### 남은 양과 조회수 분포

| 구간 | 남은 건수 |
|---|---|
| 100만+ | 1,724 |
| 10만~100만 | 14,508 |
| 1만~10만 | 55,166 |
| **1만 미만** | **73,350 (51%)** |
| **합계** | **144,748** (태깅 완료 23,988) |

★남은 것의 절반이 조회수 1만 미만이다. 매칭용으로 값이 낮으므로 **위에서부터
끝내는 게 사실상 완료**에 가깝다.

### 며칠 걸리나 — 키 개수가 유일한 변수

무료 Gemini 키는 **키당 하루 500건(RPD)**이 벽이다. 병렬화로는 못 뚫는다.
태거가 보는 키 = **20개** (`/etc/shopping-shorts.env`에 23개, `SHORTS_PRODUCE_RESERVED=3`
이 제작소 비상용으로 빠짐).

**전량(144,748건) 기준**

| 키 | 하루 처리 | 소요 |
|---|---|---|
| **20개 (현재)** | 10,000 | **14.5일** |
| 27개 (+주식키 7) | 13,500 | 10.7일 |
| 60개 | 30,000 | 4.8일 |
| 100개 | 50,000 | 2.9일 |

**상위권만 먼저 끝내는 기준 (조회수순이라 이게 실질 체감)**

| 구간 | 건수 | 20키 | 27키 |
|---|---|---|---|
| 100만+ | 1,724 | **0.2일** | 0.1일 |
| 10만+ | 16,232 | **1.6일** | 1.2일 |
| 1만+ | 71,398 | 7.1일 | 5.3일 |

> **결론: 지금 키 20개 그대로도 이틀이면 조회수 10만 이상이 전부 태깅된다.**
> 매칭에 실제로 쓰이는 구간은 이때 사실상 끝난다. 나머지 7만여 건(1만 미만)은
> 그 뒤 천천히 채워진다.

⚠️ **실측 처리량은 이론치보다 낮았다**: 8/2~8/9 평균 약 2,800건/일(최고 8/4 9,944건).
이유는 ①같은 키풀을 제품명판독·랭킹수집·제작소가 나눠 씀 ②페이서가 분당 한도를
15로 잘못 알아 429를 자초함(8/9 수정, 실제 한도는 **분당 5**). ②는 고쳤으므로
다음 리셋(UTC 00:00 = KST 09:00)부터 실측을 다시 잡아야 한다.

## 3. 썸네일 — 한 번 뜨면 영구, 다시 안 죽는다

**핵심**: `/api/thumb`가 받아온 이미지를 **서버 디스크에 영구 저장**한다
(`app.py:4195-4200`). 삭제·만료 코드는 **없다**(grep 확인). 조회 시 캐시를 먼저
보므로 CDN이 만료돼도 디스크에서 나간다.

즉 **한 번 화면에 뜬 썸네일은 다시 죽지 않는다.**

| | 실측 |
|---|---|
| 캐시 누적 | 70,519장 / 6.1GB (증가 중) |
| 죽은 썸네일(만료+캐시없음) | 63,810건 / 299채널 |

### 왜 죽나
인스타 CDN URL의 `oe=` 서명이 **약 4일**이면 만료돼 403. 아직 **한 번도 화면에
안 뜬** 것만 문제가 된다(캐시에 없으니 첫 로딩이 403).

### 살리는 방법 두 가지 — 용도가 다르다

| | 채널 통째 재크롤 | **릴스 개별 복구** |
|---|---|---|
| 방식 | 채널 전체를 스크롤 | 죽은 릴스만 `/reel/{code}/` |
| 속도 | 첫 페이지 100건에 1~2시간 | **100건 15분** (건당 ~9초) |
| 쓸 곳 | 뒤쪽 대량(6만 건) | **화면에 보이는 앞쪽** |

전량 6만 건을 개별로 하면 160시간이라 **앞쪽=개별 / 뒤쪽=채널통째**로 갈라 쓴다.

스크립트(서버): `/home/ubuntu/revive_single.py N` (댓글순 상위 N건 개별 복구)
· `/home/ubuntu/revive_thumbs.py` (채널 통째)

⚠️ **채널 통째로 할 땐 `_STALL_LIMIT`을 올려야 한다.** 기본 6은 "6번 스크롤해서
새 게 없으면 바닥"인데 인스타 지연로딩이 그보다 느려 **바닥이 아닌데 멈춘다**.
실측(salimddak 378건): 6 → 168건에서 끊겨 2026-05-06까지만(인기글 미포함, 여전히
403) / **20 → 378건 전부, 2025-12-14까지, 인기글 2건 모두 포함**.
터진 영상일수록 옛날 것이라 얕게 긁으면 정작 화면에 뜨는 카드를 못 살린다.

### 자동화 (2026-08-09 배포)
`pick_targets`가 **4일 넘게 안 본 done 채널을 신규 뒤에 자동으로 붙인다**
(`archive_stale_usernames`). 이제 수동 개입 없이 크론이 갱신한다.
재크롤은 `thumbnail`만 덮어쓰고 `vision_tags`는 shortcode가 PK라 유지 →
**재태깅 비용 0**.

## 4. 태깅은 한 번만 하면 된다

- `vision_tags.shortcode`가 **PRIMARY KEY** → 영상당 1행, 중복 0건(실측)
- 태거 후보 선정이 `NOT EXISTS(vision_tags)` → 완료분은 다시 안 집는다
- DB는 서버 디스크에 영구(`reference.db` 208MB)
- 재크롤로 썸네일 URL이 바뀌어도 shortcode는 같아 **재태깅 안 한다**

## 5. 2026-08-09에 고친 것 (커밋 `07ed7f568`, `8a4306d77` → main `738d80f1a`)

1. **페이서 과속** — `_RPM_PER_KEY` 15 → **5**. 실측 429 원문이 `limit: 5`.
   15는 추정치였고 3배 빠르게 때려 429를 자초했다.
2. **429 대기시간 무시** — 서버가 "45.5초 뒤에 오라"는데 고정 8초만 자고
   재시도 3번을 태워 조용히 빈 결과를 반환했다(`0/40건`의 직접 원인).
   → `key_vault.retry_delay_seconds()`로 서버 값을 존중.
3. **재검증이 전멸에서만 발동** — 20개 중 19개가 오탐이어도 남은 1개가 죽을
   때까지 0건이 흘렀다 → 살아있는 키가 풀의 20% 이하면 재검증.
4. **태깅 순서** → 전역 조회수순(위 2번).
5. **만료 썸네일 자동 갱신** → done 4일 뒤 재크롤(위 3번).

⚠️ **오진 기록**: "키 20개가 전부 오탐(실호출 200)"이라고 보고했으나 **틀렸다**.
표본 3개만 보고 일반화한 것이고, 20개를 전수 확인하니 **살아있는 건 3개뿐**이고
17개는 진짜 하루 한도 소진이었다(`limit: 500`, `retry in 20s`).
→ 병목은 처음부터 **키 개수(RPD)**였다. 사장님의 "키를 매일 채우겠다"가 정답.
