# 크롤·인제스트 감시 에이전트 — 설계 (2026-07-02)

## 배경

2026-07-02, 유튜브 채널 15개를 신규 등록하고 전체 크롤+인제스트를 요청받아 Claude가 SSH로
원격 크롤 로그를 약 17분간 수동으로 지켜보며(20~60초 간격 폴링) "멈춘 건지 그냥 느린 건지"를
CPU/경과시간/로그 성장 여부로 직접 판단했다. 실제로는 Gemini 분당 토큰 한도(429, retryDelay
30~40초)에 반복적으로 걸려 느려진 것뿐이었고, 크롤러 자체가 실패를 건너뛰며 정상 진행했다.
이 과정에서 사람(Claude)이 매번 붙어서 지켜봐야 하는 문제, 그리고 대시보드 크롤 트리거를
두 번 실행해 원격에 중복 프로세스가 뜨는 사고도 발생했다.

이 설계는 "수동으로 전체 크롤 누르는" 경우(대량 소스 추가 후 일괄 크롤처럼 오래 걸리고
막힐 위험이 큰 경우)에 한해, 감시·판단·제한된 재시작·인제스트·보고까지 자동화하는 것을 다룬다.
평소 자동 스케줄(하루 5회, 소량 트리클)은 건드리지 않는다.

## 조사 중 발견한 사전 조건 (구현 전 확정된 사실)

- `dashboard/server.py`의 `server_crawl()` / `/api/crawl/run`에는 **동시실행 방지 락이 없다**.
  같은 카테고리를 두 번 트리거하면 원격에 중복 `crawl_run.py` 프로세스가 뜬다(2026-07-02 실제 발생).
- 원격 `crawlers/youtube_crawler.py`는 `is_duplicate(url)`로 **파일에 영구 저장된 seen 목록**을
  확인 후 스킵한다(`processors/md_writer.py::_load_seen/_save_seen`) — 즉 크롤을 죽이고
  같은 카테고리를 처음부터 다시 돌려도 이미 완료된 항목은 재시도하지 않고 건너뛴다.
  **카테고리 전체 재시작은 안전하다** — 채널별로 쪼개서 재시작할 필요 없음.

## 결정: 순수 Python (oh-my-fable/Node.js 사용 안 함)

브레인스토밍 중 oh-my-fable(Node.js 장기실행 에이전트 프레임워크) 도입을 검토했으나,
오푸스 설계 검토 결과 다음 이유로 기각:
- 오늘 실제로 필요했던 건 "판단"이지 "크래시 복구/체크포인트"가 아니었음 — oh-my-fable의
  핵심 가치(플랜 재개)가 관측된 실패 유형과 안 맞음
- 이미 Python으로 통일된 운영 파이프라인에 Node.js 런타임을 추가로 들이는 비용(관리 포인트,
  SSH키/.env 노출면, npm 공급망 리스크)이 얻는 이득보다 큼
- 동등한 기능(감시→판단→제한 재시작→인제스트→보고)을 기존 `dashboard/server.py`의 함수들과
  같은 프로세스 내에서 Python으로 충분히 구현 가능

체크포인트/재개가 실제로 필요해지면(에이전트 프로세스 자체가 죽는 사고가 반복되면) 그때
oh-my-fable을 v2로 재검토한다.

## 아키텍처

```
sources.html "▶ 전체 크롤" / 채널별 "▶"
   → POST /api/crawl/run
   → (신규) 카테고리별 동시실행 락 획득 시도
        - 이미 실행 중이면: 즉시 {ok:false, error:"이미 진행 중"} 반환, 새로 시작 안 함
        - 락 획득 성공 시: 감시 루프를 백그라운드 스레드/프로세스로 기동, {ok:true, started:true} 즉시 반환
   → 감시 루프가 끝까지 혼자 진행(트리거→폴링→판단→[재시작]→pull→인제스트→검증→보고)
   → 완료/실패 시 락 해제 + 텔레그램 + out/ 리포트
```

기존 5개 Windows 스케줄 작업(`LottoStock_SlotIngest_Main` 등, 08:10/12:10/15:10/18:10/21:10)은
그대로 둔다 — 소량이라 감시 불필요.

## 감시 루프 상세

1. **동시실행 락**: 카테고리별 로컬 락파일(예: `pipeline/.crawl_lock_{cat}.json`, PID+시작시각 기록).
   락 획득 실패 시 시작하지 않음 — 오늘 발생한 중복 크롤 재발 방지가 최우선 목표.
2. **원격 크롤 트리거**: 기존 SSH `nohup python3 crawl_run.py {cat} {only} ...` 그대로 재사용.
3. **폴링**: 일정 간격(예: 20초)으로 원격 로그 tail + 대상 프로세스 CPU시간/경과시간 조회(기존
   세션에서 쓴 것과 동일한 `ps -o pid,etime,time,cmd` 패턴).
4. **판단 — 결정론적 규칙을 먼저, 애매할 때만 AI**:
   - `rules.json`(예: `pipeline/crawl_monitor_rules.json`)에 등록된 패턴과 로그 tail을 우선 매칭.
     예: 로그에 `RESOURCE_EXHAUSTED`+`retryDelay`가 보이면 즉시 `on_track`(그냥 대기) — AI 호출 없이.
   - 규칙에 안 걸리는 애매한 경우에만 Claude에 로그 tail + CPU/경과시간을 보여주고
     `on_track / needs_replan / blocked / goal_met` 중 하나로 판단받는다. 호출 방식은
     `dashboard/server.py::run_agent()`가 이미 쓰는 `claude -p "<프롬프트>" --permission-mode
     bypassPermissions` 헤드리스 CLI 호출 패턴을 그대로 재사용한다 — 새 API 키·SDK 의존성 추가 없음.
   - **Claude 응답 실패/타임아웃 시 기본값은 반드시 `on_track`**(그냥 더 기다림) — 네트워크 순간
     장애로 오판·자동 kill되는 최악의 경우를 막는다.
5. **재시작 상한**: `needs_replan` 판단에 따른 kill+restart는 **런당 최대 2회**로 제한. 그 이상
   반복되면 `blocked`로 간주하고 사람에게 텔레그램으로 알리고 중단(무한 재시작 방지).
6. **판단 기록**: 모든 AI 판단 호출(입력신호+판단+근거)을 `pipeline/crawl_monitor_decisions.jsonl`에
   누적. 사람이 주기적으로 검토해서 명백한 패턴만 `rules.json`에 **수동으로** 추가(자동 승격 없음).
7. **완료 처리**: `goal_met` 판단 시 기존 `pull_crawl()` 로직 재사용 → 로컬 raw 반영 →
   카테고리에 맞는 기존 인제스트 스크립트 호출(`telegram_ingest.py --all`,
   `post_ingest.py --source youtube|blog|news --all` 등, 오늘 만든 것 그대로) → 원자 수 등
   결과 검증 → 텔레그램 요약 + `out/`에 마크다운 리포트 저장 → 락 해제.

## UI 상태 표시

`/api/crawl/run`이 이제 "즉시 완료"가 아니라 "긴 감시 시작"을 의미하므로:
- 락 상태를 조회하는 엔드포인트(예: `GET /api/crawl/status?cat=youtube`)를 추가해 진행 중 여부를
  sources.html에서 버튼 옆에 표시(예: "진행 중… (5분 경과)").
- 락파일에 시작 시각을 기록해두고, 비정상적으로 오래된 락(예: 1시간 이상)은 좀비로 간주해 자동
  해제하거나 수동 해제 버튼을 제공 — 감시 루프 자체가 죽었을 때 영구히 "진행 중"으로 잠기는 것 방지.

## 테스트

- 락 획득/해제, 중복 트리거 거부를 단위 테스트로 검증.
- 판단 함수는 "로그 tail + 프로세스 통계 → 판단"을 순수 함수로 분리해, 실제 SSH/Claude 호출 없이
  고정 입력으로 유닛 테스트(오늘 실제로 본 429/느린-Gemini/완료 3가지 시나리오 로그 샘플을
  픽스처로 사용).
