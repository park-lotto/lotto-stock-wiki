2026-08-31 실사고. 유튜브 랭킹 수집이 그날 **0건**(08-30까진 9,264건 정상).
사장님이 "레퍼런스 수집 안 된 것 같다"로 발견 — 아무 알림도 없었다.

**뿌리**: `shopping-shorts-collect.timer`가 하루 08:10 **1회**뿐인데,
`daily_youtube_collect.py`가 `heavy_job_active()`면 양보하고 그냥 종료했다.
코드 주석은 "하루 1회라 다음 회차로 미뤄도 무해"라고 적혀 있었지만
**다음 회차는 내일**이다. 사장님이 낮에 제작을 계속하면 렌더가 늘 돌아
구조적으로 재발한다.

**교훈 — 양보(백오프)에는 반드시 같은 주기 안의 재시도가 짝이어야 한다.**
"바쁘면 다음에"라고 쓴 코드를 보면 **다음이 언제인지 실제 스케줄로 확인**하라.
주석이 말하는 '다음 회차'가 진짜 존재하는지가 핵심이다.

**처방**(라이브):
- 타이머 회차 08:10(본) + 11:10·14:10·17:10·20:10·22:40(재시도)
- 성공 시 `settings`의 `daily_collect_done::youtube` = 오늘(KST) → 남은 회차 건너뜀
- **양보는 표식을 남기지 않는다** — 남기면 그날 재시도가 통째로 죽는다

⚠️ **타이머/서비스 파일은 auto_deploy가 안 건드린다.** `deploy/*.timer`를 고쳐
main에 넣어도 서버엔 반영 안 된다. `sudo cp deploy/x.timer /etc/systemd/system/ &&
sudo systemctl daemon-reload && sudo systemctl restart x.timer` 를 직접 해야 한다.

⚠️ **테스트가 라이브 DB에 상태를 쓰면 운영을 망가뜨린다.** 이번에 main()이 실 DB에
'오늘 완료' 표식을 남기게 되면서, 테스트가 그걸 쓰면 그날 진짜 수집이 건너뛰어질
뻔했다(표식 누수로 기존 테스트가 깨져 발견). Store를 `_FakeStore`로 주입해 격리했다.
**부작용이 생긴 함수의 기존 테스트가 실 DB를 쓰고 있진 않은지 같이 봐라.**

수집 이력 확인: `platform_snapshots`의 `run_date`(전날 23:10 기준으로 적힌다 —
08-30 실행이 '2026-08-29 23:10'으로 남으니 하루 밀려 보인다고 오해하지 마라).
