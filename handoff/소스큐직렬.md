# 소스큐직렬 — "소스 추가가 나중에 한꺼번에 반영된다"

## 2026-09-02 고객(이유준) 제보
"소스 추가할 때 바로 반영이 안 돼요. 그니까 나중에 한꺼번에 또 반영돼요"
사장님 확인: **아까 담았던 소스 클립 5개가 한꺼번에 반영되어 있다.**

## 실측 (서버 reference.db `job_queue`)
담긴 순서대로 대기가 계단식으로 늘어난다:
`대기 72초 → 117 → 167 → 187 → 226 → 280 → 312 → 450 → 485 → 512 → 536초(9분)`
작업 자체는 0~147초. **대기가 작업보다 훨씬 크다.**

★그런데 워커는 놀고 있었다 — 25분 구간 총 점유 2,404초, 워커 12개 = 용량 18,000초.
   즉 일이 많아서가 아니라 **줄을 세우는 규칙** 때문이었다.

## 뿌리 두 겹

**① prewarm 전체가 동시 1개** (`_EXCLUSIVE_TASKS`)
인스타 세션 보호가 이유다(2026-08-05 동시 접속으로 계정 2개 소실). 그런데 최근 200건 중
인스타는 72건(36%)뿐이고 **128건(64%)은 틱톡·샤오홍슈·유튜브**로 인스타 세션과 무관하다.
관계없는 것까지 인스타 뒤에 줄 세우고 있었다.

**② 계정당 동시 1개** (공평 분배)
무거운 작업(render·mix)이 한 사람에게 독점되는 걸 막으려던 규칙인데 **가벼운 사전분석까지**
묶었다. 그래서 한 사람이 소스를 5개 담으면 하나씩 줄줄이 기다렸다 — 제보 그대로다.

## 고친 것 (둘 다 보수적으로)

① **화이트리스트로만** 배타를 푼다. 틱톡·샤오홍슈·도우인·유튜브·네이버 표식이 있고
   `instagram`이라는 글자가 **아예 없을 때만** 병렬. 모르면 종전처럼 직렬.
   ★인스타 동시성은 **그대로 1개** — 느린 건 고칠 수 있어도 죽은 계정은 못 되살린다.
② 계정 상한을 **작업 무게로** 가른다. 무거운 것은 그대로 1개(공평 분배 유지),
   가벼운 prewarm·durfill만 계정당 3개(`LIGHT_CONCURRENT_JOBS`).
