## 2026-08-17 (회사PC) — 수집 실패 55% 근본수리 + 랭킹 화면 수리 6건

### 오늘의 본론 — 수집이 절반을 버리고 있었다

등급제(`REFERENCE_TIER=1`)를 켜고 처음 돌린 결과가 이상했다.

```
채널결과 {'ok': 49, 'login_wall': 0, 'not_found': 61, 'error': 0} · 81건 수집 · 1573초
```

**`not_found` 61건을 "채널이 죽었다"로 읽었는데, 그게 오독이었다.**
`instagram_parse.classify_channel_result`는 이렇게 생겼다:

```
error 있으면 → error / nodes 있으면 → ok / URL이 로그인벽 목록 → login_wall / 그 외 전부 → 여기
```

**채널이 있는지 확인하는 코드는 없다.** 이름만 `not_found`였다.
같은 파일 주석에 2026-08-09 사고가 적혀 있다 — 관문 URL 하나가 목록에 빠져 199채널이
전부 `not_found`가 됐고 "채널이 다 없어졌다"로 오독한 뒤 엉뚱한 결론까지 갔다.
**같은 자리에서 두 번째다.**

### 원인 — 고정 2.5초 대기 (`instagram_playwright.py`)

```python
page.wait_for_timeout(2500)   # 릴스 목록 XHR이 도착할 여유
```

응답을 **기다리는 게 아니라 2.5초 자고 일어나 있으면 쓰고 없으면 빈손**으로 나갔다.
그래서 같은 채널이 될 때·안 될 때가 무작위였다.

**같은 슬롯·같은 14채널로 조건만 바꾼 실측 (이게 결정적 근거)**

| 조건 | 성공 |
|---|---|
| 그대로 (이미지차단ON, 2.5초) | 5 / 14 |
| 이미지차단만 끔 (2.5초) | 7 / 14 |
| **대기 2.5초 → 10초** | **14 / 14** |

수확 0이던 채널 30개를 15초로 10개씩 3묶음 재시험 → **30/30 전부 12건씩** 회수.
**죽은 채널은 0개였다.**

⚠️ 이미지차단(`block_heavy_assets`, 오늘 프록시 절감용으로 넣은 것)은 **범인이 아니다**
(끄나 켜나 비슷). 다만 페이지를 느리게 해 2.5초 경계를 더 자주 넘겼을 수는 있다.

⚠️ **기준선이 코드에 박혀 있었다** — `instagram_playwright.py:14`
"192채널 ok187·not_found5" = **실패율 2.6%**. 이번 55%는 20배다.
"어쩔 수 없는 실패"가 아니라 **회귀**라는 판단 근거가 여기였다.

### 수리 3건 (main `be44a8bcd`)

1. **고정 sleep → 응답 대기** — 잡히면 즉시 진행, 상한 `config.INSTAGRAM_PW_LIST_WAIT_MS`(12초)
   빠른 채널은 2.5초도 안 기다려 **오히려 빨라진다**
2. **`not_found` → `unknown`** — 여긴 판정이 아니라 나머지 통이다. 모르면 모른다고 적어야
   다음 사람이 원인을 찾으러 간다
3. **채널별 판정 기록** (`LAST_VERDICTS` + 로그) — 숫자만 남기면 "어느 채널이 실패했나"를
   못 되살린다. 실제로 오늘 61개를 복구하려다 실패했다(등급 재계산이 329로 나와 런 110과 불일치)

**수리 후 정기 수집 실측**

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 채널결과 | ok 49 · not_found 61 | **ok 104 · unknown 2 · error 1** |
| 성공률 | 45% | **97%** |
| 수집 | 81건 | **161건** |
| 소요 | 1,573초 | 1,545초 (더 빠름) |

실패 3건도 이름으로 남는다: `[수집] 실패 3채널: yeonhee._.home(error), better__item(unknown), …`

### 랭킹 화면 수리 (제보 대응)

- **탭·지표·카테고리가 전부 안 먹힘** → 버퍼가 아니라 `render` 예외 **하나**였다.
  `i.speed.toFixed(1)` — 기간·역대 탭은 `build_items`를 안 거쳐 강도지표가 없는데 화면이
  무조건 불러 **첫 카드에서 render가 죽고 화면이 얼어붙었다**. 원인 하나에 증상 넷.
  처방 2겹: `ranking.fill_intensity`(서버가 채움) + 화면 `_num`/`_pct`(없어도 '—'로 버팀)
- **썸네일 전부 검음** → 화면은 `i.thumbnail`인데 두 경로는 `thumb`으로 줬다(이름 어긋남)
- **역대 문턱버튼이 눌러도 그대로** → 댓글순 상위 400을 자르니 문턱을 낮춰도 같은 얼굴.
  **겹치지 않는 구간으로**: 1만+ / 3천대(3000~9999) / 1천대(1000~2999). 교집합 0 확인
- **역대탭 카테고리 결과 0건** → `channel_archive`에 category 컬럼이 없다.
  ★내 앞선 "20만건 Gemini 태깅 필요, 보류" 판단을 뒤집었다 — 카테고리는 릴스보다
  **채널의 성질**이라 채널 단위로 붙이면 된다. `Store.category_by_channel` 신설,
  **커버리지 79.5%(206,807건 중 164,513건), AI 비용 0**
- **카테고리 바꿔도 소리가 이어짐** → 브라우저는 재생 중인 `<video>`를 DOM에서 지워도
  **재생을 안 멈춘다**. `stopAllMedia()`를 `render` 첫 줄에서 호출
- **합친 3장이 앞장만 재생** (쿠팡선수집 트랙이 만든 기능, 그 트랙 닫혀서 인계받음)
  → `mergeSpan`이 합치기를 **한 개의 긴 구간**으로 만드는데 `planClips`는 구간이 하나면
  앞에서부터 칸 길이만큼만 쓴다. `trimPieces`가 **멤버 경계로 되가르게** 수정
  (나누는 규칙 `planClips`는 한 줄도 안 건드림). 덤: 멤버 사이 공백이 빠진다

## 함정 (다음 세션이 밟지 말 것)

- **`unknown`(옛 `not_found`)을 "채널이 없다"로 읽지 마라.** 나머지 통이다.
  오늘까지 이걸로 두 번 오독했고 두 번 다 우리 코드 문제였다
- **실패율은 코드 주석의 기준선과 대조하라** (`instagram_playwright.py:14` = 2.6%).
  대조 없이 "원래 그런가 보다" 하면 20배 회귀를 놓친다
- **"화면이 안 바뀐다 / 버퍼 같다" 제보는 콘솔부터 봐라.** 렌더가 결측 하나로 통째로
  죽으면 정확히 그렇게 보인다. 오늘 증상 4개가 예외 1개였다
- **같은 것을 두 이름으로 부르지 마라.** 오늘만 2건(`not_found`=나머지통, `thumb`/`thumbnail`).
  한쪽이 반드시 조용히 빠진다
- **비용 얘기는 "오늘 실측"과 "앞으로 정상운영"을 갈라 써라.** 안 가르면 거짓말이 된다
  (내가 "추가 비용 0원"이라 했다가 사장님께 정정당했다)
