# 청소본을 정본으로 — 자막제거는 job당 한 번, 꾸미기는 그 위에서 (설계)

**날짜** 2026-09-22 · **트랙** `소스구간청소` · **상태** 사장님 검토 대기
**대전제(사장님 2026-09-22)** "일단 한번만 제거비용이 나가는게 대전제야."

## 1. 왜 (실측)

라이브 워커 로그 7일(09-15~22) 실측:

| 항목 | 값 |
|---|---|
| 자막제거 과금 job(실패 제외) | 350 |
| job당 평균 과금 횟수 | **1.65회** (1회 205 · 2회 112 · 3회 이상 33) |
| 최종렌더에서 재과금된 job | 128 (37%) |

재과금 173쌍의 원인(청소 시점 편성 스냅샷 대조):
자막 줄 나누기만 67 · 확대만 25 · 등급 변경 20 · 장면 교체 13 · 컷 길이·구절 짝·복합 48.

뿌리: 최종렌더가 **청소본을 편집하지 않고 원본 소스에서 처음부터 다시 조립**한 뒤,
새 조립본(자막 있음)을 다시 지운다. `_final_clean_fn`은 편성 서명이 같을 때만 재사용한다.
꾸미기에서 줄·확대·컷을 손대면 서명이 바뀌어 재청소·재과금이 난다.

기각한 대안 — 소스 구간 청소(`SHORTS_CLEAN_SPAN`, 08-25 코드): 최근 80 job 실측으로
처음 청소가 완성본의 **3.05배**(한 덩이) / **2.04배**(조각 정밀, 여유 0.5초). 재료 후보 구간이
화면보다 길어서다. 고객 59%는 한 번만 지우므로 평균 비용이 오히려 오른다. **안 간다.**

## 2. 목표 / 비목표

**목표**
- 4단계에서 완성본(≈25초)을 **한 번** 지운 뒤, 5단계 꾸미기(확대·강조·자막·줄 나누기·컷 길이·
  구절 짝·음성·속도·데코)는 **청소본 위에서** 처리한다. 재청소·재과금 0.
- 최종렌더·미리보기·프레임·썸네일·전후비교·캡컷 내보내기·번들 내보내기가 **같은 청소본**에서
  나온다(시간축 하나).
- 고객이 장면을 **아직 안 지운 새 영상**으로 교체하면 그 장면 몫만 지운다(초 단위 소액).
  기존 장면은 어떤 편집에도 재과금 없음.

**비목표**
- 소스 단위 청소로의 회귀(위 실측으로 기각).
- 등급(basic→pro) 변경은 새 결과물이므로 재청소가 맞다 — 그대로 둔다.
- 4단계 이전(1~3단계) 흐름은 손대지 않는다.

## 3. 핵심 개념

### 3.1 청소 기준본(clean base)
4단계 청소 결과를 job의 **기준본**으로 승격한다.

```
job.clean_base = {
  "sig":   "<청소 시점 편성 서명>",          # 파일명 final_clean_{sig}.mp4 와 짝
  "path":  "final_clean_{sig}.mp4",
  "plan":  "final_clean_{sig}.plan.json",     # 이미 저장하는 스냅샷(_save_clean_plan_snapshot)
  "cuts":  [ {ci, beat_idx, video_id, src_start, src_end, t0, t1}, ... ]   # 청소본 시간축 지도
}
```
`cuts`는 청소 시점 편성으로 `_final_cuts`/`clean_compare_clips`가 이미 계산하는 컷 타임라인이다.
**새로 계산하지 않고 그 결과를 저장만 한다**(0순위-B: 컷 판정처는 하나).

### 3.2 재료 재배치(remap) — "청소본을 소스로 조립"
최종렌더·미리보기·내보내기는 편성표의 재료 `(video_id, start, end)`를
청소본 좌표 `(clean, t0', t1')`로 바꿔 **청소본을 유일한 소스로** 조립한다.

```
remap(material, base.cuts):
  cut = base.cuts 중 video_id 같고 [src_start, src_end] ⊇ [start, end] 인 것
  있으면 → ("clean", cut.t0 + (start - cut.src_start), cut.t0 + (end - cut.src_start))
  없으면 → 미커버(uncovered)
```
- 확대·강조·자막·줄 나누기·구절 짝·속도는 조립 단계(`_render_mix`, `_plan_phrase_clips`)가
  재료 위에서 하는 일이라 **그대로 동작**한다. 소스가 청소본으로 바뀔 뿐이다.
- 줄 나누기의 컷 재분할은 재료 구간 안에서만 일어나므로 청소본 안에 머문다.

### 3.3 미커버 재료 → 증분 청소
새 영상으로 교체된 장면(video_id가 base.cuts에 없음)은 원본에서 그 재료 구간만 잘라
**한 콜로 묶어** 지우고(기존 `_join_batches`/`_clean_joined` 재사용), 결과를 base.cuts에
**추가**한다(증분). 과금은 보낸 초수만큼(=`clean_credit_estimate`). 화면은 렌더 전에
"새 장면 N초 자막제거(≈M크레딧)"를 알린다.

### 3.4 화면 길이 부족(컷이 청소본보다 길어질 때)
음성·컷 길이 변경으로 `target_seconds > (t1'-t0')`이면:
1. **10%까지 느리게**(sync_speed 하향)로 채운다.
2. 그래도 모자라면 **마지막 프레임 정지**로 채운다.
3. 부족분이 컷의 30%를 넘으면(큰 늘림) 원본에서 뒤쪽을 더 잘라 **증분 청소**(3.3과 같은 경로).
1·2는 과금 0, 3만 소액. 상수는 `_CLEAN_BASE_STRETCH_MAX=0.10`, `_CLEAN_BASE_EXTEND_MIN=0.30`.
(사장님 확정 2026-09-22: "장면을 살짝 느리게 재생". 2·3은 그것으로 안 될 때의 안전판.)

**짧아지는 경우는 문제가 없다.** TTS 무음 구간 삭제·말 줄이기로 `target_seconds`가 청소본 컷보다
**짧아지면** 청소본의 앞부분만 쓰고 나머지는 안 쓴다(`t1' = t0' + target_seconds`). 과금 0, 화면
부족 없음. 늘림 정책은 길어질 때만 탄다.

### 3.5 언제 기준본이 무효가 되나
- 등급 변경(basic↔pro) → 새 기준본(기존 규칙).
- 고객이 4단계에서 "다시 지우기"를 명시적으로 누름.
- 그 외 편성 변경은 **무효가 아니다**(remap + 증분으로 처리).

## 4. 데이터 흐름

```
4단계 run_clean_sources ──▶ final_clean_{sig}.mp4 + plan.json + cuts  ──▶ job.clean_base 저장
5단계 꾸미기(편성 변경) ──▶ 편성표만 갱신(재청소 없음)
최종렌더 run_render:
   base = job.clean_base
   plan' = remap(plan, base.cuts)                      # 재료 → 청소본 좌표
   uncovered = 미커버 재료
   if uncovered: base.cuts += incremental_clean(uncovered)   # 증분, 소액 과금
   source_video_paths = {"clean": base.path, (+ 증분 청소 조각들)}
   assemble(plan', ..., clean_fn=None)                 # ★VMake 안 탄다
캡컷/번들 내보내기: 같은 plan'·같은 source_video_paths → 청소된 컷이 그대로 나간다
미리보기·프레임·썸네일·전후비교: base.path + base.cuts 로 좌표 계산(지금의 sig 파일 대신)
```

## 6. 과금

- 4단계: 지금과 같음(완성본 초수 × 등급 단가, 1콜).
- 최종렌더: **0**. 예외는 증분(새 장면·큰 늘림)뿐이며 보낸 초수만큼.
- 기대치: 7일 실측 기준 job당 1.65회 → 1.0회 + 증분(장면 교체 13/173 = 8% job에서 몇 초).

## 7. 오류 처리

- remap 실패(기준본 파일 없음·cuts 손상) → 기준본 무효로 보고 **지금 경로**(완성본 재청소)로
  되돌린다. 조용히 죽지 않는다: `clean_base_fallback` 로그 + 화면 안내.
- 증분 청소 실패 → 렌더 실패로 종착(지금 `_final_clean_fn` 실패와 같은 환불·상태 경로).
- 늘림 정책이 마지막 프레임 정지를 쓰면 `[clean-base] hold 0.8s beat 3`처럼 로그에 남긴다.

## 8. 검증 (라이브 전 필수 — 0순위-A1·A1c)

관리자 스위치 뒤에 두고, **실제 job 사본**(장면꾸미기UI코덱스 트랙의 실데이터 LAB 방식)으로:

1. **재과금 0**: 4단계 청소 → 줄 나누기·확대·컷 길이·음성 변경 → 최종렌더. 워커 로그에
   `청소 시작`이 **한 번만** 찍히고 VMake 콜 카운트 1.
2. **그림 일치**: 최종렌더 결과의 컷별 프레임 = 청소본의 같은 시각 프레임(phash 거리 ≤ 4).
   자막이 남은 컷 0(원본 자막 OCR 검출 0).
3. **캡컷 내보내기**: 같은 편성에서 캡컷 초안의 클립(`cc0…`) 경계·길이가 최종렌더 컷 타임라인과
   ±1프레임 일치. 클립 소스가 청소본. 캡컷에서 열어 실제 재생 확인(눈).
4. **번들 내보내기·미리보기·프레임·썸네일·전후비교**: 전부 청소본에서 뜸(원본 자막 0).
5. **증분**: 장면 하나를 새 영상으로 교체 → 그 구간만 청소(로그에 초수), 나머지 컷은 재사용.
6. **늘림 정책**: 음성을 길게 바꿔 컷이 청소본보다 길어지는 job → 느리게/정지/증분 각각 1건.
7. 회귀: `tests/test_clean_*` 전부 + 신규 계약 테스트(remap 순수함수·uncovered·stretch).
   특히 `test_clean_once_per_video`·`test_clean_sig_caption_lines`는 새 경로에서 **의미가 바뀐다** —
   "줄을 바꿔도 청소 1회"로 고쳐 잠근다.
8. 라이브: 관리자 계정 job 1건으로 4→5→최종렌더→캡컷까지 **직접 눌러** 확인 후에만 고객에게.
