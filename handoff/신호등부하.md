# 신호등부하 — 분석 신호등 조회가 웹 서버 CPU를 먹던 것 (관제 171)

## 2026-10-10 (PC: CH)

### 무엇을·왜
사장님 질문 "1단계 분석이 많이 돌면 CPU 많이 먹나"를 재다가 발견. 라이브 웹 서버(uvicorn 한 프로세스)가
가동 15.2시간에 CPU 19시간(평균 1.24코어) — 워커 12개 합계(0.53코어)의 두 배.
py-spy(`--nonblocking -d 60 -r 50`) 표본 2,657개 중 2,373개(89.3%)가 `api_basket_analysis_status`,
잎의 73.8%가 `Store._conn`(새 연결의 첫 문장 = 스키마 200객체 다시 읽기, 연결 1회 CPU 1.1ms).

### 판단 주인·결과물 검사
- 주인 함수: `shopping_shorts/app.py:_analysis_state` (판정은 그대로 한 곳). 연결을 정하는 곳은 `Store._conn` 하나.
- 결과물 검사: 라이브 py-spy 60초 표본에서 이 라우트 몫 10% 이하 + 같은 shortcodes 응답 동일.

### 고친 것
- `store.Store.reuse()` — 블록 안 조회가 연결 하나를 돌려 쓴다(스레드별, 겹쳐 불러도 됨, 끝나면 닫음).
- `store.Store.has_script()` — 있나 없나만(SELECT 1). 상태 조회가 대본 JSON을 통째로 읽던 것 제거.
- `_analysis_state(store, code, need_data=True)` — `need_data=False`면 상태만. 쓰는 곳: 신호등 조회, 스토리보드 '재료 대기' 판정.
  분석 걸기 버튼(`api_basket_analyze`)·1단계 카드(`source_brief`)는 종전 그대로.
- 테스트 `tests/test_analysis_status_load_171.py` 4건 — 수리 전 코드에서 4건 전부 실패 확인.

### 실측(라이브 DB 읽기 전용, 최근 담긴 100개)
수리 전 요청 1건 CPU 0.119~0.139초 → 수리 후 0.002초. 결과 100개 동일(done 95).

### ⏭ 남은 것
1. **라이브 확인(배포창 KST 02~06 반영 뒤)**: py-spy 60초 다시 떠서 이 라우트 몫, uvicorn 평균 코어.
2. 화면이 이 조회를 얼마나 자주 부르는지(폴링 간격·멈춤 조건)는 별도 조사 중 — 결과에 따라 후속 카드.
3. 같은 꼴(목록을 돌며 호출마다 연결)인 다른 라우트는 `with store.reuse():`로 감싸면 된다.
